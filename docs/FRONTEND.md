# Frontend

> Chinese: [Chinese](zh-CN/frontend.md)

WiseEff frontend is a Vite, React, TypeScript SPA. It supports a rich mock-backed prototype plus API mode for the M0-M6.2 productized backend surface.

Mock parameter mode keeps existing canonical-equivalent features only (#1087, #1080 Q3). Legacy Spec governance, module mapping/registry identity, organization overlay authoring, identity/spec-review task resolution, and legacy parameter detail are withdrawn; old deep links cannot revive those controls. Catalog demos, business-module taxonomy, project value editing, and structural node enablement remain. Historical legacy UI notes below do not describe available mock features.

**Workflow discovery (ADR-0036).** Sidebar groups and homepage wayfinding (cards, flow tabs, header/footer workflow links, and promotional copy that names a workflow) read `VISIBLE_WORKFLOWS` in `src/domain/workflowDiscovery.ts`. The allowlist includes parameter management, debugging, log analysis, and knowledge. The log analysis sidebar group contains Intelligent analysis (`/logs`) and Log administration (`/log-admin`), each gated by the same permissions as its route. The homepage offers four scenes. The knowledge group contains Knowledge (`/knowledge`) and Knowledge administration (`/knowledge-admin`), filtered by their route permissions; administration is Admin-only. Homepage cards, flow tabs and workflow links present knowledge as the place to upload and curate the organization's own tuning experience, failure cases, hardware manuals and procedures. Existing Xiaoze citation, log-report and Definition deep links remain unchanged. This is not a permission change and not a `NoEntryPage` retirement.

## Key Directories

Catalog definition revisions distinguish omitted optional content (retain) from explicit `null` (remove) for `unit`, `examples`, and `description`. The definition editor previews cleared units/examples and publishes a new revision. Both creation and editing accept multiline DTS property statements (the property key must match) or DTS values as one example, using the existing DTS parser. String lists retain numeric-looking strings, empty strings, commas, escapes and pipe characters. Existing JSON example arrays still round-trip with their types and nested structure unchanged; blank input removes examples. Malformed input stays editable and cannot publish. Parsed examples still pass the server's published value-schema checks. The current form has no description input, so unrelated edits preserve description; historical revisions remain readable.

- `src/app/`: page routing, navigation, permission checks, and `appRuntime.ts` — the composition root that selects every mode-dependent adapter once (`createAppRuntime`); pages receive the record via `PageProps.runtime`.
- `src/domain/`: role, parameter, log, debugging, audit, and Agent domain types and pure logic.
- `src/application/state/`: the global prototype state machine — `AppAction`, `reducer`/`appReducer`, and reducer-only transition helpers. API boot lives in `createApiInitialState()` here (#486); import state types from here, never from `@/App` (ADR-0023).
- `src/application/bridge/`: shared C5 protocol / bridge / target types and helpers (`bridgeTargetSession`, #488) used by `/node-debugging` and `/dts-reload`. The two sessions stay separate; there is no hollow `BridgeGateway` HTTP port.
- `src/application/debugging/`: `/node-debugging` session (`nodeDebuggingSession`, #485) on the same snapshot/subscribe/command shape as dts-reload.
- `src/application/ports/`: frontend-facing business interfaces.
- `src/infrastructure/mock/`: mock state and mock implementations for demos/tests. Failures throw `WiseEffApiError` via `mockApiError` so application `error.code` branches work in mock mode as well as API mode (TD-109; leftover `Object.assign` paths closed in #483). `createPrototypeState` lives in `prototypeState.ts` (#486); `src/mockData.ts` is a test-facing re-export.
- `src/infrastructure/http/`: API client, DTOs, auth client, runtime mode.
- `src/components/`: reusable UI, layout, tables, dialogs, filters, charts. Search inputs use `SearchField` (`src/components/common/SearchField.tsx`). Local structured filtering uses `src/lib/search/` plus a Search Profile in `src/lib/search/profiles.ts`. Catalog, Knowledge, Audit API, workbench unified search, and raw log / DTS source find keep their existing engines and only reuse the SearchField chrome.
- `src/features/agent/`: Xiaoze CopilotKit surface (`XiaozeProvider`, `useXiaozePageContext`, `XiaozeApprovalCard`, frontend tools).
- `src/features/log-analysis/`: `LogsPage` (upload, conclusion, evidence chain, raw viewer) and `LogDashboardPage`. Feature styles live in colocated `log-analysis.css` (imported from the pages; #476).
- `src/features/parameter-review/`: `ParameterReviewPage`, `ParameterSubmissionsPage`, submission-history diff, and review-specific UI atoms. Feature styles live in colocated `parameter-review.css` (#479).
- `src/features/parameter-catalog/`: canonical Parameter definitions page module (`CatalogPage`) mounted at `/parameter-admin/specs`. Project admin remains `ParameterAdminNextPage`.
- `src/features/parameter-catalog-governance/`: same-page Registration, Review Queue, Proposal, and M1/M2 publication (add a supported Definition, create a Subject with first definitions, or revise documentation/supported semantics) composed onto `CatalogPage`.
- `src/components/project-configuration-workbench/`: configuration workbench. Feature styles live in colocated `configuration-workbench.css` (#484); shared `.workbench-page` / `.workbench-sheet` chrome stays in `src/styles.css`.
- `src/features/product-feedback/`: sidebar `FeedbackDialog` and Admin triage UI for `/feedback-admin`.
- `src/features/knowledge/`: knowledge base pages for `/knowledge` and `/knowledge-admin` (list, split editor, upload, revisions).
- `src/test/setup.ts`: Vitest DOM setup.

## Runtime Modes

Organization management uses peer destinations for Overview, Members, Invitations, Teams, Project participation, Business handovers, Resources and Organization details. Ordinary members see Overview, published Resources and read-only Organization details. Resource children retain an explicit current location. The compact scope bar names the authorized target once; the profile owns the organization ID and creation metadata. Overview metrics share one full row, and zero pending items collapse to one empty state. Invitation and identity-sync actions carry their pending filters in the URL; project and member selection survive scoped deep links.

Member details separate basic information, access and project duties while preserving drafts across sections. Single-member duties show only that member's roles. Creation dialogs keep specific action labels; pending operations freeze inputs and selections, and accidental dismissal uses the shared unsaved-work guard. Searchable multi-selects use the existing Radix popover, design tokens and shared search. Suspended organizations retain credential reads with write actions disabled. Handover domains and directory authentication configuration load independently, so optional failures do not erase successful collections. Password resets protect platform administrators under the existing user locks; a successful self-reset ends the session.

In API mode, the platform Organization directory (`/platform/organizations`) is available only to organization-wide platform super administrators. It searches Organization names/IDs, shows status and administrators, and creates an Organization with its initial organization administrator in one transaction. Local mode provisions a username/password; OIDC mode binds the configured issuer and an explicit subject, then displays the new Organization ID for the identity provider's organization claim. Creation and viewing basic details leave the real operator's Home organization unchanged. Organization details offer entry to `/organization?organizationId=…`; the workspace displays the authorized target and Home organization, and can return to the directory or Home organization.

Organization member/settings requests bind `organizationId` to an immutable client instance. The server resolves every explicit target without rewriting the authenticated actor, and member creation, profiles, roles, activation, deletion, password resets, OIDC binding and project review-duty management reuse the existing domain services and administrator-continuity guard. The member directory and project candidates are local to that workspace, never hydrated into the Home-identity shell. Target changes remount the view, ignore late responses and use the existing unsaved-navigation/unload guard, including account/password drafts; passwords are not persisted. `withOrganizationScope` is the shared URL helper for scoped clients. This member/settings slice does not imply that other business consoles already accept a cross-organization target.

Organization details provide administrator recovery: appoint an existing member (reactivating them when necessary) or provision a new local/OIDC administrator, including for a memberless Organization. Explicit emergency disabling requires a reason and records the real platform actor and target Organization. Ordinary role removal, disabling and deletion, including self-departure, retain a usable Organization administrator; an independent global rule always retains a usable platform super administrator. Effective counts use organization-wide roles and the configured login provider, preserving legacy HMAC/development and OIDC identity compatibility. The directory distinguishes disabled administrators and missing login identities. Successful self-disabling/deletion ends the session; changing one's own roles refreshes authority and leaves administration when that permission is removed.

Organization device governance (`/organization/bridges`) and the integration-credential overview (`/organization/integrations`) use the same fixed target as members and settings. The overview and each skill's filtered integration view share `IntegrationCredentials` and its credential client; the overview can filter by binding, issue unbound organization credentials, rotate and revoke, while a skill view can issue credentials bound to that skill. Secrets appear only in the issuance/rotation dialog. Governance never transfers a member's pairing or device-execution authority: personal pairing and owner execution remain in the real actor's Home organization. Machine credentials retain their own fixed organization independently of their creator.

Default mode is `api`. `npm run dev` and `npm run dev:all` inject API runtime settings; copy `.env.example` to `.env` for the same defaults when using other Vite entrypoints.

```text
VITE_WISEEFF_RUNTIME_MODE=api
VITE_WISEEFF_API_BASE_URL=http://127.0.0.1:8787
```

The Project configuration workbench is the **canonical** project-operations experience (`/parameter-admin/projects/:projectId/configuration`). The former development flag `VITE_PROJECT_CONFIGURATION_WORKBENCH_ENABLED` is retired and ignored (#240). See `.env.example` and `docs/developer/environment-variables.md`.

Use `mock` only for frontend-only demos or component tests that should not call the backend:

```text
VITE_WISEEFF_RUNTIME_MODE=mock
```

Production builds must not use mock runtime as a business data source.

API mode never falls back to mock data. The shell boots from `createApiInitialState()` (structural fields kept, every business-data slice empty — including `auditEvents`; unused `developers` / `logAdminUsers` slices were retired in #474), shows a slim connecting strip until the first runtime sync completes, and when a domain refresh (parameters / logs / debugging) fails it clears that domain's slices via `CLEAR_API_RUNTIME_DOMAIN` and raises a persistent page-level cannot-connect / no-data error banner with a retry button instead of quietly keeping demo records on screen. Successful hydration also repoints `activeProjectId` at real server projects when the demo id is unknown. #480 stops `ParametersPage` and the reducer from falling back to `mockData.projects` when `configDraft.projects` is empty; API boot uses `createEmptyPowerManagementConfig()`. #486 reconstructs `createApiInitialState()` as an empty shell (it does not call `createPrototypeState()`). Its identity fields also start empty and guest-safe (`users: []`, `currentUserId: ""`, `activeRoleId: "guest"`); `/api/v1/me` inserts only the authenticated current user, and `/api/v1/users` hydrates the governed directory only on `/organization/members`. The nine demo users and all other mock seeding live in `src/infrastructure/mock/prototypeState.ts`. Mock mode behavior is unchanged.

M6.2 OIDC runtime support uses an async authorization provider so API clients can request the current access token and handle refresh/logout failures without static bearer injection. `VITE_WISEEFF_API_AUTHORIZATION` remains a local static-token convenience and is rejected by production builds.

When API mode starts, the app calls `/api/v1/me` before rendering the main shell. If the current token is missing or rejected, it shows the WiseEff auth screen with local account login and (when enabled) registration forms. The screen first loads unauthenticated `GET /api/v1/auth/local-config` when the auth client exposes `getLocalAuthConfig`. Local login uses username and password. Registration collects name, a self-service platform role, username, password, and a password confirmation. There is no organization picker; the new account joins the Evaluation Organization (ChargeLab when seeded; otherwise the single bootstrap Organization). The auth screen states that join rule, username syntax (3–64 characters; letters, numbers, dots, underscores, hyphens), and a one-line role hint. The registration role picker excludes Admin. When `selfRegisterEnabled` is false, the Register tab is hidden; when `hasLocalAdmin` is false, the screen shows the `npm run admin:bootstrap` hint. Hardware/Software Committer requests create an inactive account with the matching base User role plus a pending Admin approval request; `/api/v1/auth/register` returns `202 pending_approval` without a session token, and the auth screen stays on a pending-approval result state without the editable registration form until an Admin approves the request from `/organization/members`. Successful local login or non-committer registration stores the opaque `we_local_*` session token in `localStorage` under `wiseeff.localAuthToken`; the default API client prefers an OIDC runtime token when one is available and otherwise falls back to this local token. The topbar user menu opens the current-user profile dialog and logout action. Profile updates call `PATCH /api/v1/me/profile`. When the auth client exposes `changePassword`, the profile dialog also submits `POST /api/v1/me/password` and reports that other sessions were revoked. Logout calls `POST /api/v1/auth/logout` and clears the local token.

The startup probe distinguishes an auth rejection from an unreachable backend so a server restart or network blip never logs everyone out. Only a `WiseEffApiError` with code `UNAUTHENTICATED` or `FORBIDDEN` clears the local token and drops to the login screen; any other failure (fetch `TypeError`, timeout, 5xx) keeps the token and enters the `unreachable` auth state, which renders a branded cannot-connect screen whose retry button re-runs the probe (`authProbeAttempt`) and resumes the session in place — no re-login. While the probe is in flight the `checking` state renders a lightweight session-restore screen instead of the interactive login form, so a refresh no longer flashes the login page. Both states reuse `.auth-panel` chrome (`.auth-status-panel`).

Notification feedback (`state.notifications`, pushed by `ADD_NOTIFICATION`) reaches the screen through one renderer: `AppToastLayer` (`src/components/common/AppToastLayer.tsx`) is a render-less bridge mounted once in the AppShell for **both runtime modes**; it drains each queue entry into the design-system `ToastProvider` (`useToast`) with a word-level tone inference (failure vocabulary → `danger`/`role="alert"`, completion vocabulary → `success`, otherwise `info`) and immediately consumes the entry via `DISMISS_NOTIFICATION`. `ToastCard` owns display: ~4s auto-dismiss, hover pause, stacking in `.toast-viewport` (the `--z-toast` layer, above dialogs and the Xiaoze popup), and a labelled manual close button. Imperative `useToast()` calls and reducer notifications therefore share one visual pipeline. This replaces the earlier mock-mode-only toast inside `LogsPage`, which left every API-mode success/failure notice invisible. Detail selections are deep-linkable: `/parameter-review?request=<id>` restores the selected review row and the page keeps the address bar in sync via `history.replaceState`; `/logs?logId=<id>` (the copy-link target) restores the selected log after API hydration without letting the newest-upload auto-selection override it. The review queue (`/parameter-review`, pending view) supports batch advance for inspection-stage change requests: a checkbox column appears when actionable rows exist (initialization reviews and the merge stage are excluded — merging needs a per-request merge link), the toolbar arms a batch-approve button, an aggregated ConfirmDialog states the blast radius, and execution is sequential per request (`reviewChange` with `notifyOnFailure: false`) with one summarized success toast and one summarized failure toast; failed rows stay selected for retry. The same page localizes workflow statuses through `formatWorkflowDisplayText` (exact maps such as Hardware Committer inspection → Hardware MDE inspection, including column-filter labels) and supports unchorded queue shortcuts documented below. Server failures surfacing through runtime notifications go through `toUserErrorMessage` (`src/infrastructure/http/userErrorMessage.ts`), which maps `WiseEffApiError.code` (and known `details.reason` values) to Chinese copy with a short request-id suffix; unknown codes keep the server text but stay reportable, and fetch-level network failures get connectivity copy.

The audit center (`/audit`) pushes its filters down to `GET /api/v1/audit-events`: text search (`q`, matching action / kind / target id / actor name server-side), a time window (today / last 7 days / last 30 days, sent as `from`), plus the existing app-group / project / severity / trace filters and cursor paging. The CSV export button exports the current filter's full result (paged fetch, 2000-row cap) as UTF-8-BOM CSV with Chinese headers and Chinese labels for app / kind / action / severity, keeping the raw kind and action slugs in dedicated columns for machine filtering. Event rows and related trace events use the shared Chinese labels with secondary monospace codes; unknown codes remain visible verbatim. In mock mode the same filters run client-side.

Catalog definition rows retain the published display name next to a monospace property key; Chinese names are Catalog release content tracked by #1114, not UI translations. When Catalog adoption is incomplete, `/parameter-admin` shows plain-language status with a Chinese-labelled “Learn more” disclosure; this does not imply an automatic adoption process is running. Only platform admins and operators see the operator handbook's inspect/adopt instructions inside it. Definition details show the server's actual blocker (adoption, policy, freeze, authorization, or a failed status read), rather than attributing every restriction to missing account permissions. Server authoring and publishing gates remain unchanged.

Definition actions also respect each row's owning subject and registration. Retired subjects, stopped registrations, and deprecated/retired definitions open complete read-only details with their subject name and history intact; a retired definition can still be restored under an active subject through the governed lifecycle command. The routine release/version strip is omitted; actionable loading, conflict and error notices remain, and a subject-specific notice names a retired subject. Detail reads and authoring checks resolve the definition's actual owner independently of the list's subject/module scope. Opening or closing details preserves the list filters, pagination, and navigator selection/expansion; data refreshes do not remount the workspace. Superseded detail/history requests cannot replace the current selection.

The definition module navigator starts with collapsed branches and reveals a selected module/subject path automatically. Folder, driver and node-type icons distinguish the levels; subject status sits beneath its name, long names retain full tooltips, and counts remain in a fixed badge column. There is no “All definitions” row; activating a selected module or subject again clears that selection while preserving search conditions. Module management also omits the “All modules” row and duplicate tree heading/instructions; both navigators retain a visible search field and module management omits the advanced-filter section. Definition navigation searches module/subject names, keeps ancestor paths, reveals matches without changing the definition list, and restores disclosure state on clear. Obsolete module-filter URL flags no longer hide content. Both module navigators use the same name typography. Expanding a branch alone never changes the list filter.

The definition workspace excludes definitions owned by retired subjects by default. “Include retired subjects” opts into history and is preserved in the URL; switching it resets the cursor and keeps search, module scope and page size. Historical subject bookmarks opt into history automatically. The server applies owner lifecycle before pagination and counts, separately from definition lifecycle. Opening a historical definition does not change the workspace notice or entity toolbar target: detail state controls the editor, and the explicit navigation subject controls the workspace. Read-only details use one compact owner/registration/definition status instead of repeated retirement paragraphs.

Definition dialog headers contain only the action/title and close control; subject and revision information remain in the body/history. The creation dialog offers a new definition or a new subject, while existing definitions are revised through their list-row editor. It does not fetch the existing definition inventory or expose a permanent evidence-refresh action. Subject loading failures have a local retry; publication conflicts or blocked conditions offer a contextual status update. Retrying or updating the catalog version preserves entered fields and invalidates an outdated preview. Restored revision jobs remain trackable without reopening a second revision form.

The parameter workbench prefers the optional `currentDisplayName` from the current published Catalog head; `displayName` remains the Binding's pinned revision copy. Documentation-only renames therefore require no Binding or Project value cutover. The display-description column appears only when the current filtered result has a nonblank description. Property keys remain single-line, ellipsized, with their full key in a tooltip. Reseeding resolves the default driver group by its stable source key and renames only the legacy seed default ("Seed placement capacity") to its Chinese display name ("Default driver group"); administrator-chosen names remain unchanged.

Module management exposes root creation in the top toolbar. Business-module row menus offer child creation and “Change parent module”, including promotion to the root; self/descendant targets are excluded. In API mode, these taxonomy controls follow the session's `admin:access` permission and exclude Agent actors. Catalog subject registration and placement keep their separate organization-governance authorization.

Definition search applies automatically after a 300 ms pause and waits for IME composition to finish; Enter applies immediately. Search changes replace the current URL entry, preserve scope/filters and reset pagination. The shared input's clear control replaces separate search/clear buttons. Organization review opens from the pending-review action, with the same name used in its dialog and source-identification link.

Pending reviews use one bounded workbench for the list, evidence and resolution form; only the final approval or discard confirmation adds a dialog. The list searches authorized source facts and filters by reason/project, with pagination controls after the table and an audit-history link. Source details distinguish observations, properties, evidence and Catalog subject identities, including every source in a grouped review. Resolution choices explain their effect and require real subject/module/registration targets; unknown sources offer a definition intent or exclusion instead of an unusable registration form. Reasons are required, drafts survive evidence refresh, and leaving a changed form asks before discarding. Loading, permission denial, stale evidence and completed work have distinct states. Success updates the queue/count, shows a business receipt and links to the relevant next step or audit record. Opening a review does not reload the definition inventory, and focus follows list/detail transitions.

Review evidence is checked automatically when the form opens, the window becomes active again, and before final confirmation. There is no permanent refresh action or polling. Normal checks are silent; changed evidence or targets invalidate confirmation and require another review. Failed checks retain the draft and expose a retry action. Responses from a previous organization or Catalog context cannot update the current workbench.

## TopBar Project Selector

The TopBar project picker is visible only on everyday parameter-management routes. `pageUsesProjectScope()` in `src/appConfig.ts` returns `true` for `parameters`, `parameter-submissions`, `parameter-review`, and `parameter-home`. It is hidden on `/parameter-admin` and `/parameter-admin/projects` (organization-scoped governance and project operations own their own pickers; see ADR-0001), and on log analysis (`logs`, `log-admin`) and debugging (`node-debugging`, `debugging-admin`) routes because M2/M3 data loads from authenticated organization context without `projectId`. Parameter pages may still read `?project=` from the URL; log and debug pages ignore project query params.

### Parameter admin (governance scope)

`/parameter-admin` is a **single sidebar destination** (label: Parameter admin under the parameter-management group). Organization-scoped governance and project-scoped operations switch via peer scope tabs; `/parameter-admin` redirects to `/parameter-admin/specs` (query preserved). Organization peer routes are `/parameter-admin/specs` (parameter definition management: library + embedded spec review; nested `/parameter-admin/specs/identity-mapping` while unresolved historical mapping evidence exists) and `/parameter-admin/modules` (module management). Legacy `/parameter-admin/spec-review` and `/parameter-admin/identity-mapping` permanently redirect to the new locations with query preserved (ADR-0015). Project deep links use the canonical `/parameter-admin/projects/:projectId/configuration` workbench route; legacy `/parameter-admin/projects/:projectId/{files|config-sets|structure|conflicts}` paths redirect to equivalent workbench contexts for one compatibility release (#240). Panels consume a single `createParameterAdminApplication` facade over `ParameterTopologyRepository`, `ParameterModuleRegistryRepository`, and import actions from `parameterActions` (resolved for both mock and api modes). Admin cross-panel state lives in `ParameterAdminProvider` — not global `PrototypeState`. URL query params (`q`, `lifecycle`, `driver`, `sort`, `spec`, …) are the source of truth for filters, sort, and selection. Bulk import is a TopBar action on organization sub-routes. Spec review pages through `listSpecReviewTasks` cursor pagination; the spec library paginates client-side (50/page) and hides structural `#…` properties by default. Operation `PARAM-IDENTITY-MAP-ADMIN-001` tracks admin-side identity mapping coverage (browser acceptance retarget in #198).

The project-list entry opens `/parameter-admin/projects/:projectId/configuration` (label: Configuration workbench). This Phase 1 route is a full-screen, source-dominant workbench: Configuration and file query state select the Working configuration, configuration-file membership and active source come through the existing `DtsStructuredRepository` and `ParameterFileRepository` ports in both runtimes. Source-located navigation (#229) nests the structural node tree under the selected member, scrolls/highlights CST spans via `ProjectPrimaryDtsViewer`, runs unified search (file-grouped, omit-`by` = all dimensions) across Configuration members, and restores `configSet`/`file`/`node`/`property`/`sourceMode` deep links; tree metadata and source load/retry stay independent. Keyboard helpers use Alt+F / Alt+N / Alt+G / Alt+1 / Alt+2 (and `/` when not typing) so browser/system shortcuts are not overridden. Context inspection (#230) separates node/property details, versions (including file details), source updates, release and activity tasks while preserving source selection. The Versions task lists immutable versions (origin label, operator display name or "unrecorded", time) and downloads through `ParameterFileRepository`; registered source rollback requires human review, while legacy unbound files retain ConfirmDialog → `rollbackVersion` (inserts `origin=rollback`, does not rewind); canvas modes `working` / `history` / `unified-diff` / `candidate` stay read-only and restore the prior Working target/scroll on exit (legacy `side-by-side` URLs use `unified-diff`; `structured`/`raw` remain Working aliases). Source updates (#231) open from File management through Update file, or Update records for read-only users; empty configurations offer their first upload there. Its panel uploads a new file for the current member or adds a source file when no member is selected, creates a staged candidate via `ParameterFileRepository.createCandidate` without changing the active version or Configuration membership, shows unified differences against the candidate's proven source base plus impact evidence (structural diff, diagnostics, coverage/mapping, conflicts, blockers) in source update mode and the inspector, supports blocked/stale recompute and abandon for ready/blocked/failed/stale, and keeps Working / file-version / candidate / release-baseline identities independently labeled. Candidate activation (#232) adds an impact-confirmation dialog and `ParameterFileRepository.activateCandidate` with expected-current-version CAS; new-file activation requires an explicit Configuration member role; stale base preserves Working configuration and requires recompute; blocked/failed/abandoned/stale are never activatable; success refreshes files/members/source without a full-page reset. Structured edit sessions (#233) open `StructuredValueEditor` in the property inspector (`canEdit` / `canEditCritical`), accumulate session drafts in the task dock with subset validate/submit through `submitStructuredEdits` / `aggregateLocalStructuredEdits`, share property identity across tree and source-gutter markers, and keep the source canvas read-only (whole-file replacement remains the Candidate path). Recoverable session drafts (#234) persist patches and reason locally (never full DTS source) under a user/org/project/config/file/base scope: navigation or refresh restores when the base matches; a changed base keeps drafts inspectable/copyable but blocks validate/submit until reconfirm; leaving with dirty drafts uses ConfirmDialog; logout clears via `clearSessionDraftsForLogout`. Missing edit capability locks writes with product language while read context stays visible. File and Configuration operations (#236) let Admins create/configure Configurations with validation and duplicate-name handling, add/remove members with role and sortOrder through ConfirmDialog blast-radius confirmation, keep unassigned project files outside the Working/Release context until assigned, run manual sync via `ParameterFileRepository.syncFile` with dismissible operation feedback, and export the selected Configuration via `DtsStructuredRepository.exportConfigSet` from the command context; empty Configurations present a focused Candidate upload/assignment path that does not auto-activate, and `canAdmin=false` denies mutations while keeping read context. Conflict arbitration (#235) opens a source-located three-way Conflicts dock from the task bar: base / file-or-candidate / pending UI draft with provenance and readable version labels; equal-weight "Use file value" and "Keep UI value" outcomes confirm via ConfirmDialog with an optional audit reason; the queue advances in source context; eligible bulk resolve requires an impact preview first; an empty queue keeps the dock collapsed without a dedicated empty page; open conflicts continue to block Candidate activation. Release readiness (#237) loads one server-owned `getReleaseReadiness` result into the command-bar summary and release panel (ordered blockers/warnings with locators and remediation); create/release require a matching `gateToken` and stay fail-closed when blocked, unavailable, stale, or when local session drafts are dirty; the UI never reconstructs release permission from unrelated client counts. Release baselines (#238) surface draft/released/historical identities with pinned members in the inspector dock (`WorkbenchBaselineDock`), compare against Working in unified diff (restoring the prior Working position on exit), require warning acknowledgement plus impact ConfirmDialog for release (demotes prior tip to historical, refreshes drift/readiness), and restore via preview blast radius + atomic rollback that leaves the released tip unchanged. At desktop widths (769px and above), the detail panel sits beside the task area without covering source content; users can collapse file navigation for more space. The default toolbar uses one row, including at 1280px. A sole Source view has no tab; Source and Conflicts tabs appear when conflict content is available or explicitly opened. Widths of 768px and below retain the existing overlay behavior. Activity (#239 / PCW-D11) adds a command-bar Activity entry that opens an activity inspector over scoped `listAuditEvents` projections (parameter apps + current project); events use product language for actor/action/target/outcome/time, restore targetable Configuration/file/candidate/node/property context when possible, and keep missing targets as readable evidence. Legacy `/files` `/config-sets` `/structure` `/conflicts` deep links redirect to equivalent workbench contexts for one compatibility release; `/structure` and `?tab=structure` open Source while retaining file, node and property identity. The central Structure page and tab are removed. `ProjectOperationsDialog` and the four-view page-shaped panels are removed (#240).

**Project tab chrome:** the configuration workbench owns project deep views; legacy four-view dialog chrome is removed. Empty queues use `ParamAdminEmptyState` (`.param-admin-empty`) with a short status line, optional guidance, and an optional next-step action. Scope navigation (`.parameter-admin-scope-nav`) is visually heavier than organization sub-nav (`.parameter-admin-subnav`) so containment is readable: scope uses larger, solid-primary active pills with soft shadow; sub-nav keeps smaller outlined pills for every peer (not only the active one) so inactive destinations still read as switchable. The projects list page keeps a single authoritative heading (the project inventory title); the TopBar subtitle mirrors the list or workbench name instead of repeating the scope label. Encodings are never guessed from the property name. Current `dtc`/`fdtoverlay` plugin compile drops `/delete-property/` to an empty fragment; preflight refuses that no-op instead of shipping it.

## Button And Action Styling

Buttons must look and behave like buttons. Do not rely on a bare `.button` class, raw `<button>` browser defaults, or text-only styling for actions that mutate state, submit forms, close dialogs, navigate workflows, or open menus. Use the existing button component or an established local variant; if a scoped button variant is needed, define the full visual contract in that scope:

- layout: `inline-flex`, centered content, stable `min-height`, and stable `min-width` or icon-only square dimensions;
- surface: explicit `background`, `border`, `border-radius`, text color, and disabled opacity/cursor;
- hierarchy: clear primary, secondary/subtle, destructive, or ghost treatment instead of two equal-looking text labels;
- interaction: hover and focus-visible states, with focus rings that remain visible on light and dimmed modal backdrops;
- responsive behavior: buttons must not collapse to bare text, overlap siblings, overflow their container, or change layout unexpectedly across desktop, tablet, and mobile widths.

Dialog footers, table row actions, topbar actions, card actions, and toast actions are common regression points. When changing them, add a focused DOM assertion for the intended button variant or class and run browser verification that captures the relevant state. The browser check should explicitly confirm that primary and secondary actions have visible surface styling, stable dimensions, and no horizontal overflow. Text-only actions are acceptable only for low-emphasis links or inline affordances, and should use a link/text-action class rather than masquerading as a button.
