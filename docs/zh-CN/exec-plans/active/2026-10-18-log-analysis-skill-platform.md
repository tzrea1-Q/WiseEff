## 目标

把已上线的日志分析系统变成通用平台。管理员为每个业务模块构建**分析技能**：诊断流程、结构化日志内容的声明式解析与解码、信号规则、来自知识库的 Markdown 知识、模块源码以及测试用例。WiseEff 提供通用基础设施：日志包接收与解压、文件管理、通用信号提取，以及能运行任意技能的统一有界 Agent 工作流。集成方接入新场景只需发布技能，无需修改 WiseEff 代码。

## 背景

当前代码提供了什么、止步于何处，记录在 ADR-0047"背景"一节。简言之：保留作业管线、只读有界 Agent、接地、诚实降级、组织作用域以及两层评测；本计划替换的是代码中的领域规则、无版本的实时域配置、固定工具集、单文件接收、无法解读的结构化载荷和仅面向开发者的质量检查。

### 已定决策（产品负责人，2026-10-18）

- **解析**：先做声明式。必须支持从已知格式的行中抽取数据，并按配置的规则（如协议字段、寄存器定义）解码。仅限日志解析的脚本在后续阶段支持。
- **数据流**：源码和日志片段可以发送给已配置的后端 LLM API（`LOG_ANALYSIS_*`）。
- **参考模块**：不等待第二个业务模块，直接推进通用设计。首期实现落地后，产品负责人按集成指南在真实场景中验证。
- **内核**：ADR-0022 继续有效——普通有界循环，无 LangGraph、无 ToolRegistry、无写路径。
- **UX**：由实施 Agent 采用成熟模式决定，并记录在 PR 中（长期授权）。

## 非目标

- S6 之前执行管理员代码，或任何技能获得设备、参数或数据库写权限。
- 针对报告的交互式追问对话（按 ADR-0022 需要新 ADR）。
- 非面向行的二进制日志格式（例如原始环形缓冲区转储）。文本行中的十六进制或 base64 载荷在范围内。
- 用于源码或日志的外部检索服务。
- 跨组织的技能市场。组织间导出/导入在范围内，共享发布不在。

## 架构

### 技能与版本

```
分析技能（组织作用域身份；即现有 log_domains 行）
 └─ 技能版本（草稿 → 已发布 → 已取代；发布后不可变）
     ├─ procedure.md          诊断流程，插入 Agent 提示词
     ├─ 适用范围              文件通配 + 特征模式（路由、文件角色）
     ├─ 解析规范              格式画像 + 抽取器 + 解码器（带版本的 schema）
     ├─ 信号规则              针对行、字段和解码值的条件
     ├─ 知识链接              知识库条目（取其当前已发布修订）
     ├─ 源码快照引用          可选默认快照 + 版本标签匹配
     ├─ 预算/模型             最大步数、token 预算（≤ 平台上限）、模型名
     └─ 测试用例              解析测试（确定性）+ 分析用例（真实模型）
```

- 运行钉住 `skill_revision_id`；Worker 只加载所钉版本。
- 运行记录实际使用的知识修订和源码快照。
- 没有技能时，运行只使用平台通用信号和工具（演进后的未分类域）。

### 解析与解码（回答"能否做到"：能）

已知格式的行由抽取器匹配；捕获字段被类型化；类型化的值用封闭的构件集合解码。下面的 schema 仅为**示意**，最终 `parsing/v1` schema 在 S3 确定。

```yaml
# 本例解码的行：
#   2026-10-12 08:14:03.112 [chg] reg_dump addr=0x0C val=0x20
#   2026-10-12 08:14:03.140 [pd] rx hdr=0x2161 data=2C9101082CD10200
#     → msg_type Source_Capabilities，2 个固定 PDO：5000 mV / 3000 mA，9000 mV / 3000 mA
extractors:
  - id: reg_dump
    files: ["kernel*.log", "dmesg*"]
    pattern: '\[chg\] reg_dump addr=(?P<addr>0x[0-9A-Fa-f]+) val=(?P<val>0x[0-9A-Fa-f]+)'
    fields:
      addr: { type: uint }
      val:  { type: uint, decode: { registerMap: bq25890, keyField: addr } }
  - id: pd_rx
    pattern: '\[pd\] rx hdr=(?P<hdr>0x[0-9A-Fa-f]{4}) data=(?P<data>[0-9A-Fa-f]*)'
    fields:
      hdr:  { type: uint, decode: { register: pd_header } }
      data: { type: hexbytes, decode: { frame: pd_data_objects } }

registers:
  pd_header:
    width: 16
    fields:
      - { name: msg_type,    bits: "4:0",   enum: { 1: Source_Capabilities, 2: Request } }
      - { name: num_objects, bits: "14:12" }
  fixed_pdo:
    width: 32
    fields:
      - { name: supply_type,    bits: "31:30", enum: { 0: fixed, 1: battery, 2: variable, 3: apdo } }
      - { name: voltage_mV,     bits: "19:10", scale: 50 }
      - { name: max_current_mA, bits: "9:0",   scale: 10 }

registerMaps:
  bq25890:                       # 按地址索引的寄存器定义
    0x0C:
      width: 8
      fields:
        - { name: WATCHDOG_FAULT, bits: "7" }
        - { name: CHRG_FAULT,     bits: "5:4", enum: { 0: normal, 1: input_fault, 2: thermal_shutdown, 3: safety_timer } }
        - { name: NTC_FAULT,      bits: "2:0" }

frames:
  pd_data_objects:
    endian: little
    repeat: { count: "$hdr.num_objects", item: { register: fixed_pdo } }

signals:
  - id: charger-thermal-shutdown
    when: { extractor: reg_dump, field: "val.CHRG_FAULT", equals: thermal_shutdown }
    severity: error
    label: 充电芯片报告过温关断
```

第一行的解码事件：

```json
{ "file": "kernel.log", "line": 412, "extractor": "reg_dump",
  "fields": { "addr": 12,
              "val": { "raw": 32, "WATCHDOG_FAULT": 0, "CHRG_FAULT": "thermal_shutdown", "NTC_FAULT": 0 } },
  "signals": ["charger-thermal-shutdown"] }
```

`parsing/v1` 构件集合：

| 构件 | 用途 |
| --- | --- |
| 抽取器 | 文件通配 + 命名分组模式（线性时间引擎）+ 可选多行组装（开始/继续/结束模式，按键字段分组，长度有上限） |
| 类型 | `int`/`uint`（十进制、`0x`、`0b`）、`float`、`bool`、`string`、`enum`、`timestamp`（格式串）、`hexbytes`、`base64bytes` |
| 寄存器 | 固定位宽；按位段划分字段；每字段可设 `enum`、`scale`、`offset`、`unit`、`signed` |
| 寄存器映射 | 按另一字段的值（地址、消息 id）选择寄存器定义 |
| 帧 | 字节布局：按类型/长度排列的有序字段、字节序、嵌套寄存器/帧、按已解码字段 `switch`、以已解码字段为计数的 `repeat`、可配置标签/长度宽度的 TLV、可选固定集合中的校验和（sum8、xor8、crc8、crc16-ccitt、crc16-modbus、crc32） |
| 查找表 | 代码 → 含义（错误码、状态）；也可在知识中编写 |
| 信号规则 | 基于消息正则、字段相等/范围/集合、解码值或时间窗内计数的条件；产出带级别的具名信号 |

有界执行：解码深度 ≤ 8，帧 ≤ 4 KiB，重复 ≤ 256，单行长度上限，单次运行事件数与时间上限；超出上限时在该事件上记录解码错误，而不是让运行失败。

超出 `parsing/v1`（S6 脚本）的情形：键控多行组装之外的有状态重组、压缩或加密载荷、厂商专用校验和，以及需要跨事件运算的计算字段。

### Agent 工作流

沿用 ADR-0022 的循环，按运行组合工具：

| 工具 | 可用条件 | 阶段 |
| --- | --- | --- |
| `list_files`、`search_lines`、`read_line_range`（感知文件） | 始终 | S2（此前为现有单文件版本） |
| `get_signals`（通用 + 技能信号；保留旧 `get_prefilter_findings` 兼容） | 始终 | S1（技能信号）、S2（通用信号） |
| `get_line_templates`、`get_timeline` | 始终 | S2 |
| `query_events`、`describe_event_schema` | 版本含抽取器 | S3 |
| `read_domain_knowledge` | 始终（链接集合，否则全组织） | 已有 |
| `find_log_statement`、`search_source`、`read_source_range` | 版本含已索引的源码快照 | S4 |
| `get_related_parameter_context` | 运行带关联参数钉 | 已有 |

提示词顺序：平台协议 → 技能诊断流程（分隔、优先级更低）→ 任务（问题、文件清单、信号、预算）。证据类型：日志行（`file`、`line`）和源码位置（`snapshot`、`path`、`line`）；两者都以工具结果为接地依据。平台上限：步数 ≤ 20，token 预算 ≤ 全局 `LOG_ANALYSIS_TOKEN_BUDGET` × 4（具体上限在 S1 结合成本测量确定）。

诊断流程切片（#1227）从运行钉住的版本读取可选的 `skill/v1.procedure`（上限 20,000 字符），作为低优先级的不可信分隔段追加到系统协议之后、用户任务之前。流程经过 JSON 引用，分隔符字符和行分隔符转义；伪造结束标签和协议标题仍留在数据值内部。流程不能覆盖接地、工具结果证据、拒绝规则或禁止写操作的约束。规则回退忽略流程；无流程时省略流程段，平台信号工具仍可用。当前循环版本为 `2026-10-19.loop.procedure.signals.1` / `2026-10-19.loop.procedure.signals.related-parameter.1`；单发版本为 `2026-10-19.procedure.signals.1` / `2026-10-19.procedure.signals.related-parameter.1`。报告记录所选版本。行为评测覆盖正常和对抗性流程；PostgreSQL 上传到报告测试捕获脚本模型的提示词，验证草稿修改、发布和钉住版本的重新分析。

## 前端体验

UX 依据长期授权在此决定，并遵循 `docs/design-docs/ui-design-system.md`（令牌、单一强调色、五种交互状态、`ModalDialog`、`AdminListPage`、中文优先文案、空状态只给一个下一步）。三类角色使用平台：

| 角色 | 目标 | 入口 |
| --- | --- | --- |
| 技能作者（管理员） | 把模块经验变成已发布技能 | `/log-admin` 技能列表 → 技能工作区 |
| 分析用户（工程师） | 上传日志，得到可信结论，下钻证据 | `/logs` |
| 集成方（外部系统负责人） | 从自己的系统推送日志并接收结果 | 技能工作区 → 集成 |

### 交互原则

1. **零配置可用。** 不选技能上传也总能用通用信号完成分析；技能提升结果，永不阻挡上传。
2. **样例优先。** 作者先挂一份样例日志。解析、解码和信号页面都实时以它预览：高亮命中行、统计覆盖率、显示解码值。
3. **表单优先，代码可选。** 每条规则都有可视化表单。"代码视图"开关以 YAML 显示同一草稿，便于批量编辑和复制粘贴；两种视图编辑同一草稿，校验规则一致。
4. **草稿、检查、发布。** 顶部固定的草稿栏显示未发布更改、保存/放弃与发布；「运行测试」放在「测试」分区工具栏，旁边显示紧凑运行状态。发布时顶部展示测试结果，再按测试显示变更摘要，失败不阻止发布；回滚即把旧版本发布为新版本。
5. **每个结论一键直达证据。** 证据打开日志查看器并定位到所引用的行，旁边显示解码字段和源码位置。
6. **集成自助完成。** 集成方需要的一切（key、地址、凭据、可复制请求、Webhook、投递记录）都在同一个标签页。

### 信息架构

- **`/log-admin?tab=skills`**（取代 `tab=domains`）：`AdminListPage`，列为 名称 · 适用文件 · 当前版本 · 草稿 · 近 7 天分析 · 有用率 · 集成状态。顶部操作：导入技能包（次要）、新建技能（主要）。空状态：新建第一个分析技能。
- **新建技能对话框**（`md`）：名称、起点（通用文本日志 / Linux 内核 dmesg / Android logcat / JSON Lines / 复制已有技能）、可选样例日志。模板预填诊断流程大纲、基础格式和常用信号。
- **技能工作区 `/log-admin/skills/:skillId`**：导航工作台布局——左侧分区列表、中间编辑区，以及（在 样例与解析 / 解码 / 信号 中）右侧样例面板，跨分区保持滚动位置。分区：概览 · 诊断流程 · 样例与解析 · 解码 · 信号 · 知识 · 源码 · 测试 · 集成 · 版本。
- **`/logs`**：上传对话框、记录列表，以及报告视图，标签页为 结论 · 文件 · 信号 · 分析轨迹（轨迹仅技能管理员可见）。

### 关键交互

| 能力 | 交互 |
| --- | --- |
| 诊断流程 | Markdown 编辑器，预填大纲（适用场景 / 先检查什么 / 根因判定 / 常见误判 / 建议动作），可切换预览。"试运行"用真实模型在样例上运行草稿，并打开分析轨迹抽屉：每一步用了什么工具、读了什么、最终证据。 |
| 基础格式 | 用表单取代现在的格式画像 JSON：时间戳格式（从样例中选取，带自动识别的默认值）、级别映射、多行规则，均带实时样例预览。 |
| 抽取器 | 点击样例行 → "从此行创建抽取规则"。该行拆分为片段；作者框选片段并命名、选择类型。模式自动泛化（数字、十六进制、引号字符串），显示命中数和覆盖率，可在"高级"中直接编辑。每个抽取器在样例面板中有自己的高亮色。 |
| 寄存器 | 位条（高位→低位的方格，按字段着色）加字段表（位段 · 名称 · 类型 · 枚举/比例/单位）。"粘贴寄存器表"可导入从数据手册表格复制的 位、名称、说明 列。寄存器映射在左侧列出地址。选中样例行即在位条上显示解码值。 |
| 帧 | 有序字段行，字节偏移自动计算，配合样例字节的十六进制视图并高亮选中字段；`switch`、重复和 TLV 是行类型，而非自由文本。 |
| 信号 | 句式构建器：当 [抽取规则] 的 [字段] [等于 / 在范围 / 属于 / 匹配] [值]，产生信号 [名称]，级别 [错误]。列出样例中的命中，点击即跳到对应行。 |
| 知识 | 已链接条目列表，提供"链接已有条目"（在已发布条目中选择）和"上传 Markdown"（多文件拖放；创建并链接到技能的知识条目）。没有知识编辑权限时，上传按钮显示禁用原因。 |
| 源码 | 快照表（版本标签 · 文件数 · 带进度的索引状态 · 跳过文件 · 上传时间）、"上传源码"对话框（压缩包 + 标签）、"设为默认"。"试一试"：粘贴一行日志，查看打印它的源码语句。 |
| 测试 | 分区工具栏提供「运行测试」，并紧凑显示通过/失败数、「未运行」或「运行中」；列表显示各项状态。「新增测试」使用选中的样例行与当前解码字段；通过字段路径表编辑期望，保留代码视图。失败项展示「字段路径 · 期望 · 实际」以及缺失/多出的信号；样例面板遵循分区注册表的可见性规则。分析用例（S5）使用日志包及期望根因、证据、建议，比较最新得分与上一版本，也可从报告创建。 |
| 集成 | 带复制按钮的 skillKey 与接口地址；预填 skillKey、可直接运行的 `curl`；集成凭据（创建时只显示一次密钥，之后可轮换/吊销，显示最近使用）；结果 Webhook 与测试投递（从业务域行迁来）；投递记录；集成指南链接。 |
| 版本 | 版本列表；按分区分组的并排对比（诊断流程文本、新增/修改/删除的规则）；"回滚"把旧版本发布为新版本。 |

Mock 模式保留一个只读的种子技能，演示和组件测试仍可渲染；编写功能仅在 API 模式提供。

## 阶段 S1——技能版本、诊断流程与数据驱动的信号

1. 迁移：`log_skill_revisions`；为每个日志业务域按当前配置回填版本 1（已发布）；新运行设置 `log_analysis_runs.skill_revision_id`。
2. 服务与 API：`/api/v1/log-skills`（列表、获取、创建、更新草稿、发布、版本列表、两版本对比）。`/api/v1/log-domains` 与 `logDomainId` 保留为别名。
3. Worker 加载所钉版本；提示词新增诊断流程段；新提示词版本。
4. 信号规则引擎（消息正则、标记/字段条件、时间窗计数）。规则 id 改为开放字符串。充电规则成为种子技能（演示种子和评测夹具）；规则回退评估所钉版本的信号。
5. 所有管理员模式（包括现有格式画像）改用线性时间正则引擎。按自托管镜像兼容性在原生 RE2 绑定与 WASM 构建之间选择，并在 PR 中记录。
6. 分析轨迹：循环把每一步（工具、参数摘要、结果大小、返回行、结果、token）记录到 `log_analysis_traces`；仅技能管理员可读。"试运行"在技能样例上运行草稿版本，不产生用户可见的记录。
7. 前端：[分阶段 UI](#分阶段-ui) 的 S1 行。

**S1 验收**：已发布版本的诊断流程确实进入提示词（行为评测断言）；编辑草稿永不改变钉在已发布版本上的运行；重新分析旧记录时用所钉版本复现；充电种子技能在现有评测案例上给出与当前硬编码预筛相同的规则证据；跨组织读写技能和版本被拒绝（PostgreSQL 集成测试）。

## 阶段 S2——日志包、文件管理与通用信号

1. 接收：`.tar`、`.tar.gz`/`.tgz`、多条目 `.zip`、`.gz`；嵌套压缩包最多一层；拒绝路径穿越、绝对路径、链接和设备条目；上限（初始值，可用环境变量调整）：压缩上传 100 MB、解压后 512 MB、2,000 个文件、单文件 200 MB，沿用 200 倍压缩比规则。
2. 编码：UTF-8、带 BOM 的 UTF-16，以及带逐文件标记的有损解码；二进制文件列出但不分析。
3. `log_files` 带逐文件文本对象和行偏移索引；Worker 流式处理文件并按偏移读取行范围，不再把全部文本留在内存中。
4. 通用信号：崩溃特征（kernel panic、Oops、`BUG:`、watchdog、ANR、`FATAL EXCEPTION`、segfault、assert）、时间戳间隔与重启、带计数及首末出现位置的行模板聚类、错误突发、每文件首个错误。
5. 感知文件的工具，以及 `get_line_templates`、`get_timeline`；证据新增 `file_path`。
6. 前端：[分阶段 UI](#分阶段-ui) 的 S2 行；适用通配决定文件角色。

**S2 验收**：多文件日志包产出引用多个文件中行的证据；恶意压缩包（穿越、链接、炸弹、嵌套）被拒绝并说明原因；达到上限的日志包在 PR 中测得的 Worker 内存上限内完成分析；单文件上传行为与之前一致。

## 阶段 S3——结构化抽取与解码

#1237 提供抽取核心和代码视图；从样例行创建抽取规则及表单编辑由 #1240 提供。

1. `parsing/v1` schema（zod），校验错误精确到路径；解码引擎为纯函数且有界。
2. 解析阶段运行抽取器和解码器，对解码值应用信号规则，把解码事件存为每次运行的产物（对象存储，锚定到行），并在数据库中保存各抽取器计数和信号命中；报告只持久化被引用的事件。
3. 工具 `query_events`（抽取器、字段过滤、行/时间范围、条数上限）和 `describe_event_schema`；工具结果中出现的事件视为已看到其所在行，用于接地。
4. 解析测试（#1242）：可选 `skill/v1.parseTests` 将样例行、可选文件名及期望字段路径/信号与规则一起保存，随版本发布。期望字段按单个解码事件的子集匹配，包含嵌套寄存器字段；转换字段默认比较 `value`，显式指定 `raw` 时比较原始值。信号 id 或名称按集合比较，可选精确匹配。统一服务端运行器复用真实解析引擎与逐行信号规则，执行输入/输出上限和截止时间，返回每项结果与路径/期望/实际差异。每次保存草稿后、「测试」分区工具栏「运行测试」及发布前运行。结果只保留在打开的工作区并重新计算，不持久化，避免新增迁移与存储过期结果。发布对话框顶部展示通过数/总数和失败项链接，再按测试显示变更，不阻止发布。详见[解析测试契约](../../design-docs/log-parsing-v1.md#解析测试)。
5. 前端：[分阶段 UI](#分阶段-ui) 的 S3 行。表单与代码视图共用同一校验器，草稿在两者间往返不丢信息。
6. 预览接口针对未保存的草稿解码粘贴或选中的样例行，供实时面板使用。

保存、发布与测试校验共享信号规则预检查：最多 64 条规则，每条 16 个条件，条件合计 256 个；每条文本模式最多 4096 个 UTF-16 码元，模式合计 65,536 个码元。按需解析测试 POST 请求体最多 8 MiB，包含斜杠别名，校验与执行共享 1000 ms 预算。无效输入或校验超时返回 HTTP 400；执行超时返回失败测试。传输超限在 JSON 解析前返回 HTTP 413。

**S3 验收**：示意中的寄存器映射与 PD 帧示例完全按规定解码；每个构件都有单元测试，包括超限情形；Agent 结论引用解码字段且报告正确渲染；解析测试不阻止任何操作，但在发布对话框中展示。

## 阶段 S4——源码快照

实现切片 #1243 增加压缩包上传与带审计的归档、流式异步文件/分块索引、全文/trigram 索引、可配置上限（解包 1 GiB、单文件 2 MiB、20,000 个文件、压缩上传 100 MiB）、有界跳过明细、工作区源码表格/对话框和仅更新草稿的默认设置。可选 `defaultSourceSnapshotId` 随版本发布；运行解析其固定版本并记录观察到的快照 id/状态。快照未就绪或已归档时分析继续，报告明确显示中文不可用提示。源码语句索引/证据（#1244）、源码搜索/范围工具及上传 `sourceVersion` 匹配（#1245）仍为后续 S4 工作；#1243 单独不能满足下方完整 S4 验收。本切片不将源码片段发送给模型服务。运维细节和独立 1 GiB RSS 探针见[运行手册](../../runbooks/log-analysis-llm.md#源码快照1243)。

1. 为技能上传带版本标签的源码压缩包；对象存储；异步索引（参照知识库索引 Worker）；按扩展名的文本文件白名单，单文件与总量上限（初始值：解压后 1 GB、单文件 2 MB），跳过并列出第三方/二进制路径。
2. 索引：文件；分块全文 + 三元组检索；用输出语句模式抽取的日志语句索引（默认覆盖 C/C++ `printk`/`pr_*`/`dev_*`、Android `ALOG*`/`Log.*`、`LOG(...)`、Python `logging`、Go `log`/`slog`；技能可追加模式）。格式串归一化为可匹配骨架。
3. 快照选择：上传时的 `sourceVersion` 标签 → 匹配快照，否则用版本的默认快照；运行记录所用快照。
4. 工具 `find_log_statement`、`search_source`（路径通配、查询）、`read_source_range`（≤ 80 行）；源码位置证据类型，需接地。
5. 前端：[分阶段 UI](#分阶段-ui) 的 S4 行。
6. `docs/SECURITY.md`：源码与日志片段会发送给已配置的模型服务。

**S4 验收**：对于由已索引语句输出的日志行，`find_log_statement` 返回其文件与行号；结论可以引用源码位置并正确渲染；快照仍在索引时，运行在没有源码工具的情况下完成并予以说明；源码行按组织隔离（PostgreSQL 集成测试）。

## 阶段 S5——技能测试、路由、打包与集成

1. 产品内的分析测试用例（日志包 + 期望根因、关键证据、建议、可选拒答）；按需用真实模型对草稿运行；用现有质量评分打分；与上一已发布版本比较；结果显示在发布对话框中。以 `eval-cases/logs` 格式导入/导出。
2. 路由：未指定技能时，按适用通配和特征模式为已发布技能打分；选出超过阈值的最佳技能并记录原因；否则走通用路径。
3. 技能包导入/导出（zip）：`SKILL.md`（frontmatter + 诊断流程）、`parsing.yaml`、`signals.yaml`、`knowledge/*.md`（导入时创建知识库草稿条目并链接）、`cases/`。源码快照单独上传。
4. 重写[集成指南](../../api/log-analysis-integration.md)：构建技能、测试、打包、用 `skillKey` 推送日志包、消费 Webhook。更新用户指南。
5. 反馈洞察按技能版本分组。
6. 集成凭据：组织作用域的机器凭据，只能上传日志并读取自己创建的记录（可选限定一个技能）；密钥只显示一次并以哈希存储；可轮换、吊销，显示最近使用；签发与吊销均审计。这是新的主体类型，实施前先以 ADR 记录（扩展 ADR-0038）。
7. 供上传对话框使用的推荐接口：文件名加各文件开头若干行 → 带理由的技能排序。
8. 前端：[分阶段 UI](#分阶段-ui) 的 S5 行。

**S5 验收**：从一个组织导出的技能包可导入另一个组织，并对同一用例给出相同的规则证据；路由为种子技能的样例日志包选中该技能，对无关日志包走通用路径；产品负责人无需仓库访问即可按集成指南端到端完成接入；[UX 验收](#ux-验收) 中的两条 S5 走查通过；已吊销的凭据被拒绝，且凭据不能读取其他凭据创建的记录。

## 安全与隐私

- 每张新表在仓储层和复合外键上都做组织隔离；权限 `logs:admin-domains` 管理技能与快照（显示名改为"管理分析技能"）；`logs:view` 可列出快照元数据，含进度和跳过路径原因，#1243 不提供源码文件/内容浏览路由。
- 诊断流程文本、知识、解码值和源码都是不可信的模型输入；技能永远无法覆盖平台协议。
- 管理员模式在带上限的线性时间引擎上执行；压缩包在持久化任何内容之前完成校验。
- 集成凭据只有上传和读取自有记录的范围，以哈希存储，永不授予管理权限。
- 按产品负责人决定，源码与日志片段流向已配置的模型服务；报告保留模型、提示词版本、技能版本和快照来源信息，绝不保存原始提示词。

## Git 与 PR 流程

一个阶段 → 一条从最新 `main` 拉出的分支 → 一个 PR，绿灯后合并。只有协调 Agent 在用户授权范围内开启或合并 PR。

## 风险

- **在没有参考模块的情况下设计 schema。** 缓解：`parsing/v1` 带版本，`v2` 可以并存；S3 之后产品负责人的真实场景测试是对 schema 的首次评审，S5 记录发现的缺口。
- **大型日志包与快照。** 缓解：流式处理与偏移索引（S2）、异步且有上限的索引（S4），上限可用环境变量调整并在 PR 中测量。
- **更多步数和源码上下文导致模型成本上升。** 缓解：每技能预算受平台上限约束；成本和步数纳入指标。
- **诊断流程或源码内容操纵 Agent。** 缓解：协议优先级、接地、无写路径、包含对抗性诊断流程与日志文本的行为评测场景。
- **五个阶段的范围。** 缓解：每个阶段交付可用增量；仅 S1 就能提供按模块的诊断流程和可复现的运行。
