### Draft 实现与剩余边界

- `0180_mod_d02_offline_capture.sql` 创建无密码的固定维护角色与 `SECURITY DEFINER` 采集函数；`0181_mod_d02_capture_revalidation.sql` 增加 readiness 复核和按 request 区分的审计身份。Source LOGIN 仅有下文列级读取权，但获准列在 SQL 层仍跨组织可见。Capture LOGIN 只能执行固定函数，不能直接读写比较表。两个迁移均仅前向应用；本提交不携带目标凭证。
- `offlineLocalSession.ts` 无 `last_used_at` 写入地解析现有本地登录 token；`offlineModD02SourceReader.ts` 用持久化 USER invocation 和完成 manifest 复核取得真实 provider batch。URL-owning capture 入口核对两个 PostgreSQL LOGIN 身份及维护 plan/artifact/Release pins，并在成功或失败后关闭两个数据库 root。固定函数在一个事务中锁定并复核 session、active admin、P10 run、模块库存、关联、选中 MappingVersion 和 Subject 事实；还会复核当前 Catalog 能力 revision、精确 Release receipt，以及 online-publication receipt 对应的 artifact。来源读取与采集处于两个连接，写事务重查可能在两连接间变化的事实；不能把它描述成跨连接的同一快照。
- 可销毁 PostgreSQL 集成检查由真实 P0–P10、本地登录、两个 MOD 模块、Registration/Placement 和 Catalog Release 产生两条 `unexplained-difference`。第二条 result 故障及独立审计故障都回滚 case/result/audit。reader 成功后，capture 拒绝已撤销 session、被移除 admin、来源漂移及同一 Release 上不受支持的 policy revision；capture 持有 session 锁期间，并发撤销返回 `55P03`。同 requestId 精确重试不新增 case/result/audit；不同 requestId 追加第二条审计；修改任一固定审计字段都会被拒绝。带 PUBLIC TEMP 与恶意临时同名表的 capture LOGIN 成功写入 schema-qualified 持久表。URL 所有权入口成功与失败后，`pg_stat_activity` 均无遗留连接。这些只证明本地能力，不代表目标角色或目标 run 已验收。
- 固定函数复核受保护的数据库事实和结果形状，JSON batch 仍由受信维护进程的 provider 产生；函数不独立重演整个 TypeScript provider，也不证明全部 11 family 与九个 gate 已覆盖。`fullReport.available=false`；独立 P11 和 post-retirement 复核继续必需。默认关闭的维护钩子不启动 API/worker/web，也不推进 P12。
- 新增维护配置仅为 `WISEEFF_MOD_D02_CAPTURE_ENABLED=true`、`WISEEFF_MOD_D02_SOURCE_READER_DATABASE_URL` 和 `WISEEFF_MOD_D02_CAPTURE_DATABASE_URL`；`AUTH_PROVIDER` 必须为 `local`。两个 URL 必须通过各自固定 LOGIN 连接同一个数据库。本地 session token 由关闭回显的 `/dev/tty` 读取，不放入参数、环境变量或日志。未设置开关时，原维护流程不打开这两个连接。部署包仍须绑定自身的 artifact 与 Release pins；本 Draft 不安装凭证，也不在目标环境开启该开关。
- 钩子沿用 cutover controller 已核对的 P2 观测、完成 checkpoint 和操作员声明；在采集时刻没有再独立检查一次实际服务进程。因此采集回执本身不能证明流量隔离持续有效；目标操作仍须保持已接受的 P2 fence，独立 P11 也仍需单独完成。

## 待决事项

下文精确 29 relation/137 列及 `auth_sessions` 六列、获准列的数据库跨组织全行可见、function-only capture LOGIN/NOLOGIN owner、现有 `PUBLIC TEMP` 边界，已获本 Draft 实现授权。**目标启用仍须单独决定：**只在目标环境配置两份维护凭证，并通过本地角色及 P2/P10 证明后启用默认关闭的采集。这不代表部署、替代 P11 或启动候选 API。采集只限于 API、worker、web 停止时，针对**单个组织、一条已完成 S7 run** 的 **P11 之前、pre-activation** 证据。

代码入口是 `ops/self-hosted/scripts/upgrade.sh` 中已填充的 maintenance 路径：`controller.dispatch({ action: "execute" })` 返回已完成 P10 后，且 Release Verification 的 `prepareVerification` / `runVerification` 调用之前。仅 `WISEEFF_MOD_D02_CAPTURE_ENABLED=true` 才执行采集。独立的 `scripts/wayfinder/execute-parameter-catalog-cutover.ts` 不调用该采集。两者都不实现独立 P11。

Deployment Operator 启动 maintenance 进程。P10 后，Organization Admin 通过受保护的终端提示向离线进程提供现有 WiseEff local-auth session token。此 Draft seam 只支持 `AUTH_PROVIDER=local`；OIDC/HMAC 部署必须在另行批准离线认证 seam 前 fail closed。已实现的只读 resolver 使用 `hashLocalSessionToken` 对 token 求哈希，检查 `auth_sessions` 的过期和撤销状态，并从 PostgreSQL 重新读取 active user、Organization、role bindings 和有效权限。只有服务端构造的 `AuthContext` 才可传给 `createUserInvocation(auth)`。`createUserInvocation` 只给 `AuthContext` 加品牌，不执行认证。CLI 或 JSON 不得选择 user/session ID 或组织；`operatorAuditRef` 只是审计标签，不是身份认证。

该流程复用现有账户认证来源，不引入停机前授权 token。`/api/v1/auth/login` 在密码验证后创建本地 session，但它是可重复使用的 bearer credential，且不绑定 run。有效性以数据库持久化的 `expires_at` 和 `revoked_at` 为准；到期或撤销后拒绝，在此之前可重放。Capture action 会单独绑定精确 run，并对相同证据幂等；同一身份下证据变化则 fail closed。这只能证明 WiseEff 账户已认证，不能证明操作者是现场真人：ADR-0038 明确规定 `AuthContext` 不作此保证。若今后要求现场真人保障，IdP/MFA 或等效的人类专用身份契约仍不在本 seam 内。Draft 离线 resolver 使用只读查询，因为现有 HTTP resolver 会更新 `last_used_at`；目标环境启用仍待批准。

采集后，**独立的只读 P11 verifier** 必须基于相同的源边界重新计算完整 V01-V17 和跨全部 11 个 consumer family 的 D01-D09 语义比较。它必须使用与 writer 不同的代码和数据库凭证。P11 报告才是 P12 前的证据；组织投影采集响应和其数据库行都不是。Verifier 必须独立重算 D02，不能把 v2 writer 自己生成的 observation 当作自身正确性的证明。

## 仓库中观察到的边界

- `createReleaseVerificationService` 是 routes-less 模块，默认 adapter map 为空。`runVerification(planDigest)` 不接受 trusted invocation。生产 PostgreSQL adapters 覆盖 V/M/P gates。默认关闭的维护路径现在于 P10 后调用专用 MOD D02 source reader 和固定采集函数；它不调用旧 v2 writer、`generateLiveComparisonReport` 或独立 P11。生产 OPS comparison 仍只通过 `readReport` 读取 S10-PER 报告。
- `writeModParameterCatalogComparisonCasesV2` 只接受 `phase: "pre-activation"`、trusted user invocation 和 completed-manifest run。它从 invocation 推导组织、重新验证已持久化授权，并且只写 MOD D02 组织投影。返回值明确为 `fullReport.available: false`，原因是 `eleven-family-and-nine-gate-coverage-not-collected`。
- `readCompletedModComparisonManifestForComparison` 验证 trusted user、持久化组织/用户和已完成 P7 manifest。迁移 `0179_parameter_catalog_comparison_manifest_binding.sql` 将 v2 行约束到已完成的 `s7-orc-p0-p10-v2` run 和精确 P7 selection。phase 字段只表示比较场景；它不证明 P13，也不建立独立验证。
- MOD writer 的事务对 `public.users` 和 `public.user_role_bindings` 执行 `FOR SHARE`，并对 `public.parameter_modules`、`parameter_catalog.organization_subject_registrations` 和 `parameter_catalog.subject_placements` 执行 `LOCK TABLE ... IN SHARE MODE`。它调用 `parameter_catalog.assert_catalog_subject_active`，并对两张 v2 comparison 表执行写入/读取以验证幂等性。
- 迁移 0138 从 `PUBLIC`、`catalog_synchronizer_role` 和 `parameter_governance_writer_role` 撤销 comparison case/result 表权限。迁移 0139 的 `catalog_verification_writer_role` 只允许对 `verification_*` 追加写入；`catalog_verifier_role` 只允许读取 `verification_*`。这两个角色均不提供 v2 comparison 写入权限，也不提供 P11 所需的源数据读取权限。迁移 0179 增加约束和触发器，不增加运行时 grants。
- `comparisonCaseResultsV2.integration.test.ts` 中的一次性 PostgreSQL 测试角色获得了宽泛 fixture SELECT、Catalog active-Subject guard 的 EXECUTE 以及两张 comparison 表的 INSERT。随后测试观察到，在暂时授予 `users`/`user_role_bindings` 的 `UPDATE(id)` 以及 modules/registrations/placements 的表级 UPDATE 前，所需行锁和表锁均以 SQLSTATE `42501` 失败。这些 grants 是测试探针，不是部署角色契约。将它们复制给 API LOGIN 会赋予数据修改能力。
- `docs/SECURITY.md` 保留普通 API LOGIN 不直接写 Catalog，以及 Governance composition-root 的权限边界。直接向 API LOGIN 授予 0179 INSERT 或用于加锁的 UPDATE，会与已接受契约冲突。现有 Governance writer 无法组合本操作：它没有 Catalog、Cutover、Verification 或 comparison 表权限。

## 建议的执行顺序

1. 停机前，由现有 `/api/v1/auth/login` 流程创建有效的 local-auth Organization Admin session。Session 只用于认证，不批准 run，也不豁免任何 gate。OIDC/HMAC 部署不支持此拟议 seam，保持禁用。Deployment Operator 准备精确 plan、目标 artifact 与 Catalog Release pins。
2. 已接受的 P2 边界停止 API、worker、web 和 proxy 流量，暂停并排空 queue，并证明 leased work 为零、业务流量为零、无 application writer，且 legacy/candidate 两道 writer fence 均生效。此后 S7 只能通过已接受的 one-shot maintenance 进程继续。Capture 期间没有 HTTP API。
3. `executeCutover` 报告 P10 已完成后，maintenance 进程保留 completed P0-P10 run receipt/checkpoints，保留 controller 的 P2 隔离证据并读取持久化 run。它要求 P0-P10 的所有 checkpoint，包括 P2、P5/P7/P10；一个完整的 v2 P7 manifest；稳定的 source snapshot fingerprint、plan digest、target artifact SHA、Catalog Release ID/digest；且没有 live S7 run。进程从不可变的部署包 attestation 读取可信 artifact SHA，不接受请求或操作员提供的 identity 字段。Completed-run receipt/checkpoints 只是证据，不是 capture 或 P11。
4. Admin 通过无回显终端提示输入 local session token。Draft 中的 `wiseeff_mod_d02_source_reader` connection 对 token 求哈希，验证精确的 `auth_sessions` 行（包含持久化 expiry 和 revocation 字段），并重新读取当前 active user、Organization、role bindings 和有效权限。结果必须匹配 session 持久化的 user/Organization，并具有该组织 `admin` 权限。Source-reader connection 也运行只读 MOD D02 provider；其 allowlist 必须覆盖 provider 精确使用的 run/manifest、module/association 和 Catalog source reads。Capture transaction 接收已验证的 session ID，并在提交前重新检查和锁住 session、active user、Organization 和 admin role。过期/撤销 session、inactive user、角色变化、跨组织范围或任意 pin 缺失都必须拒绝。该 seam 已在 Draft 实现，但目标环境仍未启用。
5. 现有 `provideModParameterCatalogComparisonCaseBatchV2` provider 在 source-reader `Database`/root Pool 上生成 scoped projection。当前 writer 要求 `Database` 和 `pool` 指向同一个 root Pool，并把 source reads 与写事务耦合，因此不能在 source-reader 与 capture LOGIN 之间原样调用。建议的 TypeScript 拆分把生成的 batch 传给独立 `wiseeff_mod_d02_capture` connection 上的专用函数；该函数在同一事务内复核所有 pins、source inventory/associations 并加锁，然后原子写入 case/result 和 audit。完全相同重试不产生新写入；同一身份下证据变化则 fail closed。回执只包含 scoped projection digest、计数/校验和及新增/回放计数，不含 Archive payload、原始值，也不宣称 P11 通过。启动 P11 前必须提交事务并关闭 capture connection。
6. 随后单独运行只读 P11 verifier，针对相同 run、plan、artifact、Catalog Release、mapping epoch、P7 manifest 和 source boundary 重新计算所有必需的 V01-V17 和 D01-D09。它独立计算 D02；writer 生成的行只是检查输入，不是自身正确性的证明。Verifier 与 capture 使用不同代码进程和数据库身份。
7. 只有达到已接受门槛时 P11 才通过：`unexplained-difference` 为零、`unqueryable/protected-reference-missing` 为零、枚举每个 protected reference、覆盖全部 11 个 consumer family，且确定性期望计数/校验和匹配。只有已接受的 P11/报告审批流程可以进入 P12。
8. P12 将两个通过的 P11 report digest 绑定到 read-pointer switch。P13 在服务仍停止时退役 legacy writers。P13 后必须以新 attempt 重新运行完整的 `post-retirement-runtime` V01-V17 和 D01-D09，包括 V13/P02 writer reachability 与 privilege negatives。只有该报告通过且获批后，candidate API 才可 verify-only 启动；之后在流量隔离时再做 worker/web 与内部 API/browser acceptance。

## 对象与权限矩阵

此表区分建议的 scoped capture 与独立 verifier。“精确 SELECT”表示只授权所需 relation/column，不表示数据库实施了行级租户隔离。Draft source-reader 没有 RLS policy，可见获准列的所有行；组织/run 过滤由可信 maintenance process 执行。这不是 schema 级授权，但数据库本身不强制组织行范围。

| 对象 | 建议的 MOD D02 capture | 独立 P11 verifier | 明确禁止 |
| --- | --- | --- | --- |
| 已认证 principal 与 local session（`public.auth_sessions`、`public.users`、`public.user_role_bindings`、`public.organizations`、`public.roles`） | Draft 离线 resolver 校验 token hash、session expiry/revocation，并重载当前持久化 `AuthContext`；capture function 在提交前重新检查并锁定 session、active user、Organization 和 admin binding。 | 只读获取 verifier 所需的身份/授权证据。 | CLI/JSON 指定 actor/组织/角色；不得修改用户、角色或 session 数据（仅 definer owner 可用锁定所需的 `UPDATE(id)`）；Agent/System invocation；将 `operatorAuditRef` 当作身份依据。 |
| S7 run 与 P7 manifest（`parameter_catalog.parameter_catalog_cutover_runs`、`parameter_catalog.parameter_catalog_cutover_events`、`parameter_catalog.parameter_catalog_cutover_checkpoints`、`parameter_catalog.catalog_releases`、`parameter_catalog.legacy_identities`、`parameter_catalog.legacy_mapping_versions` 和 manifest 引用的 owner 行） | 应用过滤选择精确的已完成 v2 run 和不可变 P7 selection，并生成经认证组织的投影。LOGIN 可读取获准列的所有行；不得推进 head 或修改 checkpoint。 | 在同一冻结的 P0-P10 数据和 pins 上只读重算。 | 两条路径均不得写入 mapping、Archive、checkpoint、phase 或 run。 |
| MOD 源数据与 association（`public.parameter_modules`、`public.parameter_module_mappings`、`parameter_catalog.organization_subject_registrations`、`parameter_catalog.subject_placements`、`parameter_catalog.current_project_parameter_bindings`） | 应用过滤选择经认证组织的投影；source-reader 可读取获准列的所有行。Capture function 在自身事务锁内复核已接受 inventory 和 association。 | 在已接受源 snapshot 上只读执行双读语义比较。 | INSERT/UPDATE/DELETE、reconciliation、reclassification 或 fallback。 |

| Result 与审计 | 验证确定性 case ID、规范 case/库存 checksum、固定 MOD D02 分类，在一个事务中写入不可变 case/result 对和稳定 `(organization, run, requestId)` key 的脱敏审计。同 key 精确重试会比较每个固定审计字段；不同 requestId 新增审计并复用 case/result。返回前强制检查延迟的 0179 约束。 | 组织投影不是全量报告；`fullReport.available=false`。其他 family 与历史不可查询项继续阻断 P11。 |
| P2 隔离 | 维护 controller 提供既有 P2 观测和完成 run 上下文。 | capture 时刻不独立重测实时流量/fence；操作者与独立 P11 仍须满足已接受隔离条件。 |

### 已实现的入口、身份和权限

默认关闭入口是 `ops/self-hosted/scripts/upgrade.sh`：完成 P10 后、准备 Release Verification 前，在 API、worker、web 停止的既有一次性维护进程内执行。它从关闭回显的终端提示读取事先签发的本地 session token，不接受调用者指定 principal 或 organization ID。`createOfflineModD02SourceReader({ database, pool, enabled, authProvider })` 解析持久账号并调用真实 MOD provider。`captureOfflineModD02PreP11FromUrls({ sourceDatabaseUrl, captureDatabaseUrl, ... })` 拥有两个 root，核对 database/cluster 身份、固定 LOGIN、角色属性和参数日志限制，在单事务内调用 `parameter_catalog.capture_mod_d02_pre_activation_v2(runId, sessionId, tokenHash, principalId, organizationId, batch, requestId)`，并在成功或失败后关闭两个 root。低层 `captureOfflineModD02PreP11` 接收已打开的 root，供有界调用者和测试使用。

迁移 `0180_mod_d02_offline_capture.sql` 定义无密码的 `wiseeff_mod_d02_source_reader` LOGIN（上文列级 provider 授权）、`wiseeff_mod_d02_capture` LOGIN（schema USAGE 与固定函数 EXECUTE），以及 `catalog_mod_d02_capture_owner` NOLOGIN（精确读取、锁所需 UPDATE、case/result INSERT 与 audit INSERT）。`0181_mod_d02_capture_revalidation.sql` 增加 Catalog readiness 复核所需的 SELECT 和锁专用表级 UPDATE。PostgreSQL 要求 owner 具备 UPDATE 才能执行 `LOCK TABLE ... IN SHARE MODE`；`catalog_activation_receipts_immutable` 会拒绝真实 receipt UPDATE/DELETE，两个 LOGIN 都不能使用 owner 权限。迁移会拒绝固定角色既有的 relation、列和函数直接 ACL 或成员资格，检查包括 PUBLIC 在内的有效 SECURITY DEFINER EXECUTE，并设置两个 LOGIN 的 `log_parameter_max_length=0`。`PUBLIC`、普通 API、verifier 和 Governance 角色均未获 capture 函数权限。capture LOGIN 不能直接读取 session、source、case 或 audit 表；source LOGIN 不能读 `password_hash`、audit、历史 dismissed-compatible 行，不能切换角色或写业务表。因为没有 RLS，source LOGIN 对已授权列仍有跨组织的 SQL 行可见性；可信进程按持久化组织过滤。

只有 `WISEEFF_MOD_D02_CAPTURE_ENABLED=true` 且存在 `WISEEFF_MOD_D02_SOURCE_READER_DATABASE_URL`、`WISEEFF_MOD_D02_CAPTURE_DATABASE_URL` 才进入此路径；`AUTH_PROVIDER` 必须是 `local`。标志关闭时不打开这两个连接。URL 是部署配置，Draft 不提供目标凭据。仅维护包可提供预期 plan/artifact/Release pin。终端 token 及 hash 不得进入 argv、环境、回执或日志。目标环境 provisioning 与独立 P11 verifier 仍是分开的工作。

### 专用 PostgreSQL 验证与限制

聚焦集成测试通过真实 local login 建立 session，创建两个组织、模块、Registration/Placement 和 Catalog Release，经真实 S7 P0–P10 后以固定非超级用户 source LOGIN 调用 provider。两条真实 MOD selection 均为 appended，分类保持 `unexplained-difference`。测试证明 reader 可以在 SQL 层直接看见另一组织获准列，而 provider 只返回认证组织的两个 case；还验证 reader/capture 直接权限拒绝、精确身份、bearer hash 错误、投影/checksum/case ID 篡改、plan/Release 不符，以及 reader 成功后 session/admin/source/policy 漂移；capture 持有锁时并发撤销以 `55P03` 被阻塞。第二条 result 和 audit 故障均回滚并恢复。带恶意临时 shadow 表的 capture `search_path` 成功写入持久表；同 requestId 精确重试不新增行，不同 requestId 新增第二条审计并回放两条 case/result；修改每个固定审计 scalar 或 metadata 均以 `23514` 拒绝。Capture LOGIN 不能直接锁定 receipt 表（`42501`）；NOLOGIN owner 拥有 PostgreSQL SHARE 表锁所需的 UPDATE privilege，实际 receipt UPDATE 则由 immutable trigger 以 `55000` 拒绝。URL 所有权入口在成功和 invalid-token 失败路径后，`pg_stat_activity` 均无匹配连接；低层精确重试返回两条 replay。正向 case/result 回执为两条 case、恶意 search_path 首次写入两条、零条 replayed mapping selection、无全量报告。临时角色密码和故障触发器仅存在于本轮可销毁集群；这些结果不是目标环境或部署 LOGIN 验收。

既有 `comparisonCaseResultsV2.integration.test.ts` 仍负责通用 writer 证明。0179 的延迟约束在 COMMIT/强制检查时核对精确选中的 MappingVersion。新函数额外绑定持久化 batch 与确定性 case/库存 checksum；它不能独立证明 TypeScript provider 的每个值都是完整真实数据库观测。独立 P11 仍须重算 D02 及全部 family 的 V01–V17/D01–D09。历史 dismissed-compatible raw-read 的原生 ID 仍未获许可；继承原生 174 项与冻结 173 断言分开记录。

### 启用与回退

目标启用需要另行审查最终迁移 ACL、固定角色属性、凭据供应、数据库身份回执、P2 隔离，以及已接受的 P11/P12/P13 门禁。不能用专用 PostgreSQL 成功推断生产授权。关闭功能标志会停止新 capture；已启用目标可轮换/撤销专用凭据或固定函数 EXECUTE。保留已提交 case/result/audit 和 Archive 历史。本 Draft 不授权 down migration、改写历史行、启动候选 API 或推进 P12。
