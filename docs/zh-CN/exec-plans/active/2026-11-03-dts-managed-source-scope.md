# DTS 源码编辑与参数纳管范围

> English: [DTS editing and managed parameter scope](../../../exec-plans/active/2026-11-03-dts-managed-source-scope.md)

状态：实现与验证进行中。实际执行证据和最终合并状态记录在 [PR #1492](https://github.com/tzrea1-Q/WiseEff/pull/1492)；本方案不宣称 PostgreSQL、浏览器或生产验证已经通过。

## 问题与目标行为

当前源码编辑器会因历史参数的组织登记已停用且对应源码发生变化，拒绝保存整份 DTS。停用属于参数管理决策，而项目源码本来就允许存在不纳管的内容。仅为修改这些字节而要求恢复登记，混淆了两项职责。

| 源码内容 | 整份源码编辑 | 参数同步 | 当前参数读取 |
| --- | --- | --- | --- |
| 当前主体、定义、必需的所有者及组织登记有效 | 正常通过源码校验与授权后允许 | 追加值及精确来源 pin；正常删除仍产生删除回执 | 展示已同步的当前值 |
| 组织登记、当前主体、必需的所有者或当前定义已停用 | 允许修改、删除和来源迁移 | 冻结排除依据，保留原值、pin 和历史 | 不展示 |
| 未知或未登记属性 | 作为合法源码内容保留 | 不隐式创建定义、登记或 Binding | 不展示 |
| 已恢复纳管资格，但 pin 属于历史版本 | 允许编辑源码 | 下一次授权保存从最新生效源码重新同步同一 Binding | 同步前不展示旧值 |
| 已恢复资格，但属性仍不存在 | 允许编辑源码 | 继续保留历史 Binding 和排除记录，不把旧值写回源码 | 不展示 |

生命周期为 `deprecated` 的 Definition 继续参与同步和当前读取；只有 `retired` 才退出有效定义范围。主体若要求归属某个所有者，则所有者主体及其组织登记也必须有效；即使子主体自身登记仍为 active，所有者停用仍产生 `owner-inactive` 排除原因。

本方案落实 [ADR-0042](../../design-docs/adr-0042-organizations-register-canonical-subjects-once.md) 的停用语义，覆盖整份 DTS 修订、同一配置中内容未变的 JSON 成员，以及相邻源码流程对已有暂停证据的保留。不包含生产部署、绕过审核的原始文件保存或任意 JSON 修改。

## 实施方案

1. 根据当前 Catalog 主体、定义、必需的所有者主体及相关组织登记判定纳管资格。先排除失去资格的 Binding，再校验需要同步的 pin 是否属于当前源码修订；暂停纳管期间保留历史 pin 是正常状态。
2. 在正常纳管集合之外冻结 `excludedBindings`，记录精确的 Binding、值、pin、定义、登记、来源身份及排除原因。应用时持有既有治理和源码锁重新检查；生命周期、Catalog、源码或值的并发变化都使预览失效。批准提交时，为每个 Binding 保留独立、不可变的暂停回执及审计事件。每条审计仅包含本 Binding 的精确身份、生效配置和证明摘要，不包含其它定义，也不引用会导致清理相互牵连的共享请求或原审计。
3. 被排除项不进入参数同步集合。保存源码推进文件及配置版本，但不为这些项追加值、pin 或 Binding 历史。原有回执数量约束和完整文件授权保持严格。
4. 增加独立的当前纳管读取条件，保留既有 owner 投影用于写入和历史读取。当前列表、分页、比较、导入/复制候选和默认参数导出要求治理有效且来源精确对齐。整份源码导出仍包含真实文件内容，不为未纳管 JSON 生成误导性的当前参数映射。
5. 恢复资格不修改源码。历史 Binding 重新纳管时，必须找到独立保留的已批准排除回执，核对完整身份、审计依据以及同一配置内的修订顺序。DTS 属性存在时，显式以新解析源码生成 set 操作，即使值与历史相同；JSON 成员须验证未变字节与定位器后再同步。属性仍缺失则保留历史。整个节点删除后重新出现时恢复原逻辑节点连续性，避免重复创建 Binding。
6. 单参数/批量修改、成员添加/移除、JSON 纳管、快照创建及快照恢复，仅跳过有已批准暂停回执且精确身份一致的历史 Binding。它们继续操作有效参数和真实源码，不为暂停值重新生成 pin；仅有过期 pin 不能获得例外。即使治理资格已恢复，这些相邻操作也不重新纳管暂停的 Binding，重新同步由整份源码保存负责。暂停属性迁移到其它文件后，移除原来源成员仍须在内部保留 owner 的可发现性，使后续整份源码保存复用原身份；成员墓碑不能把未列入其纳管删除清单的暂停 Binding 当作已删除。
7. 新增前向数据库迁移，对排除和恢复回执实施窄范围校验。保留租户、owner、当前值 CAS、删除 pin、来源迁移、审计及请求结果约束，不修改已应用迁移。

## 独立保留暂停证据

停用保留证据，定义的破坏性擦除仍须单独授权。X 和 Y 在同一源码修订中暂停时，彻底删除 X 可以清理 X 自身的回执和共享源码请求，但必须保留 Y 的独立回执及审计。随后 Y 恢复纳管资格时，可以复用原 Binding 身份，从最新 DTS 重新同步。Y 的证据不保留 X 的专属内容。

暂停回执只能由可信数据库提交路径生成，调用者不能自行提供豁免。它只证明来源连续性：恢复仍要求当前主体/所有者/登记有效、当前值与来源 pin 的精确身份一致、配置修订顺序正确，并通过正常源码授权及新提交审计。证据缺失或伪造仍须拒绝。保留 Y 的证据既不授予删除权限，也不扩大恢复 Binding 的权限。

## 验证与交付

协调者负责影响选择器、相关 TypeScript/构建/静态检查、完整 PR CI、一次独立评审和最终必需的 Merge bar。数据库行为须使用真实 PostgreSQL 与受限 API 角色验证。注入编译器的集成测试只证明数据库行为；现有原生 DTS 测试仍负责真实编译验收。本地环境可用性、实际命令、PostgreSQL 与 CI 结果统一记录在 PR；仅选中或编写测试不构成执行证据。

必需覆盖：

- 停用后的值修改、属性删除、整节点删除、主体变化和来源迁移；连续保存不改变精确历史。
- 同一配置同时包含有效、停用和未知属性；历史 pin 存在时仍能创建新的有效参数。
- 预览与应用之间发生组织登记、必需所有者或当前 Catalog 停用/恢复；不留下部分文件、值或审计变更。deprecated 定义继续纳管。
- 源码修改、缺失、整节点删除及重新出现后的恢复；保持原 Binding 身份，以最新源码取值，幂等重试且不回写历史值。
- 未变 JSON 成员的历史保留与恢复、当前读取过滤和精确历史访问。
- 已有精确暂停证据时的单参数/批量修改、成员添加/移除、JSON 纳管及快照创建/恢复；有效参数继续可用，暂停值及 pin 不变。暂停属性迁移后移除旧来源成员，再恢复治理并从保留的源码同步同一 Binding。
- 数据库拒绝伪造排除、错误 owner/pin、未经批准的恢复，以及伪装成 derived 的 DTS 恢复。
- X/Y 由同一真实源码请求暂停后，经授权的定义删除服务清理 X 和共享请求；Y 的值、pin 和历史保留，且能从最新 DTS 恢复同一 Binding。必须实际调用删除流程，不能以手工删除请求行替代。
- 既有授权、租户隔离、原始保存限制、当前值 CAS、删除来源证明、审计回滚和原生 DTS 校验全部保持通过。

基于当前 `main` 创建一个 PR，在同一 PR 修复问题，仅当精确最新提交的全部必需检查通过后合并。部署与生产数据修复另行处理。
