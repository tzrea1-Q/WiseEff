# Overlay parsing knowledge promotes into a platform tier

ADR-0008 gave an organization a writable parsing layer and stopped there. The overlay is a terminal store: `organization_driver_schemas.organization_id` is `not null`, the active uniqueness index is `(organization_id, lower(compatible))`, and nothing reads an overlay outside the organization that wrote it. Two consequences follow that the decision did not price. First, the driver layer is strictly less capable than the definition layer it links to — `parameter_specs` already has a platform tier (`organization_id IS NULL`, readable and bindable by every tenant, not mutable through ordinary org Admin APIs), so a property's definition can be shared while "which compatible claims these properties" cannot. Second, the only route to platform-level parsing remains a `schemas/dts` change and a release, which is exactly the route ADR-0008 was written to avoid; knowledge authored in the product accumulates in the database and never flows up. If five organizations each author the same `compatible`, the platform holds five rows, has no way to notice, and a later correction has to be made five times.

We decided that overlay parsing knowledge is **promotable**, and that the promotion target is a **platform-scoped row in the same overlay tables** rather than a generated DTS file. `organization_id` becomes nullable, platform rows are visible to every organization, and the matcher's existing `manual` tier splits into platform-manual ahead of org-manual. Promotion is a reviewed platform act that supersedes the contributing organization rows instead of deleting them. The tier list stays a strict total order, so `matchDriver` gains one entry and no new precedence semantics; `schemas/dts` remains repository-managed and read-only from the product, unchanged from ADR-0008.

## Considered Options

- **Promote by generating DTS documents into `schemas/dts` and shipping a release** — rejected as the primary path because it reintroduces the release train ADR-0008 removed, and because generated documents would become a second authoring source for a tree whose value is that it is hand-written, diffable, and reviewed. It survives as a downstream step for drivers that need prefix patterns or true content-hash reproducibility, neither of which the database tier offers.
- **Copy-on-share: export an overlay from one organization and import it into another** — rejected because it multiplies rows rather than deduplicating them. N organizations still hold N rows, a correction must be re-imported N times, and there is no row that owns the fact. That is the current problem restated as a feature.
- **Drop the organization dimension and make the overlay global from the start** — rejected because it destroys blast-radius isolation and recreates the failure ADR-0008 rejected in the "edit `schemas/dts` from the product" option: one form submission changes parsing for every tenant. The organization tier is where authoring is safe precisely because it is cheap to be wrong there.
- **Let organization rows outrank the platform tier, so an organization can locally override** — rejected because `matchDriver` treats same-tier multiplicity as ambiguous and blocks parsing, so the tiers must remain a total order. A genuine per-organization divergence on the same exact `compatible` is a modeling error that should be surfaced, not silently resolved by a precedence rule.
- **Auto-promote once N organizations author the same compatible** — rejected because agreement on a `compatible` string is not agreement on property semantics, and an automatic promotion silently changes parsing for every other tenant. Detection is automatic; promotion is reviewed.
- **Leave promotion out and harvest overlays manually when the need appears** — rejected as the durable answer, though it is what ships today. The data needed to harvest is already recorded, so deferring costs duplicated authoring rather than migration; but with no signal that duplication exists, "when the need appears" has no trigger.

## Consequences

- Promotion is two-phase. An overlay property links a `parameter_spec_id`, so a platform driver would otherwise point at organization-private definitions. The linked specs must be platform-scoped first; the spec side already has the target shape (`organization_id IS NULL`) and lacks only the operation.
- Promotion is a platform act, not an organization Admin act, mirroring the existing rule that global specs are maintained through platform governance rather than ordinary org Admin activate.
- Contributing organization rows are superseded, not deleted, so authorship and audit survive. The tree must say "your overlay was promoted" or the operator reads their work as deleted — the same missing signal ADR-0008 flagged for the case where the platform later ships the driver as vendor, and the same place to put it.
- The active-uniqueness invariant widens from "one active row per (organization, compatible)" to "at most one active row per compatible visible to an organization". A new organization row whose compatible a platform row already covers is rejected at write time, which is how the total order stays enforceable at the data layer rather than at match time.
- `matchDriver`'s tier loop becomes linux → vendor → platform-manual → org-manual. Nothing above `manual` moves, so ADR-0008's guarantee that nothing an operator authors can shadow a released vendor schema holds unchanged.
- Duplication detection is a group-by on `lower(compatible)` across active organization overlays, made cheap by the partial unique index that already exists. This is the promotion queue, and it is the artifact the current design lacks entirely.
- `schemaRegistryCache` keys on `(schemasRoot, organizationId, contentHash, orgOverlayDigest)` today and gains a platform-tier digest. Invalidating the platform tier invalidates every organization's entry, which is the first cross-tenant invalidation in the cache and the main implementation risk.
- Reproducibility becomes a triple. ADR-0008 already required binding provenance to record the org overlay version alongside `vendorContentHash`; the platform tier version joins it, or a parse change that originated in a promotion is unattributable from the binding alone.
- The platform tier stays exact-compatible only. Prefix patterns remain a repository change, unchanged from ADR-0005 and ADR-0008, so promotion never becomes a way to acquire matching power the product does not otherwise grant.
- Two organizations that authored *different* property sets for one compatible make the compatible ineligible for promotion until the divergence is resolved. The queue must show the divergence rather than pick a winner.

## Follow-up

This record fixes the direction; nothing ships with it. The organization overlay remains the only writable tier, and the structure it already has — nullable-ready scoping, a total tier order, per-organization cache keys, and full authorship provenance — is what makes the promotion additive rather than a migration. The cheapest first increment is the pair of signals: the "your overlay is shadowed / was promoted" chip on the attribution tree, and the cross-organization duplicate report. Both are reads over existing data, and together they turn "should this be promoted" from an unanswerable question into a queue.
