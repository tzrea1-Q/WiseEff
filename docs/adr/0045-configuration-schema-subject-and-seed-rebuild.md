# ADR-0045: Configuration models share the canonical parameter catalog

> Chinese: [Chinese](../zh-CN/design-docs/adr-0045-configuration-schema-subject-and-seed-rebuild.md)

Date: 2026-09-14; D10 confirmed 2026-09-15. Status: accepted destination decisions D01–D10; implementation and target execution are pending the [unification plan](../exec-plans/active/2026-09-14-parameter-unification-and-seed-parity.md). Number 0044 was unused at source baseline `6d72e17cb4c581e7235b181dbbfd45d92f4dee7b`; recheck before integration.

The retained product seeds include software configuration with no authoritative device compatible. Add **ConfigurationSchema** as the third formal Catalog subject, identified by a governed model identifier. Keep Driver compatible matching and NodeType fallback unchanged; share the existing ParameterDefinition, DefinitionRevision, registration, placement, Binding, ProjectValue and unique publication writer. File format and model identity are separate; the two JSON compatibility seeds still require ConfigurationSchema.

Scope amendment accepted on 2026-09-15: deliver native DTS and JSON project-source import, approval-driven writeback and export this round. Defer YAML/TOML/ENV project-source support and their eight compatibility seeds to [TD-124](../exec-plans/tech-debt-tracker.md), preserving original metadata, examples and project initial/recommended values without converting them into active JSON seeds. The four DTS/JSON compatibility items remain in scope. Reject unsupported project-source formats before staging/apply. YAML-authored vendor Catalog definitions remain valid metadata inputs for DTS publication. This changes delivery timing, not the shared subject model or the remaining archive-rebuild decisions.

The three built-in projects receive complete, explicitly identified demo DTS baselines. Dangling overlay references must resolve against reviewed source declarations; compiler stubs and similar names do not establish a formal Driver or NodeType. Preserve business properties and project values, record each identity assignment, and label these configurations as demonstrations rather than real-device firmware.

This extends the two-kind restriction in ADR-0040/0041/0042 only where subject kinds, selector kinds and their consumers must recognize ConfigurationSchema. Stable identities, complete immutable releases, explicit lifecycle, pinned interpretation, authorization, audit and ADR-0043 publication controls remain binding. Historical two-kind releases must still replay; new capabilities require explicit version admission, never reinterpretation of old bytes. Database changes use new migrations; applied migrations and prior ADR history are not rewritten.

We rejected inventing a device compatible for software configuration because it would falsify source identity. We rejected broadening logical-service Driver because that would weaken the existing device-matching contract. We rejected a second configuration definition/value library because it would recreate the divergence this work removes. The cost is explicit extension of compiler, matcher, storage constraints, APIs, registration/placement and authoring/workbench UI.

For this deployment, the user also chose seed rebuilding over populated parameter migration: preserve non-parameter data, archive old parameter values/drafts/history/source versions, initialize only Atlas/Aurora/Nebula, and retain acme release history while retiring that sample from new selection.

The bounded `archive-rebuild` profile supersedes the ordinary two-release/90-day legacy-read window **only for the explicitly selected deployment and its inventoried old parameter surfaces**: authorized old links immediately become archived notices once the verified rebuild switches traffic. It replaces old/new configured-value equivalence with seed parity, archive completeness, non-parameter preservation and complete canonical-consumer coverage. Target identity, scope and candidate must be pinned by the operator plan. This is not normal S13/P13 retirement evidence, OP-09 completion or a change to other deployments; the original R0–R10 classification facts remain intact. No waiver applies to whole-state restoration, permissions, audit, reference reconciliation, complete release lineage or publication authorization. Offline archives/mappings/audit are retained under the deployment's existing retention policy; this decision authorizes no archive destruction.
