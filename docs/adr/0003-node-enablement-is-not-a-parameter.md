# Node enablement is not a parameter, but rides the parameter draft pipeline

The DTS `status` property decides whether a node is available to be probed, so it is a switch that turns hardware on and off rather than a value that tunes hardware. The codebase never made that call, and as a result `status` entered the system through three contradictory doors at once: it matched vendor schemas and became an ordinary spec plus binding on nodes that carry `compatible`; it fell through to the spec review queue on overlay fragments that do not; and the mock runtime hard-coded `spec-sc8562-status` as a parameter whose own description read "Node enablement status". The review-queue door was the expensive one, because `evaluateCandidateSemanticGate` fail-closes on open spec reviews while `editService` kept a second, divergent list of structural keys that omitted `status` — so noise tasks nobody should ever have seen were blocking candidate promotion and migration finalize.

We decided that **node enablement is a first-class domain concept that is not a parameter**: it never has a `ParameterSpec`, never appears in the spec library, and never produces a spec review task. We also decided that **it nevertheless shares the parameter draft pipeline** rather than getting one of its own, by generalizing a draft's subject from "a binding" to "an edit target" that is either a binding or a node's enablement.

## Considered Options

- **Model enablement as a specially-typed parameter** — give `status` a built-in organization-shared spec with an enum or boolean editor and reuse bindings, review, validation, and writeback untouched. Rejected because every governance surface would then have to special-case a row that looks like a parameter but must not be reviewed, versioned, or policy-targeted like one, and because the concept genuinely differs: enablement is per node, defaults to on when unstated, and is invalidated by a disabled ancestor.
- **Keep the domain concept but store it as a hidden internal spec plus binding** — cleanest to implement, since nothing in the storage layer changes. Rejected because it reopens the same door we just closed; a "hidden" spec leaks the moment any query, export, or dashboard forgets the filter.
- **Build a fully parallel enablement draft and publish pipeline** — the most faithful to the domain boundary. Rejected on a concrete failure: `createBindingDraft` refuses to submit when a round's drafts sit on more than one working tip (`mixed-working-tips`, HTTP 409). A user who changes two parameters and disables one node in the same round would produce two candidate revisions, two toolchain runs, and two gate evaluations, and then be unable to submit them together.

## Consequences

- Structural-key classification collapses to one exported predicate in `src/domain/parameter-topology/parameterSurface.ts`, taking the union of the two lists that had drifted apart. Ingest short-circuits structural keys *before* matching, so the matched door closes along with the unmatched one.
- Enablement is derived, not stored as an edit: enabled means the node's own `status` is absent, `ok`, or `okay`. Reachability is a separate derivation that also requires every ancestor to be enabled, and the product names the blocking ancestor instead of restating the node as disabled.
- Because enablement shares the draft pipeline, it inherits working-tip coordination, candidate revisions, toolchain validation, publish gates, and audit for free, and a mixed round of parameter and enablement edits submits as one unit.
- Because enablement is not a parameter, `status` is removed from generated vendor schemas, existing `status` specs and bindings are deprecated and hidden rather than deleted, and the enablement vocabulary is hard-coded in the domain module — it comes from the Devicetree specification, not from a vendor's YAML.
- Values that are neither `ok`/`okay` nor `disabled`, such as `reserved` and `fail`, are treated as not enabled but are never rewritten by a toggle, so an author's intent survives a round-trip through the product.
