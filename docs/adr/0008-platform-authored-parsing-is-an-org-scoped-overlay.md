# Platform-authored parsing is an org-scoped overlay, not repository editing

ADR-0007 made declaring a supported driver a product act, and surfaced parse coverage on the attribution tree. That immediately created a dead end: an Admin can register a driver group whose exact `compatible` no pinned schema matches, the row reads "解析未覆盖", and the product offers nothing further. The parsing contract lives in `schemas/dts`, is loaded from disk by `loadSchemaRegistry`, is pinned by `catalog.vendorContentHash`, and is the only input `matchDriver` and `matchProperty` read inside the ingest transaction. Closing the gap requires a repository change and a release, performed by someone other than the operator who holds the vendor binding.

The product does already let a human author property definitions. The spec review queue's `createOrgManualParameterSpec` writes an organization-scoped `parameter_specs` row with `source_kind = 'manual'`, a draft→active lifecycle, and provenance back to the review task. But those rows carry `driver_schema_id = null` and are never merged into `SchemaRegistry`, so they resolve one occurrence in one revision and change nothing about what the next upload matches. Authoring exists; it is occurrence-scoped, so it never compounds and never moves coverage.

We decided that parsing support authored in the product is **driver-scoped and organization-scoped**: an org-owned manual `DriverSchema` — exact compatible plus **links to ParameterSpecs** (definition library) — merged into `SchemaRegistry` as the lowest releasable tier at ingest. Overlay rows declare which properties a driver claims; types, units, and docs live only on ParameterSpec / `dts_property_specs`. The pinned `schemas/dts` tree stays repository-managed and is read-only from the product. The answer to "should Admins manage schemas from the frontend" is therefore yes for the organization's own gap-fill layer and no for the global contract, and the split is not a compromise: the two layers differ in blast radius, in who can review them, and in whether reproducibility depends on them.

## Considered Options

- **Leave everything in the repository and turn "解析未覆盖" into a support request** — rejected because the coverage chip already ships, so the gap is visible with no path, and because it puts a release train between a known vendor binding and a parsed parameter. It also concedes that registration, which ADR-0007 defined as one act, is only half an act.
- **Let Admins edit `schemas/dts` documents through the product, writing back to git or opening a PR** — rejected because that layer is global and has no organization dimension: one form submission changes parsing for every organization. It also dissolves `vendorContentHash`, whose purpose is that the same DTS at the same version parses the same way; and a form gives up the diff, review, and rollback that are the actual reason the contract is a file.
- **Merge the existing org manual `parameter_specs` into the matcher instead of adding a driver layer** — rejected because those rows are keyed by property key with no compatible, so they would gap-fill every node in the organization sharing that key. More decisively, `matchProperty` returns unmatched as soon as `matchDriver` is unmatched, so property-only rows structurally cannot help the case that motivates this decision: no matching driver at all.
- **Give org-authored drivers the prefix patterns pinned schemas have** — rejected for this decision. Overlapping prefixes across the pinned tier and the overlay need a new precedence rule, and ADR-0005 and ADR-0007 already fixed exact `compatible` as the only operator-facing lever. A device that genuinely needs prefix matching remains a repository change.
- **Add `organization_id` to the `driver_schemas` table** — already rejected by ADR-0007: that table is a shadow written by `upsertMatchedDriverSchema` only when a node matches, so it cannot hold a driver no DTS has produced.

## Consequences

- Precedence needs no new semantics. `matchDriver` already selects `manual` only when no linux or vendor driver matches, and `matchProperty` already places `manual` last as gap-fill. Nothing an operator authors can shadow a released vendor schema, and that guarantee comes from existing code rather than a new rule.
- `loadSchemaRegistry` becomes pinned files plus an organization overlay, so `schemaRegistryCache` must key by organization and invalidate when the overlay changes. This is the largest implementation cost, and it is the same cost ADR-0007 flagged when it pulled the registry out of ingest.
- Reproducibility shifts from a content hash to a content hash plus an overlay version. Binding provenance must record which overlay version matched, not only `source`, or "why did this revision parse differently" becomes unanswerable.
- Overlay drivers are draft→active with audit, mirroring the existing manual spec workflow; `isReleasableDriver` already excludes drafts, so a half-authored driver cannot affect ingest.
- Two overlay drivers claiming the same exact compatible within one organization must be rejected at write time. `matchDriver` treats same-tier multiplicity as ambiguous, which would block parsing rather than pick one.
- `SchemaRegistry` ids are globally shaped (`driver:$id:v{version}`). Overlay ids need an organization segment or they will collide across tenants inside a shared cache.
- The parse-coverage chip gains an action: an uncovered registered driver group can be given an overlay schema from the same dialog, which is what finally makes registration complete.
- The spec review queue narrows rather than disappears. It keeps the case of a property under a *matched* driver the schema does not define; authoring a whole driver moves to the overlay. `createOrgManualParameterSpec` stays as is.
- An organization can author a driver the platform later ships as vendor. The overlay must lose silently at that point, which existing precedence already delivers, but the tree should say so or the operator will read their own work as deleted.

## Follow-up

Scoping the writable tier to one organization left the knowledge authored there with no way out: no promotion, and no way for two organizations to share one row. ADR-0009 settles the direction — overlay rows promote into a platform tier in the same tables — while keeping this decision's rule that `schemas/dts` stays repository-managed.
