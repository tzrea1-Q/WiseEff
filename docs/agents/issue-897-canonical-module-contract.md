## 2. Minimal user contract

**Identity and actions.** A row is keyed by the current-release `subjectId`, with `type`, `canonicalName`, aliases, membership, organization registration status/id, and placement id/module id. Driver uses a `driver-group` destination; NodeType uses `node-type`; ConfigurationSchema uses `business` as already enforced by the guarded registration writer. Only an active current-release subject may be explicitly registered. A registered subject may move through its existing registration's Placement owner; retire/restore and unresolved recognition stay in Governance/Review Queue. DTS parse coverage remains a capability annotation. Keep the shared `public.parameter_modules` taxonomy; its row is a destination, never a Catalog identity.

**Compatible discovery.** The recommended source is verified DTS observation evidence in `parameter_catalog.parameter_observations`, joined through the exact organization/project, logical node, and captured config revision to `dts_logical_node_revisions`. `parameter_review_evidence` supplies linked review state where its provenance is sufficient; its `observation_id` may be null and must not be treated as a proven DTS observation. Expose only evidence from a current, proven source context in the actionable queue; historical or stale evidence remains retained as history, not current actionable work. An incomplete locator, ambiguous owner, non-DTS source, or unverified currentness is not a candidate. Obtain individual compatible selectors from the DTS ingest/parser owner (`parameter-topology/ingestService.ts`, `parseCompatibleList`), not a query-side copy of its parsing rule; validate each full selector **byte-for-byte** under ADR-0040. The persisted `dts_logical_node_revisions.compatible` text alone is not proof of token boundaries: a comma inside `vendor,device` belongs to one selector. No lowercasing, trimming, quote stripping, suffix matching, or name-derived identity. Use `CatalogSnapshot.resolveSubject` / `catalog-kernel/runtime/subjectMatch.ts` on the captured release with **only** parsed `driverCompatibles`, `nodeTypeFallback: { kind: "absent" }`, and no `configurationSchemaIds`; otherwise an unknown compatible could match a NodeType fallback. A compatible is evidence, not a `subjectId`.

The narrow read result is a release-pinned, cursor-paged list of `{ compatible, evidenceCount, projectCount, evidenceRefs: [{ observationId, projectId, logicalNodeId, configRevisionId }], candidate: { kind: "recognized", subjectId, registrationId? } | { kind: "review-required", reviewItemIds } | { kind: "unavailable", reason }, catalogReleaseId, matcherRevision }`. `subjectId` is returned only when the existing exact Catalog matcher proves a unique current-release match; otherwise the row is review-required or unavailable, never a guessed registration target. `evidenceCount` deduplicates exact logical-node/config-revision observations, not property rows or Bindings; `projectCount` is distinct authorized projects. Group for display by organization + exact full compatible + captured release/matcher revision. Review evidence without proven DTS provenance stays in Review Queue rather than acquiring a fabricated observation reference. Keep review item IDs separate: several review items may share one compatible and must not be resolved by one guessed group ID. Bound both page size and returned evidence references. Do not expose raw evidence or foreign project IDs to an unauthorized principal. If the existing Review Queue projection can provide this exact result, reuse it instead of adding a route; otherwise add only this read through the Governance query/HTTP seam, not through a new module taxonomy service.

**Ignore semantics and count.** “Ignore” means `resolveReviewItem({ resolution: { type: "mark-out-of-scope" }, reason })` on one authorized review item with its ETag, release pin, and idempotency key. It does not create a permanent `(organization, compatible)` suppression row. A grouped row with multiple open items links to each item for individual resolution; no unreviewed bulk action. The module page's `ignoredReviewItemCount` is the number of distinct `parameter_review_items.id` with `status = 'out-of-scope'` for the authorized organization and captured Catalog release. Label it “ignored review items,” not “ignored compatibles”; historical releases remain persisted history and do not inflate the current card. Existing `listReviewQueue` exposes open work only, so the count needs a narrow authorized projection. An out-of-scope resolution does not auto-reopen, per ADR-0042. The old `parameter_module_dismissed_compatibles` is legacy state, not canonical history.

**Counts.** Module `definitionCount` is the distinct set of active current-release Definition IDs inherited through active registrations/placements in that module subtree; definition-only subjects count. Module `parameterCount` is distinct current canonical Binding IDs in the subtree, excluding deleted/replaced/non-current rows through `current_project_parameter_bindings`. Subject detail uses its own active/deprecated/retired Definition counts; `getRegistration.impact` gives current Binding and distinct-project counts for a placement move. Do not label observation count as Binding count, sum child counts with duplicates, use ProjectValue count, or return zero when Catalog/registration data failed. Reuse the existing registry rollup and Catalog pagination, repairing only a demonstrated mismatch.

**Meaning of “recompute.”** Canonical Binding has `registration_id` and `subject_id`, not a mutable per-Binding `module_id`. There is no equivalent to the legacy bulk `update project_parameter_bindings set module_id`. A Placement move changes the **current view** of every current/future Definition and Binding of one registration; it preserves their identities, values, source pins, and history. A wrong recognized subject is resolved through the existing review/identity-correction owner, never by moving individual Binding rows. Canonical mode has no “recompute” write button; a refresh is read-only. Legacy mapping/recompute controls and calls must not remain actionable or fire on canonical page load. Overlay authoring and shared taxonomy controls retain their separate owners.

**Move sequence.** Capture one Catalog release; load subject/registration and module-kind options; fetch `getRegistration` impact and `getPlacement` ETag; show source/destination, active Definition count, current Binding/project counts and a clear advisory label; require the authorized admin's confirmation; call existing `updatePlacement` with destination module ID, release pin, ETag and idempotency key; refresh canonical subject, registry and project views. The Governance owner must validate organization, current membership, registration state, destination existence/kind/parent where applicable, and any approved capacity rule in the same write transaction, then audit the actual before/after state. A stale pin/ETag, capacity failure, duplicate key with different payload, or conflicting placement fails without a partial move. Replay of the same key/payload returns the original result. Do not add a second placement writer or promise an exact post-write count from an advisory preview. Module rename/reparent preserves Placement module IDs; kind change or delete must honor the retained Placement constraints in `parameterModuleRepository` and the database.

## 3. Decisions to confirm in review

1. **Currentness and token extraction.** Recommendation: actionable compatible rows require a verified current project source/config revision and parser-proven individual selector tokens; older observations remain persisted history. C1 must name the authoritative current-source pointer and the ingest/parser output used. If the tokens are not persisted or the source owner cannot prove currentness, C1 must first expose a narrow source-owned read seam or report that exact blocker; the Governance query must not parse raw text itself. Omit unproven rows and expose an explicit unavailable/error state. Including all immutable observations would resurrect stale discoveries after source replacement; splitting raw text on a comma would break `vendor,device` identity.
2. **Grouped ignore.** Recommendation: item-scoped `mark-out-of-scope`, with a grouped compatible row linking to each review item. A permanent compatible-wide suppression would need a new governed identity, reopen policy, and audit contract; it is outside #897's minimal flow.
3. **Destination capacity.** Recommendation: reuse an approved placement/registration capacity rule if one applies, and enforce it transactionally. Current kind/ownership checks alone are not proof of a capacity policy. If a move requires capacity approval and no approved source exists, report that exact gate and stop that move; do not invent a threshold. #815 Policy usage and #816 read-query budget are separate concerns.
