### Draft implementation and remaining boundary

- `0180_mod_d02_offline_capture.sql` creates passwordless fixed maintenance roles and a fixed `SECURITY DEFINER` capture function. Its source LOGIN has only the listed column grants, but those columns remain visible across organizations at SQL level. The capture LOGIN can execute only the fixed function and cannot read/write the case tables directly. Database migration application is forward-only; no deployed credentials are included.
- `offlineLocalSession.ts` resolves an existing local login token without updating `last_used_at`; `offlineModD02SourceReader.ts` obtains the real provider batch with a persisted USER invocation and completed-manifest recheck. `offlineModD02Capture.ts` verifies both PostgreSQL LOGIN identities and the maintenance plan/artifact/Release pins, then calls the fixed function in one transaction. The function locks and rechecks the session, active admin, P10 run, module inventory, associations, selected mapping versions and Subject facts before case/result/audit writes. The source read and capture use separate connections, so the transaction rechecks the facts that can drift between them; it does not turn the source read into one cross-connection snapshot.
- In the disposable PostgreSQL integration check, real P0-P10, local login, two MOD modules, Registration/Placement, and Catalog Release produce two `unexplained-difference` results. A second-result fault and a separate audit fault each roll back cases, results, and audit; recovery writes two, then exact retry writes zero. The test confirms the source LOGIN can query the other organization's permitted module columns, cannot read `password_hash` or write audit, and capture leaves `last_used_at` unchanged. This is local capability evidence only, not target role or target run acceptance.
- The fixed function verifies the protected database facts and outcome shape but receives a provider-produced JSON batch from the trusted maintenance process. It does not independently reproduce the whole TypeScript provider or establish that all 11 families and nine gates were collected. `fullReport.available=false`; independent P11 and post-retirement verification remain mandatory. The default-off maintenance hook does not start API/worker/web or advance P12.
- The only new maintenance configuration is `WISEEFF_MOD_D02_CAPTURE_ENABLED=true`, `WISEEFF_MOD_D02_SOURCE_READER_DATABASE_URL`, and `WISEEFF_MOD_D02_CAPTURE_DATABASE_URL`; `AUTH_PROVIDER` must be `local`. The two URLs must reach the same database through their distinct fixed LOGINs. The local session token is read from `/dev/tty` with echo disabled, never an argument, environment value, or log field. Without the flag, the existing maintenance flow does not open either new connection. The deployment package must bind its own artifact and Release pins; this Draft does not install credentials or enable the flag in a target environment.
- The hook uses the existing P2 observation, completed checkpoint, and operator attestation handled by the cutover controller. It does not independently inspect live service processes a second time at the capture instant. Its receipt therefore cannot by itself prove sustained traffic isolation; target operation must keep the accepted P2 fences in force, and independent P11 remains separate.

## Decision requested

The permission choice for the exact 29-relation/137-column provider list plus six `auth_sessions` columns, database-wide row visibility on those columns, the function-only capture LOGIN/NOLOGIN owner, and the existing `PUBLIC TEMP` boundary has been accepted for this Draft implementation. **Target enablement remains a separate decision:** provision only the two maintenance credentials in the target environment and run the default-off capture after local role and P2/P10 checks. This is not deployment, P11 substitution, or candidate API startup. Capture is limited to **pre-P11, pre-activation evidence for one organization and one completed S7 run** while API, worker, and web remain stopped.

The code entry is the populated maintenance path in `ops/self-hosted/scripts/upgrade.sh`, after `controller.dispatch({ action: "execute" })` has returned a completed P10 run and before the Release Verification `prepareVerification` / `runVerification` calls. It remains disabled unless `WISEEFF_MOD_D02_CAPTURE_ENABLED=true`. The standalone `scripts/wayfinder/execute-parameter-catalog-cutover.ts` does not invoke this capture. Neither entry implements independent P11.

The Deployment Operator launches that maintenance process. After P10, the Organization Admin authenticates to the offline process using an existing WiseEff local-auth session token presented through a protected terminal prompt. This Draft seam supports `AUTH_PROVIDER=local` only; OIDC/HMAC deployments fail closed until a separate offline authentication seam is approved. The implemented read-only resolver hashes the token with `hashLocalSessionToken`, checks its `auth_sessions` row for expiry and revocation, and reloads the active user, Organization, role bindings, and effective permissions from PostgreSQL. Only that server-built `AuthContext` may be passed to `createUserInvocation(auth)`. `createUserInvocation` only brands an `AuthContext`; it does not authenticate. The user/session ID and organization are never accepted as CLI or JSON identity selectors; `operatorAuditRef` remains an audit label, not authentication.

This uses the existing account-authentication source, not a new pre-shutdown authorization token. `/api/v1/auth/login` creates the local session after password verification, but the session itself is a reusable bearer credential and is not bound to a run. It expires at the persisted `expires_at` and is refused after `revoked_at` is set; it may be replayed until then. The capture action separately pins the exact run and is idempotent for the same evidence, with changed evidence refused. The local session authenticates a WiseEff account, not proof of a physical human: ADR-0038 explicitly says `AuthContext` makes no such claim. If physical-human assurance is later required, an IdP/MFA or equivalent human-only identity contract remains outside this seam. The Draft offline resolver uses a read-only query because the existing HTTP resolver updates `last_used_at`; target enablement remains pending.

After capture, a **separate read-only independent P11 verifier** must recompute the complete V01-V17 set and D01-D09 semantic comparison across all 11 consumer families from the same pinned source boundary. It must use code and database credentials distinct from writers. The P11 report, not the organization-projection capture response or rows, is the pre-P12 evidence. The verifier independently recomputes D02; it does not treat the v2 writer's observations as proof of itself.

## Recommended execution sequence

1. Before downtime, a valid local-auth Organization Admin session is created by the existing `/api/v1/auth/login` flow. The session is authentication only; it does not approve a run or waive any gate. OIDC/HMAC deployments are unsupported by this proposed seam and remain disabled. The Deployment Operator prepares the exact plan and its target artifact / Catalog Release pins.
2. The accepted P2 boundary stops API, worker, and web; stops proxy traffic; pauses and drains the queue; and proves zero leased work, zero business traffic, no application writer, and both legacy and candidate writer fences. S7 then continues only through the accepted one-shot maintenance process. No HTTP API is available during capture.
3. Immediately after `executeCutover` reports completed P10, the maintenance process preserves the completed P0-P10 run receipt/checkpoints, retains the controller's P2 isolation evidence, and rereads the persisted run. It requires every P0-P10 checkpoint, including P2, P5/P7/P10, one complete v2 P7 manifest, stable source snapshot fingerprint, plan digest, target artifact SHA, Catalog Release ID/digest, and no live S7 run. The process obtains the trusted artifact SHA from the immutable deployed-package attestation, not a request or operator-supplied identity field. The completed-run receipt/checkpoints are evidence only; they are neither capture nor P11.
4. The Admin supplies the local session token through a no-echo terminal prompt. The Draft `wiseeff_mod_d02_source_reader` connection hashes it, verifies the exact `auth_sessions` row (including persisted expiry and revocation fields), and reloads the current active user, Organization, role bindings, and effective permissions. It must match the session's persisted user/Organization and grant Organization `admin` authority. This source-reader connection also runs the existing read-only MOD D02 provider; its allowlist must cover the provider's exact run/manifest, module/association, and Catalog source reads. The capture transaction receives the validated session ID and rechecks and locks the session, active user, Organization, and admin role until commit. It refuses expired/revoked sessions, inactive users, changed roles, cross-organization scope, or any missing pin. This Draft seam is implemented but remains disabled in target environments.
5. The existing `provideModParameterCatalogComparisonCaseBatchV2` provider builds the scoped projection on the source-reader `Database`/root Pool. The current writer requires its `Database` and `pool` to resolve to the same root Pool and combines source reads with writes, so it cannot be called unchanged across the reader and capture logins. The Draft TypeScript split passes the generated batch to the dedicated capture function over the separate `wiseeff_mod_d02_capture` connection; in one transaction the function rechecks all pins and source inventory/associations under locks, then writes the case/result batch and audit atomically. Exact retry is a no-op; changed evidence under an existing identity fails closed. The receipt contains only the scoped projection digest, counts/checksums, and append/replay counts—no Archive payload, raw value, or claim that P11 passed. Close the capture transaction and connection before starting P11.
6. A separately operated, read-only P11 verifier then recomputes every required V01-V17 and D01-D09 check across all 11 consumer families against the same run, plan, artifact, Catalog Release, mapping epoch, P7 manifest, and source boundary. It independently recomputes D02; the writer's rows are inputs to inspect, not proof of themselves. The verifier and capture use distinct code processes and database identities.
7. P11 passes only at the accepted thresholds: zero `unexplained-difference`, zero `unqueryable/protected-reference-missing`, every protected reference enumerated, all 11 consumer families covered, and deterministic expected counts/checksums. The accepted P11/report approval flow may then advance to P12.
8. P12 binds both passing P11 report digests to the read-pointer switch. P13 retires legacy writers while services remain stopped. After P13, a **new** `post-retirement-runtime` attempt reruns the complete V01-V17 plus D01-D09 set, including V13/P02 writer-reachability and privilege negatives. Only that passing and approved post-P13 runtime pin permits candidate API verify-only startup; worker/web and isolated API/browser acceptance follow while traffic remains isolated.

The phase order preserves the accepted maintenance contract: no API/worker/web process is used for pre-P11 capture, P11 remains independent and mandatory before P12, and candidate API startup remains after P13 plus a fresh full P11 rerun. A successful MOD D02 capture alone is never a P11 result. Any missing session/auth seam, failed P2 proof, incomplete run/manifest, pin drift, provider error, ambiguous association, or P11 failure blocks progress and keeps traffic isolated.

### Disposable PostgreSQL read-permission probe

The focused probe in `server/modules/release-verification/comparison/comparisonCaseResultsV2.integration.test.ts` uses the real P0–P10 orchestrator, two persisted organizations, MOD modules, Registration/Placement, a published Catalog Release, and the production `provideModParameterCatalogComparisonCaseBatchV2` function. A disposable `LOGIN NOINHERIT NOSUPERUSER NOBYPASSRLS` receives **column** SELECT grants only. The source `Database` and direct `Pool` resolve to the same root Pool; server-side statement logging for this test role records parameterized SQL without bind values, including queries made through acquired Pool clients. A successful read under these grants measures the current generic provider call graph, not a deployed reader role or a purpose-built minimum data projection. Registry and Kernel currently read more DTO fields and release content than MOD D02 itself consumes.

The table is the fixed grant candidate for that call graph. Each listed column includes output, JOIN, WHERE, and ORDER BY use; a predicate column cannot be omitted merely because it is absent from the returned DTO. The test grants no table-wide or schema-wide SELECT. Unless a row says otherwise, the statement is SELECT-only with no row or table lock. The organization filter is applied in the application, **not** in PostgreSQL row security.

The source reader remains an all-row, column-limited LOGIN; application organization filtering is not database row security.

### Implemented entry, identities and privileges

The default-off entry is `ops/self-hosted/scripts/upgrade.sh` after completed P10 and before Release Verification preparation. It runs in the existing one-shot maintenance process while API, worker and web remain stopped. It reads a previously issued local session token through a no-echo terminal prompt; it does not accept caller-provided principal or organization IDs. `createOfflineModD02SourceReader({ database, pool, enabled, authProvider })` resolves the persisted account and calls the real MOD provider. `captureOfflineModD02PreP11({ sourceDatabase, sourcePool, captureDatabase, token, runId, requestId, expectedPlanDigest, expectedArtifactSha, expectedCatalogReleaseDigest, enabled, authProvider })` compares both database names and cluster identifiers, fixed LOGINs, role attributes and parameter-logging limits, then calls `parameter_catalog.capture_mod_d02_pre_activation_v2(runId, sessionId, tokenHash, principalId, organizationId, batch, requestId)` in one transaction.

Migration `0180_mod_d02_offline_capture.sql` defines passwordless `wiseeff_mod_d02_source_reader` (LOGIN) with the column-only provider grants listed above, `wiseeff_mod_d02_capture` (LOGIN) with schema USAGE and only fixed-function EXECUTE, and `catalog_mod_d02_capture_owner` (NOLOGIN) with exact read, lock-motivated UPDATE, case/result INSERT and audit INSERT privileges. It rejects pre-existing direct relation, column and function ACLs or membership on those fixed roles, checks effective SECURITY DEFINER execution including PUBLIC, and sets both LOGINs' `log_parameter_max_length=0`. `PUBLIC`, ordinary API, verifier and Governance roles receive no capture-function grant. The capture LOGIN cannot directly SELECT the session, source, case or audit tables. The source LOGIN cannot read `password_hash`, audit, or historical dismissed-compatible rows, switch roles, or write business tables. The source LOGIN's permitted columns are visible across organizations because this path has no RLS; the trusted process filters by persisted organization.

`WISEEFF_MOD_D02_CAPTURE_ENABLED=true` plus `WISEEFF_MOD_D02_SOURCE_READER_DATABASE_URL` and `WISEEFF_MOD_D02_CAPTURE_DATABASE_URL` are required to enter this path; `AUTH_PROVIDER` must be `local`. Without the flag, neither connection is opened. The URLs are deployment configuration, not credentials supplied by this Draft. Only the maintenance package may provide the expected plan/artifact/Release pins. The terminal token and its hash must not enter arguments, environment, receipts or logs. Target provisioning and the independent P11 verifier remain separate work.
