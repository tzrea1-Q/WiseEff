## Decision requested

Approve or reject one offline, post-P10 capture extension to the existing one-shot maintenance composition, plus its narrowly scoped source-reader and database call capabilities. It captures **pre-P11, pre-activation evidence for one organization and one completed S7 run** while API, worker, and web remain stopped. It does not run, replace, or pass P11.

The proposed code entry is the populated maintenance path in `ops/self-hosted/scripts/upgrade.sh`, after `controller.dispatch({ action: "execute" })` has returned a completed P10 run and before the Release Verification `prepareVerification` / `runVerification` calls. That controller already composes `executeCutover`, the Release Verification core, and the PostgreSQL gate adapters in one process. The standalone `scripts/wayfinder/execute-parameter-catalog-cutover.ts` also exits after P10. Neither entry currently invokes the v2 comparison writer, implements P11, or creates a trusted invocation; this is a proposed forward extension, not current behavior.

The Deployment Operator launches that maintenance process. After P10, the Organization Admin authenticates to the offline process using an existing WiseEff local-auth session token presented through a protected terminal prompt. This proposed seam supports `AUTH_PROVIDER=local` only; OIDC/HMAC deployments fail closed until a separate offline authentication seam is approved. A proposed read-only resolver hashes the token with `hashLocalSessionToken`, checks its `auth_sessions` row for expiry and revocation, and reloads the active user, Organization, role bindings, and effective permissions from PostgreSQL. Only that server-built `AuthContext` may be passed to `createUserInvocation(auth)`. `createUserInvocation` only brands an `AuthContext`; it does not authenticate. The user/session ID and organization are never accepted as CLI or JSON identity selectors; `operatorAuditRef` remains an audit label, not authentication.

This uses the existing account-authentication source, not a new pre-shutdown authorization token. `/api/v1/auth/login` creates the local session after password verification, but the session itself is a reusable bearer credential and is not bound to a run. It expires at the persisted `expires_at` and is refused after `revoked_at` is set; it may be replayed until then. The capture action separately pins the exact run and is idempotent for the same evidence, with changed evidence refused. The local session authenticates a WiseEff account, not proof of a physical human: ADR-0038 explicitly says `AuthContext` makes no such claim. If this decision requires physical-human assurance, an IdP/MFA or equivalent human-only identity contract is missing and capture must remain disabled until approved. The offline resolver, its connection, and this replay boundary are all pending approval; the existing HTTP resolver cannot be reused because its local-session path updates `last_used_at`.

After capture, a **separate read-only independent P11 verifier** must recompute the complete V01-V17 set and D01-D09 semantic comparison across all 11 consumer families from the same pinned source boundary. It must use code and database credentials distinct from writers. The P11 report, not the organization-projection capture response or rows, is the pre-P12 evidence. The verifier independently recomputes D02; it does not treat the v2 writer's observations as proof of itself.

## Observed repository boundary

- `createReleaseVerificationService` is routes-less and defaults to an empty adapter map. `runVerification(planDigest)` accepts no trusted invocation. The production PostgreSQL adapters cover V/M/P gates; no production call to `runVerification`, `generateLiveComparisonReport`, or the v2 MOD writer exists in this tree. Production OPS comparison reads S10-PER reports through `readReport` only.
- `writeModParameterCatalogComparisonCasesV2` accepts only `phase: "pre-activation"`, a trusted user invocation, and a completed-manifest run. It derives the organization from that invocation, re-reads persisted authorization, and writes only the MOD D02 organization projection. Its result explicitly says `fullReport.available: false` and `eleven-family-and-nine-gate-coverage-not-collected`.
- `readCompletedModComparisonManifestForComparison` verifies the trusted user, persisted organization/principal, and completed P7 manifest. `0179_parameter_catalog_comparison_manifest_binding.sql` constrains v2 rows to a completed `s7-orc-p0-p10-v2` run and an exact P7 selection. Its phase column records the comparison scenario; it does not attest P13 or establish independent verification.
- The MOD writer's transaction locks `public.users` and `public.user_role_bindings` `FOR SHARE`, then locks `public.parameter_modules`, `parameter_catalog.organization_subject_registrations`, and `parameter_catalog.subject_placements` `IN SHARE MODE`. It calls `parameter_catalog.assert_catalog_subject_active` and inserts/reads the two v2 comparison relations to verify idempotency.
- Migration 0138 revokes comparison case/result table access from `PUBLIC`, `catalog_synchronizer_role`, and `parameter_governance_writer_role`. Migration 0139's `catalog_verification_writer_role` is append-only on `verification_*`; `catalog_verifier_role` is SELECT-only on `verification_*`. Neither role grants v2 comparison writes or the source reads needed by P11. Migration 0179 adds constraints and triggers, not runtime grants.
- The disposable PostgreSQL test role in `comparisonCaseResultsV2.integration.test.ts` receives broad fixture SELECT grants, the Catalog active-subject guard EXECUTE, and INSERT on the two comparison tables. The test then observes SQLSTATE `42501` for the required row/table locks until it temporarily grants `UPDATE(id)` on `users`/`user_role_bindings` and table UPDATE on modules/registrations/placements. Those grants are test probes, not a deployment role contract. Copying them to an API LOGIN would grant mutation capability.
- `docs/SECURITY.md` preserves the ordinary API LOGIN's no-direct-Catalog-write boundary and the Governance composition-root boundary. Direct API grants for 0179 INSERT or UPDATE locks would contradict that accepted contract. The existing Governance writer cannot compose this operation: it has no Catalog, Cutover, Verification, or comparison-table grants.

## Recommended execution sequence

1. Before downtime, a valid local-auth Organization Admin session is created by the existing `/api/v1/auth/login` flow. The session is authentication only; it does not approve a run or waive any gate. OIDC/HMAC deployments are unsupported by this proposed seam and remain disabled. The Deployment Operator prepares the exact plan and its target artifact / Catalog Release pins.
2. The accepted P2 boundary stops API, worker, and web; stops proxy traffic; pauses and drains the queue; and proves zero leased work, zero business traffic, no application writer, and both legacy and candidate writer fences. S7 then continues only through the accepted one-shot maintenance process. No HTTP API is available during capture.
3. Immediately after `executeCutover` reports completed P10, the maintenance process preserves the completed P0-P10 run receipt/checkpoints, re-proves P2 isolation, and rereads the persisted run. It requires every P0-P10 checkpoint, including P2, P5/P7/P10, one complete v2 P7 manifest, stable source snapshot fingerprint, plan digest, target artifact SHA, Catalog Release ID/digest, and no live S7 run. The process obtains the trusted artifact SHA from the immutable deployed-package attestation, not a request or operator-supplied identity field. The completed-run receipt/checkpoints are evidence only; they are neither capture nor P11.
4. The Admin supplies the local session token through a no-echo terminal prompt. A proposed `wiseeff_mod_d02_source_reader` connection hashes it, verifies the exact `auth_sessions` row (including persisted creation, expiry, and revocation fields), and reloads the current active user, Organization, role bindings, and effective permissions. It must match the session's persisted user/Organization and grant Organization `admin` authority. This source-reader connection also runs the existing read-only MOD D02 provider; its allowlist must cover the provider's exact run/manifest, module/association, and Catalog source reads. The capture transaction receives the validated session ID and rechecks and locks the session, active user, Organization, and admin role until commit. It refuses expired/revoked sessions, inactive users, changed roles, cross-organization scope, or any missing pin. This seam is proposed and unavailable today.
5. The existing `provideModParameterCatalogComparisonCaseBatchV2` provider builds the scoped projection on the source-reader `Database`/root Pool. The current writer requires its `Database` and `pool` to resolve to the same root Pool and combines source reads with writes, so it cannot be called unchanged across the reader and capture logins. A proposed TypeScript split passes the generated batch to the dedicated capture function over the separate `wiseeff_mod_d02_capture` connection; in one transaction the function rechecks all pins and source inventory/associations under locks, then writes the case/result batch and audit atomically. Exact retry is a no-op; changed evidence under an existing identity fails closed. The receipt contains only the scoped projection digest, counts/checksums, and append/replay counts—no Archive payload, raw value, or claim that P11 passed. Close the capture transaction and connection before starting P11.
6. A separately operated, read-only P11 verifier then recomputes every required V01-V17 and D01-D09 check across all 11 consumer families against the same run, plan, artifact, Catalog Release, mapping epoch, P7 manifest, and source boundary. It independently recomputes D02; the writer's rows are inputs to inspect, not proof of themselves. The verifier and capture use distinct code processes and database identities.
7. P11 passes only at the accepted thresholds: zero `unexplained-difference`, zero `unqueryable/protected-reference-missing`, every protected reference enumerated, all 11 consumer families covered, and deterministic expected counts/checksums. The accepted P11/report approval flow may then advance to P12.
8. P12 binds both passing P11 report digests to the read-pointer switch. P13 retires legacy writers while services remain stopped. After P13, a **new** `post-retirement-runtime` attempt reruns the complete V01-V17 plus D01-D09 set, including V13/P02 writer-reachability and privilege negatives. Only that passing and approved post-P13 runtime pin permits candidate API verify-only startup; worker/web and isolated API/browser acceptance follow while traffic remains isolated.

The phase order preserves the accepted maintenance contract: no API/worker/web process is used for pre-P11 capture, P11 remains independent and mandatory before P12, and candidate API startup remains after P13 plus a fresh full P11 rerun. A successful MOD D02 capture alone is never a P11 result. Any missing session/auth seam, failed P2 proof, incomplete run/manifest, pin drift, provider error, ambiguous association, or P11 failure blocks progress and keeps traffic isolated.

## Proposed database call boundary — not current SQL or grants

The existing TypeScript writer cannot run safely under the formal API LOGIN today: direct Catalog active-Subject EXECUTE and 0179 INSERT are unavailable, and its SHARE locks require UPDATE privileges under PostgreSQL. The existing local API session resolver is not a read-only offline authentication seam because it updates `auth_sessions.last_used_at`. Neither new LOGIN exists today. Also, `provideModParameterCatalogComparisonCaseBatchV2` requires `Database` and `pool` to resolve to the same root Pool, and current writer composition couples those provider reads to its write transaction. The proposal therefore requires a TypeScript split: read/authenticate/build the batch using one scoped source-reader `Database`/Pool, then submit it to the separate fixed-function capture connection. The capture function must recheck and lock the relevant source/auth rows and pins in its own write transaction before accepting that batch; the source-reader and capture LOGINs cannot be collapsed. A new migration or runtime grant is **not** implied by this proposal.

Recommended implementation candidate: one atomic `SECURITY DEFINER` function, for example `parameter_catalog.capture_mod_d02_pre_activation_v2(...)`, owned by a new `catalog_mod_d02_capture_owner` role (`NOLOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOINHERIT`, `NOBYPASSRLS`). It receives the run ID, session ID, server-resolved principal and organization IDs, immutable manifest pins, and the TypeScript-produced batch/checksum. The proposed offline resolver must first verify the local bearer session and build the current `AuthContext`; only then may the maintenance process construct `createUserInvocation(auth)`. The function independently rechecks and locks the session, active user, and persisted Organization-admin binding, then relies on the 0179 deferred constraint/trigger for exact completed-run P7 selection binding. It atomically inserts the supplied evidence and audit fact. It does not authenticate the bearer token itself, run the HTTP resolver, or certify the TypeScript provider's semantic observations; only independent P11 does that. This entire offline auth-resolution seam is pending approval and implementation.

The function owner would receive only:

- `SELECT` on `public.users`, `public.user_role_bindings`, `public.organizations`, `public.roles`, `public.parameter_modules`, `parameter_catalog.organization_subject_registrations`, `parameter_catalog.subject_placements`, `parameter_catalog.parameter_catalog_cutover_runs`, `parameter_catalog.parameter_catalog_cutover_events`, `parameter_catalog.parameter_catalog_cutover_checkpoints`, `parameter_catalog.catalog_releases`, `parameter_catalog.legacy_identities`, and `parameter_catalog.legacy_mapping_versions`;
- `SELECT` on `public.auth_sessions` and `UPDATE(id)` on `public.auth_sessions`, `public.users`, `public.organizations`, and `public.user_role_bindings` only because PostgreSQL requires it for the exact `FOR SHARE` rows that bind the local session and persisted Organization-admin authorization until commit;
- table-level `UPDATE` on `public.parameter_modules`, `parameter_catalog.organization_subject_registrations`, and `parameter_catalog.subject_placements` only because PostgreSQL requires it for the existing `LOCK TABLE ... IN SHARE MODE` checks;
- `SELECT, INSERT` on `parameter_catalog.parameter_catalog_comparison_cases` and `parameter_catalog.parameter_catalog_comparison_results`, with no `UPDATE`, `DELETE`, or `TRUNCATE`;
- `EXECUTE` on the exact `parameter_catalog.assert_catalog_subject_active(text,text,text,text)` guard; and
- `SELECT, INSERT` on `public.audit_events` for one fixed capture event and exact-ID retry verification; no update/delete/truncate.

These lock-motivated UPDATE privileges belong only to the `NOLOGIN` function owner. The owner has no members and no login. Its `audit_events` SELECT is a table grant; the proposed definer body's fixed-ID lookup, not SQL row-level privilege, narrows its use. One separate `wiseeff_mod_d02_source_reader` LOGIN is used for local-session resolution and all provider reads because the provider requires one root Pool. Its proposed SELECT-only object set is `public.auth_sessions`, `users`, `organizations`, `user_role_bindings`, `user_password_credentials`, `roles`, `parameter_modules`, `parameter_module_mappings`, `projects`; and `parameter_catalog.organization_subject_registrations`, `subject_placements`, `current_project_parameter_bindings`, `parameter_catalog_cutover_runs`, `parameter_catalog_cutover_events`, `parameter_catalog_cutover_checkpoints`, `catalog_releases`, `legacy_identities`, `legacy_mapping_versions`, `catalog_state`, `catalog_subjects`, plus release-definition/kernel relations found in the pinned Catalog read path. This role has no RLS policy: it can read every row for each granted column, and organization filtering comes from the trusted maintenance process using the server-built `AuthContext`, not from PostgreSQL tenant isolation. The Admin never receives this credential. This is an explicit process trust boundary; if all-row column visibility is unacceptable, a separately designed restricted reader function is required. The exact provider/kernel column grants are not yet known well enough to approve: capture remains disabled until a query trace records every table/column and proves no omitted dependency. The eventual allowlist must include `roles(id, permissions)` and only `user_password_credentials(username)`; exclude `password_hash`, broad schema SELECT, writes, role membership, audit access, and `parameter_module_dismissed_compatibles` raw reads. Each source fact must be protected by the capture transaction's exact recheck/lock or capture must fail closed on fingerprint drift. Record source-reader `session_user`/`current_user`. The ordinary API runtime gets no comparison-table grants and no membership in the function-owner role. A dedicated `wiseeff_mod_d02_capture` LOGIN, provisioned as a separate connection used only by the maintenance capture step, gets schema `USAGE` and `EXECUTE` on this exact function only; it has no membership in Governance, Catalog, Cutover, Verification, or migration-owner roles. Inside the function require `session_user = 'wiseeff_mod_d02_capture'` and `current_user = 'catalog_mod_d02_capture_owner'`, and record those values with `rolsuper=false` and `rolbypassrls=false`. Revoke function EXECUTE from `PUBLIC` and every other role. Pin `search_path` to trusted system schemas (for example `pg_catalog, pg_temp`) and schema-qualify every non-system object inside the function.

The TypeScript writer must adapt to submit its produced batch through this one function call. In that transaction the function takes the existing `FOR SHARE` user/role locks and `SHARE` locks on modules, registrations, and placements, then rechecks the complete MOD inventory count/checksum, each locked module's `id/kind/origin/parentId/attributionSubjectId/sourceKey` against its case's legacy observation, and the exact Registration/Placement association. It inserts and verifies every case/result pair plus audit atomically, then forces the 0179 deferred constraint before commit; 0179 checks run/P7 selection binding but does not reject a case lacking a result. The function does not duplicate the TypeScript semantic provider or claim those observations are true. A detached preflight lock call followed by direct API DML is rejected: the locks are transaction-scoped and direct DML still fails `42501`. The independent P11 verifier remains responsible for source-boundary and semantic equivalence across all families.

The function itself owns the fixed audit insert. The existing TypeScript `withAuditedWrite` helper can share a `Database` transaction, but its ordinary audit INSERT would execute as the capture LOGIN, which deliberately has no direct `audit_events` grant. Its `public.audit_events` row uses the rechecked organization and user (`actor_type='user'`), fixed `app='release-verification'`, `kind='mod-d02-comparison-capture'`, `action='capture-pre-activation'`, `severity='Medium'`, `target_type='cutover-run'`, and `target_id=runId`; `trace_id` is a validated server-generated request ID. Metadata contains only stable manifest/projection and source-inventory digests, session ID, and case count. New/replayed counts belong in the call receipt, not the audit content checked on retry. A deterministic ID derived from length-prefixed organization, run, and request IDs makes the same request retry return the existing audit row only after reading it by ID and verifying all stable fields; changed evidence under that ID refuses. The local session token is never persisted or logged. Audit failure aborts the case/result transaction. This is a proposed new fixed-event definer routine, not the existing application audit helper or an already granted capability.

The SQL function receives principal, organization, and session IDs as values; PostgreSQL cannot verify the presented bearer token from those IDs. Only the offline maintenance resolver may validate the token and construct the trusted `AuthContext`; the function then rechecks the referenced session, active user, and persisted Organization-admin state under its row locks. Its lock closes the race with session revocation or role removal until commit. The session is not action-bound: its DB expiry/revocation state is authoritative, and the session may be replayed until then. ## Archive retention and rollback

Comparison evidence stores typed Archive IDs and mapping/manifest digests, never Archive payload bytes. Archive relations and objects remain append-only and follow the longest protected-reference, audit, business, and legal retention period. P16 cleanup and application rollback do not delete Archive or comparison history. If the maintenance step is disabled or rolled back, revoke the dedicated function EXECUTE grant and disable/rotate the dedicated connection secrets; retain 0179 and all committed case/result/audit rows. Do not apply a down migration or erase data to make an old binary appear compatible. The proposed migration is forward-only and additive; its exact version number is assigned only after approval.

## Remaining approval boundary

The single approval package is the proposed offline read-only local-session resolver, scoped auth/provider source-reader connection, split provider-to-capture composition, dedicated capture connection/function capability, and atomic audit path. The local session authenticates a reusable WiseEff account; it is not run-bound and does not prove physical-human presence. A run-bound one-time permit or literal human-assurance requirement has no current contract and would need separate approval. OIDC/HMAC deployments remain unsupported by this seam. The accepted independent P11 verifier remains a separate blocking prerequisite owned by its existing contract; the current self-hosted controller does not yet implement P11-P13. Approval or successful local tests alone does not authorize Hosted/target credentials, production invocation, P12, candidate API startup, or public release. Until the auth/capture package and role-faithful tests land, the v2 writer is a testable internal primitive and P11 remains a separate required gate.
