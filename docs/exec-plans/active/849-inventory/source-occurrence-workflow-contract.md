# T1.1 source workflow contract

> Chinese: [中文](../../../zh-CN/exec-plans/active/849-inventory/source-occurrence-workflow-contract.md)

Design candidate, not implementation evidence. Read with [the threat matrix](source-occurrence-threat-matrix.md) and ADR-0046's user-confirmed clarification. This specifies the source module interface so schema and workflow implementation share one ownership model.

## Source identity and entry points

The occurrence identifies a DTS node or a JSON configuration-instance root within an immutable file and config-set; it does not use a revision as identity. The exact parameter locator is separate: a DTS property occurrence/CST span, or a document-absolute escaped JSON Pointer. Root and parameter pointers both start at the document root. Containment compares decoded token arrays: the root tokens must be a prefix of the parameter tokens (including equality); never concatenate encoded strings or use a textual prefix. Decode and re-encode each token with `~0`/`~1` to obtain canonical pointers, preserving empty tokens. Its association with a Definition is explicit and reviewed, never inferred by display name, dotted-path splitting, or filename.

JSON import supplies the governed ConfigurationSchema identifier, root Pointer, and explicit Definition-to-Pointer mapping to the existing parameter-files candidate owner. The server checks the published pinned subject, active registration/placement, Definition ownership, file/config-set ownership and every pointer. It allocates the opaque instance identity only at the authorized persisted transition, reusing the same instance under the accepted immutable ownership tuple. A candidate cannot move current file/value pointers. Unknown Definitions or unresolved mappings remain blockers/observation evidence, not new definitions.

Existing DTS parsing and continuity remain in parameter-topology; use historical file-version IDs, exact property occurrences, CST spans/checksums and the accepted governed Definition mapping. A canonical-source adapter consumes those facts without another DTS parser. It must not route canonical mutation through legacy Binding/value owners. Retained legacy readers under TD-125 are outside this implementation's removal scope.

Only DTS and strict JSON enter this source workflow. Reject YAML, TOML and ENV before creating a candidate, active occurrence, Binding or ProjectValue; native negative tests assert no persisted active identity or current-pointer change.

## Minimal source module interface

The parameter-files owner exposes two source operations to the canonical workflow, with the existing Database/ObjectStore/trusted invocation dependencies:

1. **Prepare a pinned source change**: resolve an authorized canonical Binding and its immutable source pin; load bounded exact source bytes by file-version, validate size/digest/UTF-8, parse and resolve the exact locator, patch only the selected value, reparse and verify target/non-target semantics. Persist a server-owned object using the existing file-candidate owner and return its opaque candidate ID plus original/proposed digests and a reviewer-visible diff. This operation moves no current pointer. Submit stores that candidate ID, base/proposed byte digests, diff digest and complete base pins on the immutable submitted request. Candidate object/base fields become immutable while referenced by a submitted request; edits require a new candidate and submission.
2. **Commit an approved prepared source change**: inside the caller's audited transaction, revalidate authorization/provenance and load only the server-owned candidate referenced by the submitted request. Verify its bytes/digest, frozen locator, diff digest and all base pins; reject client replacement bytes, candidate IDs or locators at approval. Use the shared `commitCanonicalSourceRevision` boundary to acquire locks and compare every frozen member, insert immutable file/config revisions plus source pins, CAS current pointers and commit workflow/history/audit together. Return the exact new pin, never `skipped:true` for a required source.

Names/types may follow nearby module conventions. These are concrete ownership operations, not a second generic repository abstraction. Reuse file-version insertion, object storage, config-revision/member persistence, canonical append/history, trusted audit and existing DTS CST patch logic. Do not call a helper that silently falls back to latest revision, a pool outside the owned transaction, a memory object store, or a fake storage key.

The commit unit includes the verified file object, immutable file-version/config-revision/member rows, and a new immutable ProjectValue/source pin for every affected Binding, followed by each Binding's current-tip CAS and the immutable ordered request batch result/history/shared applied audit. File and Binding CAS belong to the same transaction. A source-only or value-only result is not success.

Every writer of a canonical-backed file's `current_version_id` is covered, not just review routes. Current writer inventory: `parameter-files/repository.ts:setCurrentVersion` and its upload/rollback (`service.ts`), candidate activation (`candidateService.ts`), baseline rollback (`baselineService.ts`) and generic writeback (`writebackService.ts`) callers; the two direct updates in `parameter-topology/overlayWriteback.ts`; canonical import/apply. `catalog-cutover/mapping/persist.ts` writes a legacy mapping head, not a source-file pointer. `parameter-files/configSetRepository.ts` membership moves/clears must also preserve referenced file identity. Route each affected pointer path through the shared sorted-lock/CAS boundary or explicitly refuse canonical-backed files before mutation. Do not migrate unrelated legacy consumers in this step. Native tests and a final writer search must prove no unguarded direct update remains; adding a canonical source must not silently enable an older writer.

The source object may outlive a rolled-back transaction; on failure it is an orphan/recovery diagnostic, not an applied result or cleanup authorization. Missing bytes or digest failures block preview/apply. The change-request ID is the idempotency key: one pending-to-approved transition stores an immutable ordered batch result with target and sibling-derived value/pin/version/revision/history IDs plus the shared audit. The unique target applied-event key prevents a second batch. After uncertain commit, authorize and re-read the stored result before retrying; replay adds no version/value/history/applied audit. Refusal/attempt audit is distinct from the applied event.

The writer inventory also includes the value side: `parameter-bindings/values/service.ts` append and `values/repositories.ts:casCurrentTip`, their protected-reference adapters, sync/import callers and any direct Binding-tip update. These low-level helpers may be reused **inside** the owned source transaction, not as independent value-only apply routes. Source-backed calls outside that unit are refused; deferred pin/current-tip constraints are a DB backstop, not a substitute for the source commit. Initial source materialization retains its existing separately authorized source/import owner and must atomically establish the real source revision and pin; it is not an escape for later edits. Placeholder creation is only transient within that atomic initialization, never a standalone current-value success. Native tests must exercise direct append/CAS bypass attempts as well as file-pointer writers.

## Frozen workflow and concurrency

- Drafts freeze Binding/Definition/release/current-value and source occurrence/file/version/config-revision/property locator pins. Store the original typed value without DTS/JSON coercion. A JSON tagged value is handled by the JSON source owner, not cast to `DtsValue`.
- Draft creation/edit/removal changes only pending work. Submit freezes the target and complete proposed source diff. Editing after submit requires a new submission; review never silently refreshes a stale diff.
- Review retains current project-scoped policy and independent submitter/reviewer separation. Authorize before both first apply and replay; an approved-state shortcut cannot disclose outcomes to a now-unauthorized caller. DTS sensitive-node checks use the exact pinned source/occurrence, not the latest logical-node revision. JSON remains software configuration and never reaches device overlay execution.
- Approval and apply remain the existing single atomic action, but must now include real source writeback. Reject/withdraw do not modify source/current values. A missing source/ObjectStore is an error, never a value-only success.
- `commitCanonicalSourceRevision` is the single source-current-version writer boundary for canonical apply and candidate/import activation affecting canonical-backed sources. All such paths must use its transaction/lock protocol; until adapted, candidate/legacy activation is refused for canonical-backed sources rather than advancing pointers independently. Acquire all affected config-set IDs sorted lexically, then all member file IDs sorted, then all Binding IDs sorted, then request IDs sorted; no writer reverses this order. Lock and compare the exact frozen set of `(config_set_id, file_id, current_version_id)` for **every** member, revision/member IDs and membership, Binding current-value/Definition/release pins, request state/candidate ID and base/proposed/diff digests. Config sets have no single current-revision pointer, so a latest revision lookup is not a CAS substitute. Perform comparison and all pointer updates in the same transaction. Concurrent unrelated member changes conflict rather than replacing the member with an older snapshot. Two requests at one base have at most one successful apply; the other must be re-prepared and reviewed. Opposing multi-config-set requests test global lock ordering.
- A new config revision retains untouched member version IDs and changes only intended members. Source rename uses immutable file identity; returned name is metadata and cannot select the source. JSON-only revision creation uses shared revision/member persistence without entering the DTS parser/toolchain; mixed sets preserve complete membership and let the DTS owner inspect only its own files.
- A source commit advances every existing source-backed sibling Binding in each affected config set, including Bindings on untouched member files. Under the same sorted locks, prove the same occurrence and exact locator still resolve and each non-target typed business value is unchanged. Append a same-value ProjectValue and new immutable source pin for each sibling, CAS its tip, and create exactly one complete revision per config set. Missing locators, changed identities or unexpected sibling values abort the whole transaction; never create or transfer Bindings to repair them. Older drafts/requests remain immutable but stale and require preparation/review again. The batch has one user approval and one applied audit, plus per-Binding history referencing that audit; sibling history is explicitly source-revision propagation, not another user edit. The request stores the ordered complete batch result for replay without additional appends. Membership additions/removals and changes to members without their own occurrence are subject to this same boundary or refused.
- Existing import-batch apply must stage canonical pending drafts/review work and report actual staged counts, never directly append current values or call the legacy writer. Stage the entire validated batch in one transaction: ambiguous rows or failed candidates leave no partially staged drafts/requests or applied batch status. Orphan pending objects may remain diagnostic only. Exact Binding/Definition mappings must already be resolved. A staged batch is not an applied source change; only approval through the shared writer can advance the source, and rejected/withdrawn rows do not count as applied.
- External reimport at a numeric instance-root Pointer does not prove continuity after array reordering. If enclosing-array structure/ordering changed, require explicit new-instance mapping; do not silently reuse an index-owned ID. An approved exact pinned scalar edit does not relocate the instance.

## Canonical property deletion amendment (2026-09-21)

The owner accepted completing canonical property edit/delete through the existing single software-review stage. This amendment governs the canonical source path; the older 0059–0063 topology contract still creates no replacement `parameter_binding_revisions` row for a deleted property. Neither path creates a replacement Binding or DefinitionRevision. Design review and implementation evidence are recorded separately in [the local closure record](local-closure-20260921.md).

A canonical delete has no target value. Its request contains `action: delete`, the reason and the existing base revision; the server derives DTS/JSON format from the exact owned base pin. Draft and request DTOs preserve action and pin-derived format after reload, including JSON deletes with no target value from which to infer format. Prepare and apply both read bounded, checksum-verified immutable ObjectStore bytes and repeat the deletion proof. Candidate, base/proposed/diff digests, complete member manifests, independent reviewer authorization and current-tip CAS retain their existing owners.

For DTS, use the existing CST writer to emit `/delete-property/`. Prove the old property span/raw value and enclosing node against the base pin, unchanged non-target source semantics, and the exact new revision/member/node/effect graph. The winning effect must be the unique maximum `source_order` for that logical node/property and must be a delete. Tied maxima fail; effect IDs cannot break ties. Reuse migration 0152's complete pinned-graph immutability and first-pin fence.

For JSON, extend the existing bounded span scanner to remove exactly one object member and its necessary comma, then reparse. Prove the old member/value, root and parent continuity, exact target absence and unchanged non-target bytes/values. Decode escaped and empty pointer tokens correctly. Deleting an instance root, array element, missing member, or an ancestor/descendant of another current Binding is refused. JSON `null` is a present value: an explicit delete may remove that object member, but `null` itself is never an absence marker.

Successful approval appends one immutable ProjectValue with `value_state=deleted` and one exact `dts-delete`/`json-delete` source pin linked to the original present pin and approved delete request. The retained old payload is historical context only. Source revision, current tip, pin, request result, history and applied audit commit atomically; any failure rolls back the database transition. Exact approved replay first reauthorizes and reproves the stored source result, then returns it without another append/history/applied audit.

Current projections and resolvers exclude deleted tips. Exact-ID/history/export responses expose `deleted` explicitly and cannot present the retained payload as an active value; the pre-delete present value and its original source export remain readable. Ordinary edits, imports and replay shortcuts cannot resurrect a deleted Binding. This delivery introduces no re-add/restore operation.

**Clarification of the sibling-propagation rule above:** “every existing source-backed sibling” means the present active cohort. A deleted Binding retains its terminal historical tip, original deletion revision, pin and history; later sibling commits do not append another deleted value/pin/history. Under the same sorted source locks, enumerate every retained deleted anchor in the affected config sets and prove it remains absent in the new exact bytes. Reappearance, ambiguity or invalid deletion provenance aborts the complete sibling commit. Advance the present cohort normally and preserve terminal deleted identity.

PostgreSQL enforces value-state/pin-kind agreement and tenant-complete base-pin/request/value/revision ownership. It cannot inspect ObjectStore bytes: the source transaction owns parser/absence and non-target proof, while deferred database checks bind the proof to exact immutable file checksums, candidate/request digests and the applied result. Previous migrations, source identities, authorization and audit constraints remain unchanged.

## Approved DTS continuity

For an approved DTS patch, logical continuity uses the exact submitted base revision, never the latest parsed revision or a fabricated reviewed mapping. Preparation and apply both prove that the old pin is the unique final active property effect, non-target CST semantics and non-target member byte digests are unchanged, and the target member's before/after bytes match the frozen base/proposed digests respectively. The DTS owner compares the complete node cohort, including locator, name, unit address, compatible, reg and parent identity; any added/deleted/changed node aborts. Existing logical IDs survive only under this proof. Each new revision receives new property/node occurrence IDs and freshly resolved source pins; “same locator” means the same semantic target, not reusing old occurrence IDs or offsets. Generic external-import identity matching remains unchanged.

## Reopened source-value proof design

Design status: the concrete amendment below received independent Spec and Standards design PASS on 2026-09-17. The following freeze/proposal statements record the gate that preceded that approval; implementation must obey the amendment, and no implementation acceptance is implied.

The second P1 repair cycle reopens the R3 design gate. Migration-adapter and Definition-replacement production changes stay frozen until independent Spec and Standards reviewers approve this section and its threat cases. Earlier implementation/test results do not approve this proposal.

**Authoritative proof, not caller agreement.** Neither a supplied payload nor persisted `dts_property_occurrences.raw_text` alone proves the source value. The 0151 immutability trigger protects a property only after a source pin references it; an unpinned replacement target can still differ from stored object bytes. Both callers must derive the value from the exact bounded immutable file-version object and cross-check the persisted occurrence/CST facts. Missing storage is a hard refusal, never a database-only fallback.

**Concrete owner interface.** Reuse the bounded read, SHA-256/size and fatal UTF-8 checks in `parameter-files/canonicalSource.ts:loadCanonicalSourceSnapshot` as a concrete exact-file-version read operation in the parameter-files owner. It resolves storage metadata from the supplied transaction and verifies Organization/Project/config-set/file/version ownership; callers cannot supply storage keys, checksums or source text as authoritative evidence. The existing snapshot loader and new pre-pin proof reuse that implementation. The parameter-topology owner exposes an exact DTS property proof taking the same transaction, ObjectStore and explicit Organization/Project/config-set/revision/logical-node/file/version/property tuple. It verifies one exact revision member and frozen alias, a resolved owned revision, the matching property/node and one unique final set/override effect (consider deletes and tied orders before selecting the winner). It reparses the verified bytes with the existing DTS parser, matches the stored property name/span/raw text and enclosing node span/identity, and returns the existing lossless `DtsValue` plus exact identity/object digest. No new parser, generic query wrapper or fabricated canonical pin is introduced. The Binding/value owner reuses `dtsValueToPayload`, `serializeContract` and `digestProjectValuePayload` for exact typed-value comparison and persistence.

**Transaction and stability.** Use a caller-owned transaction, never a pool read between checks and writes. For all affected projects acquire config sets lexically, then member files lexically, then canonical Bindings lexically before migration/replacement mutation. Lock the exact source revision and relevant member/node/property/effect rows through commit; guard against new conflicting effects/members as well as row updates, using the parent revision lock and foreign-key locking contract. Re-read the unique final-effect/identity proof after locks. The reviewer must verify that every relevant mutator participates or is blocked by those locks; an unproven writer/phantom path is a design blocker, not permission to assume immutability. Source-object mutation/deletion is detected by bounded checksum reads at preview and apply; source objects are never overwritten by this operation. Legacy-row verification and preserved Binding-ID behavior remain required inside the transaction.

**Legacy mapping.** Treat `command.source.payload` only as a claim. Before creating a Binding/value/pin, compare its complete typed payload with the server-derived proof and refuse on disagreement. Persist the server-derived payload, not the claim. Existing-identity replay must reprove ownership, exact source and equivalent current value; it cannot bypass the check. Unsupported JSON in this DTS legacy seam remains refused rather than synthesizing a DTS identity. Inject the real ObjectStore through the migration adapter dependency, not through a caller-provided trusted flag.

**Definition replacement.** Preview derives the exact target payload/digest from bytes, requires equality with the old canonical typed value/digest, and freezes that proof together with the old current-value ID and exact locator/member/object digest. A rename is source-preserving, not a business-value edit. Apply repeats the exact proof under locks, compares all frozen evidence and the old-tip CAS, and only then creates replacement identity/value/pin/history. Source value `9` versus old canonical `5`, missing/unparseable bytes, changed digest/span/final effect or stale tip blocks the affected project without identity/value/pin/history/retirement mutation; existing blocked-attempt records remain permitted. Wire the already-owned application ObjectStore from `server/app.ts` through `parameter-catalog-api/productionWire.ts` to `DefinitionReplacementServiceInput`; unavailable storage refuses preview/apply. Publication policy and source-first key-cutover rules do not change.

### Concrete amendment after both NOT PASS design reviews

This amendment replaces any less-specific interface/locking statement above; it remains proposed until both reviewers re-review it.

1. **Pre-pin read and acyclic ownership.** Add the concrete operation `loadExactSourceRevisionForProof(tx, objectStore, { organizationId, projectId, configSetId, configRevisionId, fileId, fileVersionId })` in `parameter-files/sourceVersion.ts`. It works before a Binding/value/pin exists. It loads the exact owned revision/member/version graph from that transaction, requires the selected file/version exactly once, and returns the complete frozen manifest plus each member's verified bytes, size, checksum, immutable alias and identity. No storage key/checksum/source text/alias supplied by a caller is authority. Reuse the existing bounded-read implementation, rather than calling the pin-only loader. This file depends only on shared DB/errors, ObjectStore types, existing source size constants and pure manifest normalization; it must not import canonicalSource, sourcePropertyProof, Binding owners or a topology writer. `parameter-topology/sourcePropertyProof.ts:proveExactDtsProperty(tx, objectStore, exactIdentity)` consumes this operation. `canonicalSource.ts` also consumes sourceVersion; topology never imports canonicalSource. Lossless payload conversion stays in the Binding owner. No new dependency or generic storage/proof interface is needed.
2. **Exact include/overlay origin.** Load every frozen member and resolve the pinned entry/include-search-path/overlay-order manifest with the existing `resolveDtsConfigSet`. A legal `&label` ref-path is not necessarily the resolved logical-node path. Extend that resolver's existing expansion segment/source-chain metadata only as needed to retain immutable file-version and original source offsets, including include-segment origin offsets. Never equate the two paths by string or select an occurrence by same name/raw value. Match the final resolved effect's original file/version/property span to the persisted property and its enclosing CST node, and match the resolved node to the requested logical-node revision. Check the full ordered target source-chain against persisted effects, including deletes and duplicate/tied orders; changed or missing origins refuse. Reject unresolved/dangling/duplicate labels, missing/cyclic includes, cross-member target spans and ambiguous origin mappings before writes. Reuse this exact-origin matching in the ingest owner for canonical proofs instead of its permissive name/raw fallback; unrelated retained legacy matching stays outside this change. Preserve existing span units (UTF-16 string offsets), never reinterpret them as UTF-8 byte offsets. Compare the parsed lossless `DtsValue` structures from verified CST and recorded raw text first, then derive ProjectValue payload/digest; large cells, groups, arrays and non-scalars never undergo lossy numeric conversion.
3. **Bound the complete proof.** Existing per-member maximum remains 2 MiB. The proof operation also preflights at most 128 members and 32 MiB total stored bytes; resolution refuses before exceeding 32 MiB expanded UTF-8 bytes, 64 include levels, 100,000 visited syntax/source-chain entries, or 8 MiB aggregate locator/origin metadata. Repeated includes consume the expansion budget each time. These are explicit refusal ceilings, not truncation or permission to omit members. Record a stable source-proof-limit error and leave all pointers unchanged. Limits belong to this exact-proof entry, not a capability-version change or a new configurable framework.
4. **Exact lock order and phantom fencing.** Discovery reads select lock targets only; they are not proof. In the one apply transaction, acquire rows by this rank and lexically by ID within each rank: config sets → member files → file versions → config revisions → revision members → logical nodes → logical-node revisions → node occurrences → property occurrences → effects → legacy Bindings → canonical Bindings → current ProjectValues/pins → previews → replacements → replacement-project rows → change requests → operation idempotency rows. Include the complete relevant source graph, not only the selected property. Use explicit `FOR UPDATE NOWAIT` for potentially competing existing rows and return a retryable conflict on lock contention; never wait while holding a suffix then acquire an earlier rank. Re-read the complete discovered membership/ID set after locks and refuse if it changed; do not add newly discovered earlier-rank locks. Parent config-set/file/version/revision/logical/node row locks block new child inserts through the actual FKs in migration 0048 and subsequent composite constraints; row locks protect updates/deletes of already-existing children. Validate this behavior with two connections, including inserts already in flight before discovery. No table locks or broad role grants are added.
5. **Writer inventory and state phases.** Relevant writers are topology repository revision/member/node/property/effect inserts/status updates via `ingestService`; logical remapping in `bindingService`; file-version creation in file repository, `overlayWriteback` and `editService`; revision status in parameter-drafts repository; project revision deletion in projects repository; and property-key rewrite callers that activate new file/config versions. Existing canonical source/current-pointer fencing remains. A writer touching this graph must use the same order, hit the locked FK/row and cause the proof's NOWAIT conflict, or refuse canonical-backed mutation; no assertion that config-set locks alone serialize all writers. The implementation writer inventory and two-connection evidence must establish which of these holds for each path before PASS. Preview proof runs in a transaction too. Replacement reservation/publication/finalization retain their existing separate phases: never hold source locks over publication/network work, and never acquire source locks in a reservation transaction already holding workflow/idempotency locks. The apply phase reacquires source locks in the order above, then locks/rechecks workflow state and the exact manifest/current release before proof/mutation. Concurrent continues with different idempotency keys converge under replacement/project row locks; completed rows return their stored outcome without another append/history/applied audit. Post-publication source drift blocks project application, not an invented rollback of an already activated Catalog release.
6. **Executable dependency/transaction wiring.** Change the migration adapter to `mapLegacyBinding(tx: Queryable, objectStore: ObjectStore, command)`; its caller owns BEGIN/COMMIT/ROLLBACK and must use the existing atomic owner, not autocommit. A refusal after tentative writes must roll back the whole unit. Thread the application store through `app.ts → registerParameterCatalogApi → createGovernancePorts → createParameterCatalogMigrationService`, with a required `objectStore: ObjectStore | undefined` field in the service input. Unconfigured storage may retain unrelated read routes, but preview/apply fail closed before source-dependent writes. All integration callers/harnesses supply the real local ObjectStore with real version objects and independently expected bytes; no memory-store success proof, bypass flag or invented source metadata. Both operations call the same topology proof within their actual transaction. The store is a server dependency, never a command field. Exact replay revalidates the existing Binding/current pin/current value against the same derived source digest and typed payload; any mismatch refuses without an append/history event. No current-value reset or force replay is allowed.

## Strict JSON source format

Use the existing 2 MiB upload limit, plus maximum nesting 64, a 100,000-token/container-entry budget and an 8 MiB aggregate locator-text budget; fail before building unbounded structures. The locator budget bounds repeated long prefixes even when input bytes and token count are small. Reject invalid UTF-8, NUL/unpaired-surrogate characters in **all decoded strings (keys and values)** unsupported by PostgreSQL text/JSONB, comments, trailing commas, malformed literals/escapes and duplicate **decoded** object keys. Test both proposed target strings and unrelated source strings, before candidate staging. A bounded scanner records value spans and duplicate-key sets; native JSON parsing still owns grammar/value decoding where possible. No dependency is required solely to support this format.

Accept exact JSON scalar kinds, objects and arrays. Values that cannot survive the native JSON/ProjectValue round trip without numeric change are explicitly refused, not rounded. Compare normalized decimal/exponent text with the round-tripped number; leading/trailing insignificant zeros and exponent spelling are not numeric changes. Preserve finite decimals such as 0.1 and 36.5; reject integer precision loss, overflow/underflow and negative-zero loss. DTS cells keep their lossless typed/raw representation; no `Number(...)` coercion may silently lose precision or cell shape.

Pointers are empty for document root or start with `/`; decode only `~0` and `~1`, preserve empty/Unicode/dotted keys, and use own properties only. For arrays accept only canonical decimal indices `0|[1-9][0-9]*` within bounds, never `-`, negatives, leading zeros or an implicit append. A literal object key named `01` is still legal. Prototype-like keys are data; never traverse inherited properties or assign through a prototype setter.

Patch the exact recorded value span, not a split slash path. Reparse the result with the same strict owner and prove target equality and non-target semantic equality. Preserve unrelated source bytes whenever the span patch permits it. Any serialization change appears in the frozen source diff, including formatting/key-order changes. This JSON source parser does not widen Catalog capability v3 or implement v4 array schema semantics.

## Exact export and accepted evidence

The implemented HTTP seams are `GET /api/v2/projects/:projectId/parameter-bindings/:bindingId/export?projectValueId=...` (omit the value selector for the current tip) and `POST` on the same Binding's `/reimport-preview`, accepting the full export item. Export metadata comes from the selected immutable value/history, not the current Definition head. Reimport preview compares the complete package against persisted ownership and byte evidence, reparses its exact target and verifies the stored typed value. It is read-only validation, not application of a changed external file; altered manifests/bytes require explicit new mapping or the reviewed edit workflow. UI downloads retain the full identity package even for one source file.

The existing import-batch `/apply` URL now returns `status: staged`, `summary.staged` and per-item immutable candidate/base proof without setting `appliedAt`. Only changed, explicitly resolved rows can stage. Exact retries validate that the same actor's original draft and candidate still exist and match both frozen manifests and stored bytes; a removed, consumed or edited draft returns conflict and is never silently recreated. Initial JSON registration validates every member's bounded bytes; a mixed DTS/JSON set must already have one exact complete resolved DTS revision, and its entry/base/alias manifest is checked before registration.
