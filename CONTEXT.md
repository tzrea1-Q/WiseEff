## Glossary (stub)

Expand lazily via `/domain-modeling` when terms are resolved. Prefer terms from `docs/design-docs/domain-model.md`.

| Term | Meaning |
| --- | --- |
| DTS | Device tree / parameter topology source format in the parameter workbench |
| Parameter surface | Manageable parameter rows bound to topology, not raw DTS paths alone |
| Project-primary DTS | One uploaded DTS per project; merges update that file |
| Catalog subject | Permanent Platform-owned formal identity that is exactly one Driver, NodeType or ConfigurationSchema ([ADR-0045](docs/adr/0045-configuration-schema-subject-and-seed-rebuild.md)). Its canonical key is never reassigned, and it has no independent current lifecycle; Organizations use it through registration and placement. _Avoid_: attribution subject (legacy storage term), organization-owned subject, current subject row |
| Driver | A Catalog subject recognized by a unique authoritative `compatible` match and carrying Driver-only nature/cardinality facts. It is a sibling of NodeType, not its parent; any organization taxonomy nesting is placement, not catalog identity |
| Driver nature | Closed Driver fact: `physical-device` or `logical-service` |
| Driver instance cardinality | Closed Driver fact: `multiple` or `singleton-per-project` |
| NodeType | A Catalog subject recognized by canonical node name only when no Driver matches. It is a fallback formal owner, not a weak Driver or an observed module label, and has no family classification |
| ConfigurationSchema | A Catalog subject that owns a software configuration contract and is selected by an explicit governed configuration-model identifier. It is independent of file format, business taxonomy and device compatible selectors |
| Configuration instance | One project-owned occurrence of a ConfigurationSchema in a particular source file, config-set and root location. Source revisions or renaming the same file do not replace it; changing its file, config-set, model or root creates a distinct instance without automatically transferring values/history ([ADR-0046](docs/adr/0046-source-occurrence-identity-spans-dts-and-software-configuration.md)). Distinct instances may use the same definitions with different values |
| Canonical compatible selector | A validation-only, byte-preserved ASCII `compatible` identity accepted by the S0-ID constructor; no normalization or wildcard inference |
| Canonical node name | A validation-only, byte-preserved ASCII formal node identity; `/` is the root token and unit addresses are not part of the identity |
| Canonical property key | A validation-only, byte-preserved ASCII property identity after structural DTS keys are rejected; it is never inferred from display text |
| Catalog release | One immutable complete as-of publication of every previously published Catalog subject and alias plus definition content. Authoring may be a typed in-product ChangeSet, controlled YAML import, or historical repository bundle; only the compiled Catalog Release is materialization input. Omission is not retirement; active/retired state is explicit in that release |
| Catalog release subject | The immutable membership of one Catalog subject in one Catalog release, stating that release's active or retired lifecycle plus selector/tombstone provenance. Current status comes only from the current Catalog release; replay uses its pinned release |
| Catalog subject alias | Permanent ownership of one constructor-validated, byte-preserved external selector by one Catalog subject. Whether the alias is active or retired is stated independently in each immutable Catalog release and it is never reassigned |
| Catalog release synchronizer | The sole steady-state materializer of Catalog subjects, release memberships, aliases, Parameter definitions, and Definition revisions from a published immutable Catalog release. Proposal, ingest, review, HTTP, and ordinary application services have no parallel write path |
| Catalog ChangeSet | Typed authoring intent (create definition, create subject, revise definition). It is not a Catalog release and cannot be matched or ingested until a successor release is activated |
| Catalog publication candidate | Immutable frozen Artifact plus predecessor pin, identity allocation, impact report, and capability contract. Draft edits after freeze require a new candidate |
| Catalog activation receipt | Immutable synchronizer-written proof, committed with pointer/heads, that a job/authorization/release tuple actually activated. Proposal `accepted` and job `queued` are not this proof. A one-time `adopted-preexisting` proof covers Catalogs installed before the control plane |
| Catalog kernel | The routes-less deep module that turns one published immutable Catalog release into verified current or pinned catalog snapshots and is the only steady-state seam allowed to materialize catalog structure. Callers consume its typed results and never coordinate catalog tables, revision heads, aliases, transactions, or cache repair. _Avoid_: catalog repository facade, schema loader (too narrow), runtime repair service |
| Catalog snapshot | An immutable, verified read model of one exact Catalog release, carrying its opaque release identity and digest. Current snapshots are selected only by the current release pointer; pinned snapshots replay their named historical release without current aliases or lifecycle. _Avoid_: latest registry, mutable cache, organization overlay view |
| Parameter definition | The reusable Platform property-contract identity declared by one Catalog subject and permanent property key. It carries a stable opaque ID and one explicit revision head, not mutable content. It is never created from DTS evidence, a value, an Organization override, or Proposal acceptance |
| Definition revision | An immutable complete snapshot of one Parameter definition's persisted content, including documentation. Every content change creates a revision; exactly one is the definition head even when retired. Documentation-only head changes do not require Binding or Project value cutover. _Avoid_: ParameterSpecVersion (legacy storage term) |
| Definition proposal | Pending governed intent to change the Platform catalog. Acceptance produces or approves publication intent, a repository change, or a Candidate-bound authorization; it never directly materializes a Definition or Definition revision. _Avoid_: draft definition, provisional definition, accepted revision write |
| Parameter observation | Immutable evidence that a property occurred on one project logical node/source revision. It may gain one accepted match or require review; it never creates or becomes a Parameter definition |
| Subject registration | One Organization's durable `(Organization, Catalog subject)` declaration, created explicitly or by a uniquely proven match. Its lifecycle is active or retired; in either state it owns no schema/definitions and references exactly one retained Subject placement |
| Subject placement | The exactly-one retained authoritative Organization taxonomy node of one Subject registration. Rename/reparent preserves its ID; observed usage and Binding are separate, and retirement never deletes it |
| Binding | Stable association between one project source occurrence (a logical node or configuration instance), one matched Parameter definition, and the Organization's Subject registration. Placement and values are separate; `module_id` is not identity. Its effective Definition revision changes only through governed semantic cutover |
| Project value | An immutable configured-value fact under one Binding, interpreted through an exact Definition revision. Project-specific values never redefine the Platform property contract |
| Seed definition set | Reviewed reusable parameter contracts supplied for explicit initialization. It defines available parameters and their meaning, not a project's configured values |
| Seed project configuration | The initial source configuration and parameter values assigned to an explicitly selected example project. Different projects and node occurrences may use different values under the same definition |
| Offline parameter archive | Preserved former parameter records and source versions outside the current online parameter workflow. An archival reference identifies where authorized historical retrieval is available; it is never an editable current parameter |
| Definition retirement | Reversible unavailability for new use that preserves the definition's stable ID, permanent subject/property unique key, current revision, history, Bindings, and Project values. Restore reuses the same identity |
| Parameter draft | A user's staged pending change (binding value or node enablement) held in `parameter_drafts` between editing and submission. Editing writes drafts, submission/review reads them, so the staging area is a standalone module (`server/modules/parameter-drafts/`) both workflows depend on (ADR-0028) |
| Xiaoze | WiseEff Agent assistant surface in the product |
| Parameter admin | Governance surface for parameter specs, review queues, module/driver mappings, project files, config sets, and baselines. Does not own everyday binding edits |
| Parameter workbench | Everyday surface where users read topology and propose binding changes. Does not own governance queues or catalog upkeep |
| Organization | An independent collaboration and data space, normally representing one company or deployment customer. Departments and teams are internal groups, not separate Organizations. _Avoid_: tenant (as a product noun), department, team, 硬件部, 软件部 |
| Organization provisioning | Establishing an Organization and designating its initial administrator; a platform-administration responsibility. Distinct from admitting a member to an existing Organization |
| Member admission | An Organization administrator's decision to admit a person to that Organization, through invitation or direct addition. Distinct from creating an Organization or assigning project duties |
| Organization administrator | A member responsible for managing one Organization's members, projects and business assets. An Organization may have several equal administrators who can arrange succession; this is not a unique owner or a platform-wide role |
| Invitation | An Organization administrator's offer for a person to join that Organization. An invitation may be accepted once, revoked or expire; an unaccepted invitation is not membership |
| Member handover | Reassigning a departing member's outstanding duties and work while preserving the Organization's business assets and history. Disabling the member's access does not wait for handover completion |
| Account transfer | Moving an account's sole Organization membership to another Organization, with new permissions. The source Organization's projects, knowledge and history do not follow the account |
| Organization suspension | A reversible pause of an Organization's business activity. Members retain previously permitted read access, while new business writes, integrations, tasks and device operations are unavailable |
| Organization erasure | Permanent removal of an Organization's own accounts, business data and files, excluding platform-shared Catalog definitions. It finishes only when cleanup is complete and retains a minimal platform deletion receipt |
| Home organization | The single Organization an account belongs to. A platform administrator's choice of Operating organization does not change that membership |
| Operating organization | The Organization whose data and resources are the scope of an operation. It is the Home organization for an ordinary user, or an explicitly selected Organization for a platform administrator acting under their own identity ([ADR-0051](docs/adr/0051-organization-provisioning-and-member-admission.md)). _Avoid_: impersonated organization, second membership |
| Team | A flat grouping of members within one Organization; a member may belong to several Teams. Team membership alone does not grant project permissions. _Avoid_: Organization, department hierarchy, permission role |
| Authenticated principal | The user whose verified identity, Organization, roles, and permissions authorize an operation and remain accountable for it. A user bearer credential proves this principal; it does not prove that a human, rather than software holding the credential, is physically present. `AuthContext` represents this principal, not the operation's execution source |
| Invocation initiator | The server-trusted source through which one operation executes: user, Agent, or system. It is distinct from the authenticated principal: an approved Xiaoze action remains Agent-initiated while the approving user remains the accountable principal. A request header, body field, ordinary user bearer credential, or audit row cannot self-assert the initiator. System is unattended and never counts as human merely because it is not an Agent |
| Trusted invocation context | Server-internal per-operation provenance, derived only from a server-known execution path and propagated unchanged through nested domain writes and their audits. User and Agent invocations pair their initiator with the authenticated principal; a system invocation names its service/job identity and never invents a user. Sensitive mutation paths require this context explicitly, and absence never defaults to user. It is not returned by `/me` or accepted from request headers/bodies. WiseEff promises honest provenance for paths it recognizes, not detection of arbitrary software directly using an ordinary user credential. External Agent credentials are not a current product surface |
| Human-required operation | A mutation whose policy accepts only a user-initiated trusted invocation. Agent and unattended system initiators fail closed even when they carry an otherwise authorized user or service context. This is an execution-source policy, not proof that a physical human is present behind an ordinary user credential |
| Organization administration | 「组织管理」— operating an Organization's membership, onboarding, teams and settings. Distinct from platform Organization provisioning and from the business-specific Organization-scoped governance consoles. _Avoid_: 组织治理, organization governance (ambiguous) |
| Organization display name | The mutable human label of an Organization. Identity stays on `organizations.id`. Not a slug, department, or Role discipline |
| Evaluation Organization | The Organization local self-registration joins. In the seeded local profile that row is ChargeLab (`org-chargelab`). Not a second kind of Organization. _Avoid_: 硬件部, 软件部 (retired join targets) |
| Organization membership | Belonging to one Organization. It is not access to a project and does not imply a project-scoped role |
| Project member | An Organization member's explicit participation in one Project, whose project role determines their editing rights. It is distinct from being able to view the Project and from holding a Project review duty. _Avoid_: Organization member, reviewer (as a synonym for every participant) |
| Project review duty | A person's responsibility for a review or merge stage in one Project's change workflow. It is configured separately from Project participation. _Avoid_: project membership, organization role |
| Organization-scoped governance | Parameter assets governed independently of any single project: specs, module trees, business categories, policy targets. A catalog-scope axis (ADR-0001), not the Organization administration product |
| Role discipline | The hardware or software side of a platform role (`RoleDiscipline`). A property of the role, never an Organization. Local registration labels 硬件部 / 软件部 were a department-as-tenant accident, not this term |
| Project-scoped operations | Parameter assets owned by one project: files, config sets, release baselines, bindings |
| Project configuration workbench | The project-scoped operational surface where Admins manage source files, configuration composition, release state, and file conflicts in one project context. Distinct from the everyday parameter workbench, which is organized around reading and proposing parameter changes |
| Config set (UI: configuration / 配置) | A project-scoped, buildable composition of parameter files with a purpose and order for each file; a release baseline freezes their versions. Each project file belongs to at most one configuration, and files without an assignment remain outside its working configuration |
| Config file (配置文件) | A project parameter file assigned to a configuration with its purpose and order; this file membership is distinct from project users |
| Working configuration | The current member-file versions of a config set. It is the mutable source state inspected and changed in the project configuration workbench and becomes releasable only after a release baseline snapshots it |
| Candidate file version | An uploaded file version that has been parsed and compared but has not been activated into a config set's working configuration. Uploading creates a candidate; explicit activation changes the working configuration |
| Structured DTS edit | A property-level source change addressed through parsed DTS identity and submitted through the governed change-request flow. It is distinct from replacing or freely rewriting an entire source file |
| Release readiness | The derived blocking-and-warning state that says whether a config set's working configuration can be snapshotted or released. It summarizes member/version completeness, local edits, file conflicts, validation diagnostics, and publish-blocking governance tasks |
| Catalog release verification | The independent, deterministic, purpose-ordered proof that one exact application artifact, Catalog Release, database state, target, and recovery boundary satisfy the gates executable at each release phase. It produces immutable purpose-scoped reports with explicit lineage; it never migrates, synchronizes, repairs, approves, starts traffic, or claims later evidence early |
| Verification purpose | The closed release act whose exact phase determines gate applicability and approval authority: pre-activation, post-retirement runtime startup, isolated candidate acceptance, public release, legacy-read sunset, or P16 cleanup. Evidence or approval for one purpose cannot authorize another |
| Release Verification Report | An immutable, digest-addressed, purpose-scoped aggregate for one exact verification plan and phase snapshot. It passes only when every gate required now passes; gates executable only at a later purpose remain explicit successor obligations, and predecessor evidence can be referenced but never presented as newly executed |
| Pre-activation report | The report that proves the exact candidate pins, Catalog and migration state, initial full database/comparison verification, Recovery point, and pre-switch writer fence before the application read switch. Live candidate API and browser evidence are not yet executable and are never marked passed in this report |
| Post-retirement runtime report | A new report produced after the application read switch and permanent legacy-writer retirement by rerunning the complete database and comparison verification, including writer-reachability and privilege negatives. It is the only report Runtime readiness may consume for candidate startup |
| Isolated candidate acceptance | Real candidate API and browser verification performed only after the post-retirement runtime pin passes, while queue, proxy, and public traffic remain isolated. Any business mutation permanently closes pointer-only rollback; acceptance alone authorizes no traffic |
| Public-release report | The purpose-scoped report that aggregates exact pre-activation, post-retirement runtime, isolated candidate API/browser, target, recovery, and observability evidence. Only its distinct Operator and Platform owner approvals authorize queue, proxy, and public traffic |
| Runtime readiness | A verify-only statement that a running artifact and its dependencies still match the latest approved Post-retirement runtime report after legacy-writer retirement. It is distinct from Catalog release verification and public-release approval and never performs migration, Catalog synchronization, legacy repair, or fallback |
| Recovery point | One verified, same-boundary manifest for PostgreSQL, configured object storage, and durable Redis, including exact storage identities, checksums, and restore proof. A partial cross-store snapshot is not a Recovery point |
| Legacy retirement | The staged removal of legacy structural write reachability, then public read compatibility, then legacy code and schema after the evidence window and recovery dependencies end. It never deletes Audit, Archive, mappings, Catalog history, Definition revisions, Bindings, Project values, Proposals, Observations, or Review evidence merely because they are no longer current |
| Legacy lookup identifier type | The seven public compatibility lookup kinds exposed to authorized API callers; distinct from the internal migration source inventory |
| Legacy mapping source kind | One of the 49 closed internal cutover-ledger source kinds used to classify and map legacy evidence; never a public lookup discriminator |
| Release baseline | The only release unit in WiseEff: a snapshot pinning every config-set member to a file version, moved `draft → released` by an Admin. Builds and devices consume DTS files, so releasing happens at the file layer. Releasing, rolling back, and removing a config-set member each require an explicit confirmation stating the blast radius |
| Conflict arbitration | Deciding which side wins when a file sync and a UI draft changed the same parameter. The workbench Conflicts dock compares the shared base with the file/candidate and pending UI values (source-located); both outcomes carry equal weight, confirmation may record an audit reason, eligible bulk resolve needs an impact preview, and open conflicts block Candidate activation |
| Config revision | A derived read model of one parsed file version, never a releasable artifact. Its statuses describe ingest, identity mapping, validation, and review readiness only; a revision is never published |
| Identity mapping task | Read-only historical evidence of a migration-time identity or continuity choice. Legacy resolve/reopen is retired; validation, ingest, readiness and governance do not produce new tasks. A prior-logical-node choice has no canonical Review Queue equivalent and needs an explicit canonical decision, never name-based auto-resolution. Historical outcomes remain readable (ADR-0033). |
| Spec review task | Read-only legacy governance evidence. Only an exact unresolved typed mapping may adapt to a canonical Review Queue item; legacy resolve is retired. |
| Parameter spec lifecycle | A parameter definition's governance state: `draft`, `active`, or `deprecated`. Stated for the definition as a whole, never per version. Edges are activate (`draft → active`), deprecate (`draft` or `active` → `deprecated`), and restore (`deprecated` → whichever state the definition had reached before it was deprecated) |
| Spec deprecation | Soft retirement of a parameter definition. It stops being selectable when resolving a spec review task and leaves the default library view, but stays releasable for DTS parsing so no project loses parse coverage as a result of a governance action. Deprecating never rewrites project data. Contrast with overlay retirement |
| Overlay retirement | Withdrawing a driver schema overlay from the schema registry. Unlike spec deprecation this does remove parsing capability, so compatibles that relied on the overlay become parse uncovered. Surfaced as 停用解析, never as 废弃, because the two governance acts have opposite consequences |
| Deprecated-definition reference | A binding pointing at a deprecated definition. A reported state rather than an error: parsing is unchanged, and the product shows the reference count so an Admin can decide whether a successor definition is needed |
| Node enablement | Whether a logical node instance is itself enabled, derived only from that node's own DTS `status`: absent, `ok`, or `okay` means enabled; anything else means disabled. The subject is the node instance, never the driver module — two instances of one driver are enabled and disabled independently. Not a parameter: it never enters the spec library or the spec review queue |
| Node reachability | Whether an enabled node can actually be probed, which additionally requires every ancestor to be enabled. A node can be enabled but unreachable because an ancestor bus is disabled; the product reports the blocking ancestor rather than restating the node as disabled |
| Enablement override | An overlay's explicit statement about one node's enablement. Three states: inherit from base, force enabled, force disabled. Inherit means the overlay carries no `status` for that node |
| Non-standard enablement value | A DTS `status` value that is neither `ok`/`okay` nor `disabled`, such as `reserved` or `fail`. Treated as not enabled, but its original text is preserved and one-click toggling is refused so the author's intent is not silently overwritten |
| Runtime mode | Whether the frontend reads live APIs or mock fixtures. Both serve the same semantic product model; mock is a data-source substitution, never a different product. Server authentication, trusted invocation provenance, and other production security boundaries are proved only by backend/API paths, not reimplemented in mock as a second security source |
| Workbench session | A recoverable client-side state machine inside the project configuration workbench for one domain act (structured DTS edit, candidate file version flow, release baseline, conflict locate, config-set ops, navigation/selection, workspace load, canvas history, or activity timeline). It is not a server artifact and must not be confused with a candidate file version or a config revision |
| Module kind | A module's role in the attribution taxonomy: business category, driver group, node-type unit, or unclassified root. Stated on the module, orthogonal to origin — adopting a node-type unit makes it curated but never makes it a business category (ADR-0010) |
| Business category | A module humans reason in, such as 充电策略 or 电池安全. Holds driver groups and node-type units; never receives bindings |
| Driver group | The binding target a `compatible` resolves to. Holds parameter definitions for every device instance sharing that compatible; instance identity on bindings is `logical_node_id`, not a per-instance module |
| Node-type unit | The binding target a driverless configuration node resolves to via the `node-type` lever. Keyed by bare node name (`nodetype:{name}`); may nest under a business category or another node-type unit. Not one row per topology instance (ADR-0010) |
| Module origin | Who authored a business module: curated (a human made it a business concept), auto-discovered (DTS ingest created it from a device instance or driver group), or unclassified (the fallback bucket for bindings nothing else claimed). A stated fact about the module, never inferred from its name |
| Curated module | A business module a human owns. Ingest may file bindings into it but never renames, moves, or deletes it |
| Auto-discovered module | A module ingest created to hold bindings it could place but no human has claimed. Ingest still owns its name and position |
| Module adoption | The moment an Admin renames, moves, or re-weights an auto-discovered module. The module becomes curated from then on; there is no separate "adopt" action |
| Unclassified queue | Observed-but-unregistered compatibles plus node types ingest could not place. Scaffolding compatibles never enter it; an Admin can dismiss a compatible entry. Bindings with no attribution match park on the unclassified root module (ADR-0010) |
| Dismissed compatible | A compatible an Admin declared out of scope for the module tree. It leaves the unclassified queue without gaining a driver group, and the decision is reversible |
| Driver registration | Stable catalog subject (`DriverRegistration`) declaring a device or logical service is in scope, with `driverNature` and `instanceCardinality`. A taxonomy `driver-group` module places it in the tree but is not the registration itself (ADR-0013) |
| Attribution subject | Stable catalog identity for where a parameter definition belongs: `DriverRegistration` or `NodeTypeDefinition`. Specs bind to subjects + `property_key`; never to a project `logical_node_id` (ADR-0013). Mis-authored subjects are correctable in place (ADR-0017); placement in the module tree is a separate fact |
| Identity correction | Audited governance act that rewrites a definition's `attribution_subject_id` and/or `property_key` while keeping `parameter_specs.id` as a surrogate key. Re-attribution is allowed in any lifecycle; property-key rename only while `referenceCount = 0` (ADR-0017) |
| ParameterSpecVersion | Versioned content of a parameter definition (shape, constraints, docs). Definition lifecycle is draft/active/deprecated; version status is draft/active/superseded. Soft retirement is definition-level (ADR-0014) |
| Policy target | Product-scoped suggested value keyed by `(organization_id, parameter_spec_id, product_code)` in `parameter_policy_targets`. Spec detail, editService, and Agent perception tools still read it; **there is no production writer today** (SE-D1 / TD-055). Do not rebuild a definition-level editor field for it |
| Parse coverage | Whether a compatible is matched by a releasable schema — a pinned `schemas/dts` document (including prefix patterns) or an active organization overlay (exact compatible only). The chip distinguishes platform vs organization coverage |
| Organization driver schema overlay | An org-owned manual driver schema (exact compatible + property definitions) that merges into the schema registry as the lowest releasable tier. Closes "parse uncovered" without editing repository files (ADR-0008) |
| Platform driver schema tier | A promoted overlay row scoped to no organization (`driver_schema_overlays.organization_id IS NULL`), readable by every tenant, matched ahead of org overlays and behind vendor (ADR-0009) |
| Overlay promotion | The reviewed platform act (`platform-admin` / `platform:schema-promote`) that lifts organization overlays into the platform tier, superseding contributing org rows instead of deleting them |
| Platform super admin | Administrator of platform-owned resources and Organization records, who may explicitly operate in any Organization under their own accountable identity ([ADR-0051](docs/adr/0051-organization-provisioning-and-member-admission.md)). Choosing an Operating organization is not impersonating one of its members |
| Observed coverage | Whether a registered driver has produced parameters in at least one project. None means declared but not yet seen, which is a normal state rather than a misconfiguration |
| Not-yet-observed driver group | A registered driver group holding no parameters. Shown in the tree rather than hidden, because being visible before the DTS arrives is why it was registered |
| DTS reload debugging | Product UI title 「参数调试」 on `/dts-reload` — validating candidate parameter values on real hardware by generating a device-tree overlay from library parameters, compiling it, deploying it, and triggering a kernel reload. The unit of work is a batch of parameters reloaded together, never one property at a time. Distinct from node debugging, which reads and writes individual runtime node paths. Distinct from the product-offline legacy `/debugging` route (TD-032) |
| Debug overlay | The generated artifact of one reload run: a `/plugin/` DTS document addressing nodes by absolute `target-path` (never by `&label`), plus the `dtbo` compiled from it. Authored entirely by the platform from resolved bindings; never hand-edited by users |
| Reload run | One attempt to put a set of debug values onto one device: generate, compile, pre-flight against the project base DTB, deploy, trigger, verify. The run is the audit and evidence subject, and it either lands as a whole or fails as a whole. A deploy stamps a `deploy_claimed_at` heartbeat while it holds the run; if the deployer process dies mid-deploy the run would otherwise be stuck in `deploying`, so a maintenance sweep resets runs whose heartbeat is older than the worst-case deploy window (well beyond the device-lease TTL) back to `failed` (`deploy-reclaimed`), making them deployable again without ever reclaiming a live deploy |
| Debug value | A candidate value carried by a reload run. Transient and run-scoped: it never mutates a binding revision, working configuration, draft, or release baseline. Promoting a debug value into the library is a separate governed change request |
| Reload value shape | The normalized value vocabulary a debug value must conform to, resolved server-side from a definition's catalog shape plus its library baseline (baseline inference requires parsing). Four families: integer cell arrays (`/bits/` 8/16/32), GPIO-style phandle cell arrays, single string, and string list. The resolved shape — never the raw catalog kind — decides debuggability, authoring validation, device read-back comparison, and the canonical form compared against decompiled overlays; per-width integer overflow is refused by the DTS value parser itself. Shape knowledge is single-sourced in the `ReloadValueShape` module; unresolved catalog input keeps the name `CandidateValueShape` |
| Reload configuration | The device-side contract a reload run must obey: where the overlay file lands, which kernel node triggers the reload, what payload that node expects, and which command reads the kernel log. Stated as organization defaults (with seeded fallbacks when none are saved), editable only by a debugging admin and resolved server-side from stored records — never accepted from the client, because a client-supplied kernel path or log command is a privileged-execution primitive. Kernel log commands are validated on save against the closed exact allowlist in `@wiseeff/device-command-core/kernelLogCommand` (`dmesg`, `dmesg -T`, `hilog`, `hilog -x`, `cat /proc/kmsg`); the bridge re-validates independently before execution |
| Kernel log evidence | The raw kernel-log excerpt a reload run captures and stores verbatim. Filtering by parameter name happens server-side after capture, so no parameter name is ever interpolated into a device command. Presented to humans as unjudged evidence: the platform never infers success or failure from its text |
| Reload snapshot | The evidence a reload run captures instead of an undoable snapshot: each parameter's library baseline value, the deployed artifact digest verified against the on-device copy, whatever kernel-side signal the platform could obtain, and per-parameter behavioural verification outcomes when debug-node bindings exist. It deliberately makes no device-tree value claim from kernel logs alone |
| Unverifiable reload | The honest default outcome of a reload run: every command succeeded and the artifact landed intact, yet the platform cannot confirm the driver observed the new values — either no selected parameter has a readable debug-node binding, or bound reads failed without a contradiction. Reported as a distinct state from success, never collapsed into it |
| Behaviourally verified | A stronger terminal than unverifiable: every selected parameter that has a readable debug-node binding was read through the existing node-read path and matched the debug value under the parameter's declared value shape |
| Contradicted reload | A terminal where at least one bound debug-node read disagreed with the debug value. Never reported as verified |
| Reload residue | The platform's own bookkeeping that a device was last left carrying debug values rather than baseline. Derived from run history, not from the device, so it goes stale on reboot, reflash, or any manual change made outside the platform, and must be presented with that limitation stated. Keyed to the bridge-derived device id (`bridge:<bridgeId>`), which the server derives from the authenticated bridge rather than trusting a client-supplied device id. Set on ordinary post-write terminals and also, defensively, when the trigger write did not confirm (RPC timeout / transport drop) since the overlay may have applied; a confirmed device rejection leaves it clean. A restore-baseline refuses when a residue parameter's node path has drifted from the current binding rather than compensate the wrong node |
| Restore-baseline | A reload run with `purpose: restore-baseline` whose debug values are the current library baselines for the residue parameter set. It reuses the normal start + deploy path (no shortcut) and clears residue only when it reaches a post-device-write terminal while still targeting the recorded source run |
| Reload purpose | `ordinary` (put debug values on the device) or `restore-baseline` (compensating reload toward library baselines). Stored on `dts_reload_runs.purpose` and surfaced in history / last-reload projections |
| Sensitive reload | The sensitive-node extension of reload start: matching `dts_sensitive_node_rules` additionally requires `parameter:edit-critical`, and critical-tier matches also require `confirmationToken: "confirm-sensitive-reload"`. Distinct from the deploy token `confirm-dts-reload` |
| Parameter reload (retired) | The 2026 M1-era concept binding one parameter definition to one device node path and writing it through sysfs, which also wrote the accepted value back into project parameter values. Never shipped, HTTP surface returned `410` from its first commit, and its binding table was dropped in migration `0037`. Retained here only so the term is not confused with DTS reload debugging |
| Log analysis agent | 「日志分析 Agent」— the autonomous multi-step analysis kernel planned behind the log pipeline's `LogAnalysisAdapter` seam: it iterates read-only tools (log-line retrieval, domain knowledge, context lookups) inside the `rootcause` stage until it lands an evidence-grounded conclusion. Always distinct from Xiaoze, the conversational assistant surface, which only reads finished conclusions and never analyzes. Never a write actor |
| Analysis skill | 「分析技能」— an organization-scoped, versioned description of how to analyze one business module's logs: diagnostic procedure, file applicability, parsing and decoding rules, signal rules, linked knowledge, an optional source snapshot, budgets and test cases. The unit administrators build and integrators publish; the platform supplies everything not specific to a module. Evolves the log domain in place and keeps its identity (ADR-0047). _Avoid_: plugin, Xiaoze skill, log domain (retiring) |
| Skill revision | 「技能版本」— one immutable published state of an analysis skill. Every analysis run pins exactly one, so a report can always say which procedure, rules and decoders produced it; editing creates a draft and never changes a pinned run |
| Diagnostic procedure | 「诊断流程」— the Markdown part of a skill revision telling the log analysis agent how an expert investigates this module: what to check first, which signals matter, how to confirm a root cause. Guidance only; it can never override the platform's read-only, grounded-evidence protocol |
| Log bundle | 「日志包」— everything uploaded for one analysis: one text log, or an archive unpacked into many files. Evidence always names the file and line it cites |
| Decoded event | 「解码事件」— a structured record produced from one log line (or a keyed multi-line group) by a skill's extractor and decoders: typed fields, register bit-fields and frame fields with their meanings, plus the signals it triggered. Always anchored to its file and line, so it can be cited as evidence |
| Decoder | 「解码器」— a declarative rule turning an extracted raw value into named, meaningful fields: register bit-field definitions, register maps selected by address or id, byte-layout frames, lookup tables, scale/offset/unit. Parse scripts, when they arrive, must produce the same decoded events |
| Signal rule | 「信号规则」— a skill-authored condition over lines, fields or decoded values that emits a named, severity-tagged signal for the agent and the rules fallback. Replaces rules written in code; the platform adds generic signals (crash signatures, error bursts, gaps, line templates) that need no skill |
| Source snapshot | 「源码快照」— an immutable, version-labelled upload of a business module's source code, attached to a skill so the agent can trace a log line to the statement that printed it. Reached only through bounded tools, never loaded wholesale into the prompt |
| Parse test | 「解析测试」— a skill test case pairing sample log lines with the decoded fields and signals they must produce. Deterministic and model-free; the analysis-case counterpart runs the real model against expected root cause and evidence |
| Log domain | 「日志业务域」— retiring term, superseded by analysis skill (ADR-0047); existing log domains become skills with the same identity. Originally: an organization-scoped registration of one business's log intake: a format profile plus domain knowledge plus analysis emphasis (for example charging-subsystem kernel log). Tenant isolation stays on `organization_id` and is never part of this term; `log_records.source` stays the intake channel (`upload`), never the domain. _Avoid_: 业务 (bare), business line, tenant |
| Format profile | 「格式画像」— a log domain's statement of how its raw logs are read: timestamp shape, multi-line merge rules, severity mapping, structured-field hints. Parsing stays UTF-8 text indexed by stable line numbers |
| Golden case set | 「金标准案例集」— the shared labelled corpus anchoring log-analysis evaluation: real logs plus expert-confirmed root cause, key evidence lines, and expected actions. One set serves regression gating, model comparison, and online monitoring; synthetic logs count only toward format-coverage checks, never toward quality scores. The deterministic rule analyzer is its fixed comparison baseline |
| Uncategorized log domain | 「未分类域」— the built-in fallback log domain for uploads that state no domain: analysis runs with generic, non-domain knowledge and the upload is never blocked. Mirrors the unclassified-queue pattern from parameter attribution |
| Degraded analysis | 「降级分析」— an analysis result the pipeline still delivers when the LLM path is unavailable after retries or the token budget is exhausted: the deterministic rule analyzer's result, or an early-converged low-confidence agent conclusion. Always marked with its analyzer provenance and never impersonates a full agent analysis — the same honesty rule as unverifiable reload |
| Prefilter findings | 「预筛信号」— the deterministic output of the parse/pattern stages handed to the log analysis agent: candidate anomaly lines, error-code statistics, and rule hits from the legacy rule analyzer. Free high-confidence signals that bound what the model must read |
| Domain knowledge document | 「领域知识文档」— the domain knowledge the log analysis agent retrieves during analysis (error-code meanings, known failure modes, module background). Since the knowledge base landed (P2), this is no longer domain-stored markdown: it means **published knowledge entries linked to a log domain** (`log_domain_knowledge_links`, admin-maintained in `/log-admin`). `read_domain_knowledge` retrieval is bounded to the linked set and inherits published-only retrieval; a domain with no links degrades to organization-wide generic retrieval, mirroring the uncategorized log domain |
| Behavior-layer eval | 「行为层评测」— deterministic fake-model evaluation of the log analysis agent's conduct: tool-call legality, in-budget convergence, honest degradation marking, no conclusion without cited evidence. Runs in CI on every change at zero API cost — the log-analysis sibling of the Xiaoze eval harness |
| Quality-layer eval | 「效果层评测」— real-model evaluation scoring golden-case runs: root-cause accuracy (rubric plus LLM-as-judge with sampled human review), deterministic evidence-line overlap, hallucination and refusal rates. Runs on prompt or model change and before release, gated against the previous baseline minus a stated tolerance |
| Result webhook | 「结果 Webhook」— a log domain's admin-configured HTTPS callback fired best-effort after an analysis reaches a terminal state: a signed compact summary (never raw log content), HMAC-SHA256 over timestamp+body, hard anti-SSRF address policy. A notification channel, never the source of truth — it must not block, fail, or delay the analysis. _Avoid_: SDK (deferred until a real consumer names one) |
| Webhook delivery record | 「投递记录」— one row per result-webhook delivery ATTEMPT (`log_webhook_deliveries`): kind (result/test), attempt number, delivered/retrying/failed, HTTP status or error. Exists for per-attempt honesty in `/log-admin` and metrics; carries no analysis state |
| Judge-human agreement | 「judge-human 一致性」— the quality report's calibration metric comparing the LLM-as-judge against committed human reviews (`eval-cases/logs/reviews/`): exact agreement rate plus mean absolute score difference over the deterministically sampled cases. Honestly "no human reviews yet" until reviews exist; never calibrated against synthetic-only cases |
| Agent approval chain | The orchestrator-owned path every mutating Agent tool call must cross: `beginApproval` persists `agent_tool_calls` + `agent_approvals` rows and raises the interrupt; `resolveApproval` carries the human decision, applies `editedArgs` as a full payload replacement, re-authorizes transactionally, and executes. Its only state is those database rows — never process memory — so begin and resolve may land on different processes (ADR-0024). Approval authorizes the action but never changes its invocation initiator from Agent to user |
| Audited write | A domain write whose audit event commits in the same database transaction — both land or both roll back (ADR-0027). Carried by the `withAuditedWrite` seam and the `AuditTx` proof-of-transaction brand rather than by call-site discipline; correlation (`requestId`) is mandatory at the seam. The legacy audit-outside-the-transaction path is pinned by a ratchet test and retires call site by call site |
| Refusal audit | Deny evidence written when a guard blocks an action and throws (agent on a critical sensitive node, agent on reload mutating paths). The deliberate inverse of an audited write: the throw rolls the caller's transaction back, so the evidence is written through the pool handle via `writeRefusalAudit`, deliberately outside any transaction, and survives the rollback (ADR-0027 amendment) |
| Workflow | 「工作流」— one of the four peer product areas of 雷泽: parameter management, log analysis, debugging, and the knowledge base. The unit of product discovery, not a page, a permission, or an API. _Avoid_: 功能, feature (as the user-facing unit), module, sub-app |
| Workflow discovery visibility | 「工作流发现面可见性」— whether a workflow is offered on the product's discovery surfaces. A hidden workflow is omitted from those surfaces; it is not unauthorized, not retired, and not capability-disabled. _Avoid_: feature flag, interim hide, permission hide, NoEntryPage retirement |
| Workflow publication | 「工作流发布」— the platform-wide product decision to offer an entire workflow's user interfaces to non-administrators, covering both entry points and direct page access. Administrators are exempt from publication restrictions, while existing data and operation permissions and underlying capabilities remain unchanged ([ADR-0050](docs/adr/0050-workflow-publication-is-platform-wide-ui-availability.md)). _Avoid_: permission grant, capability shutdown, per-organization packaging |
| Published workflow | 「已发布工作流」— a workflow offered to non-administrators under the workflow publication policy, subject to their existing permissions. An unpublished workflow remains available to administrators without granting additional data or operation permissions. _Avoid_: enabled API, authorized workflow |
| Visible workflow | 「可见工作流」— a workflow whose entry points are shown to a particular viewer under the publication policy and existing permissions. Visibility to an administrator does not mean the workflow has been published to ordinary users ([ADR-0050](docs/adr/0050-workflow-publication-is-platform-wide-ui-availability.md)). _Avoid_: enabled capability, published workflow (when describing administrator-only visibility) |
| Discovery surface | 「发现面」— a primary wayfinding surface that offers a workflow: the app sidebar group, homepage sub-app cards, homepage flow tabs, homepage header/footer workflow links, and homepage promotional copy that names a workflow as something the product offers. _Avoid_: deep link, contextual cross-workflow CTA, Agent tool, utility nav, 平台总览, incidental mention of another workflow's inputs |
| Knowledge base | The in-product, organization-scoped home for enterprise engineering knowledge: tuning experience, fault cases, hardware manuals, and process norms. A fourth workflow peer to parameter management, log analysis, and debugging. Never means the repository `docs/` developer documentation, which is a development artifact rather than a product surface. Xiaoze reads it through registered tools; agent-authored knowledge always lands as a draft that a human must publish |
| Knowledge entry | The unit of knowledge in the knowledge base. Its content form is exactly one of markdown (created and edited in product, or uploaded as a Markdown or plain-text document, which becomes editable) or file (an uploaded PDF or Word document whose extracted text is searchable while the binary itself is only replaceable). A file whose text cannot be extracted is shown as unsearchable, never as a success. Organization is flat: multi-tags including project tags, never a hierarchy. Lifecycle is `draft → published → archived`. Every published entry is visible to the whole organization |
| Knowledge origin | How a knowledge entry came to exist: authored in product, uploaded by a person, distilled from an analysis outcome, drafted by an agent, or imported with an analysis skill package. Provenance shown to readers only — origin never changes whether an entry is retrievable; publication alone decides that. _Avoid_: user knowledge, platform knowledge (as separate kinds) |
| Knowledge import | Bringing many documents into the knowledge base at once, as several files or one archive. Each document becomes its own draft entry; folder names become tags, never a hierarchy. Publishing stays a separate act under the normal ownership rules |
| Knowledge scope | The set of published entries one knowledge consumer retrieves from: either an explicit set bound to that consumer's own object (an analysis skill, a parameter definition) or the whole organization. Scope narrows retrieval; it never widens it past published entries in the caller's organization. _Avoid_: knowledge filter, knowledge space |
| Reference suggestion | A definition reference the platform proposes for a knowledge entry because the entry's text mentions that parameter definition. Pending until a person who governs the entry accepts it, which creates an ordinary definition reference, or dismisses it, which is remembered so it never returns for that entry and definition. A pending suggestion is not a binding: it never changes any knowledge scope, related-knowledge list or retrieval, and only the entry's governors see it. _Avoid_: auto-link, inferred reference |
| Page citation | A citation of a PDF knowledge entry that names the 1-based physical page (or page range) its text came from, pinned to the revision it was read from, so a reader can open that revision's file at that page. Only PDFs have page citations; other content forms cite by heading |
| Knowledge revision | The immutable snapshot produced by every save of a knowledge entry. Published entries edit in place wiki-style — there is no pending-changes state — and any prior revision can be restored, which itself produces a new revision |
| Agent knowledge draft | A knowledge entry Xiaoze creates through its approval-gated draft tool. Always born `draft`, never modifies an existing entry, and stays invisible to retrieval until a human publishes it; whoever publishes takes responsibility for the content |
| Knowledge distillation | Turning a structured analysis outcome into a pre-filled knowledge draft carrying references to its evidence. Two sources ship today: log-analysis conclusions (MVP) and terminal DTS reload runs (verified / unverifiable / contradicted / failed — the honest outcome is part of the knowledge value) |
| Published-only retrieval | Search, RAG, and Xiaoze only ever see `published` knowledge entries. Draft and archived entries never enter the retrieval index, which makes publishing the single trust gate for knowledge |
| Design token | A named CSS custom property in the single `:root` block of `src/styles.css` that is the only allowed source of a visual value (color, type, spacing, radius, elevation, motion, z-index). Components consume tokens via `var()`/`color-mix()`; raw literals outside the token block are defects (ADR-0026). Scales are specified in `docs/design-docs/ui-design-system.md` |
| Accent | The single interactive brand color family (`--accent`, blue). Buttons, links, active navigation, selection, and focus rings derive from it; a second filled accent (black, teal) on interactive elements is a defect |
| Elevation | The four-level surface-depth vocabulary: `--shadow-1` (rest cards), `--shadow-2` (popovers), `--shadow-3` (dialogs), plus the `--ring` focus ring. Shadows are never invented inline |
